## 실제 공원 통합 확인

설치된 내장 브라우저는 연결 시 두 번 시간 초과되었다. Playwright의 설치된 Microsoft Edge를 대체 수단으로 사용했으며, 세 개의 독립 브라우저 context에서 실제 공원·인증 WS·게임 엔진을 조작했다.

- 계정 101, 202가 최신 맵 일치를 확인하고 `channel-1`에 접속.
- 전통놀이존 E → 선택 카드 → 방 생성 → 다른 계정 참가 → 팀/준비 → 방장 시작.
- 서버 결과에 따라 던지기·이동권 선택·말 선택·목적지 이동. 잡기 및 추가 기회 표시도 관찰.
- 202 계정의 페이지 재로딩·새 소켓 후 동일한 경기 복구.
- 505 관전자 공개 상태 조회, 던지기 불가, 경기 채팅 및 윷판 위치 핑 공유.
- 기권 확인 → 기권 결과가 상대 화면에 반영 → 두 참가자 공원 복귀.
- 긴 화면 검수 중 실제 90초 시간 초과 종료도 별도로 관찰. 남은 차례 표시를 추가했다.
- 일반 네 말 완주와 경로·스택 규칙은 서버 단위 검사로 확인했다. 무작위 실제 브라우저 경기에서 네 말을 모두 완주시키는 장기 검수는 별도다.
- 이동 복귀는 활성 탭에서 입구 벽을 피하는 짧은 WASD 조작으로 두 계정 모두 통과했다. `--movement-only` 실행은 exit 0이며 `movement-red.png`, `movement-green.png`를 남겼다. 전체 흐름은 게임·복구·관전·기권·반응형까지 통과한 뒤 비활성 탭의 첫 W 입력 가정 때문에 마지막 이동 assertion이 실패했다. 탭 활성화/방향 검사를 보완하고 이동 부분을 두 계정으로 다시 통과시켰으며 전체 실행 1회 성공으로 합쳐 보고하지 않는다.

시나리오: `frontend/scripts/verify-yutnori.mjs`. `--movement-only`는 로그인·공원 진입·게임 화면 닫기 후 이동만 재검수한다. 전체 시나리오에서 이미 확인된 게임 동작을 이동만 재확인한 실행 결과와 혼동하지 않는다.

## 제약과 인계

- 실제 회원 DB·외부 OAuth·지갑/정산·MySQL 저장은 이 로컬 검수에 연결하지 않았다. 로그인/프로필/지갑은 기존 loopback fixture이며 게임 판정·맵·이동·소켓은 실제 서버다.
- V186 신규·기존 DB 순차 적용과 종료 기록 INSERT는 MySQL 8.4에서 미확인이다. 담당자 요청문을 채팅에 전달했다. CI/CD·Jenkins·배포/서버 설정 파일은 수정하지 않았다.
- 서버 재시작 시 진행 중인 윷놀이 복원은 보장하지 않는다. 종료 기록 저장 실패는 재시도하지만 메모리 보관 기간/프로세스 종료 이후의 저장은 보장하지 않는다.
- MR·머지는 사용자 명시 요청 전까지 보류한다. Jenkins는 실제 빌드 조회 권한/접속 정보가 없어 결과 미확인이다. 저장소 Jenkinsfile은 dev 대상이다.
- 작업 브랜치는 통합/빌드 성공 후 삭제 조건이 충족되지 않아 유지한다.
