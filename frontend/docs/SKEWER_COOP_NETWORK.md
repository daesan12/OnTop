## 서버 계약

### 입장과 로비

- 신규 참가자는 입구 거리·인증 소켓·검증된 맵·동일 채널·다른 게임/시설 이용 여부를 확인한다. 이미 방을 만든 대기자는 입구 거리만 면제한다. `requireSkewerWaitingPlayer`는 로비 사용 가능 여부를 계속 검사하므로 방장의 위치 보정은 허용하되 다른 게임 이용·접속 종료·채널 이탈은 참가를 막는다.

- `GET /api/v1/minigames/skewer/coop/rooms?channelId=...`: 같은 공원의 대기 방과 본인의 방. 다른 플레이어의 개인 상태는 반환하지 않는다.
- `POST .../rooms`: `{channelId, requestKey, roomName, password}`로 생성 또는 `{channelId, gameId, password}`로 참가. 가게 이름은 1~24자, 선택 비밀번호는 영문·숫자 4~20자다. 빈 비밀번호는 공개 방이다. 이전 클라이언트의 생략 필드는 기본 이름·공개 방으로 처리한다.
- 방 목록에는 `gameId, roomName, hostNickname, locked, players, mine`을 반환한다. 방장 닉네임은 인증 Principal의 계정 프로필에서 읽으며 클라이언트가 보낸 닉네임 필드는 거절한다. 비밀번호는 BCrypt 해시로 메모리에 보관하고 공개 응답·정산에 포함하지 않는다. 해시 계산·검증은 엔진 공유 락 밖에서 한다. 잠긴 방의 신규 입장 검증은 계정별 30초에 5회로 제한한다. 기존 참가자의 복구는 비밀번호를 다시 요구하지 않는다.
- 잘못된 비밀번호는 409 `SKEWER_COOP_PASSWORD_INVALID`, 시도 제한은 409 `SKEWER_COOP_PASSWORD_THROTTLED`다. 공통 인증 만료로 취급하지 않고 게임 화면에서 안내한다.
- `POST .../leave`: WAITING 단계에서는 인원 수와 무관하게 방을 `SKEWER_CANCELLED`로 닫고 두 사람 모두 방 목록으로 돌아간다. 공통 라우터의 점유를 해제하며 정산·보상·랭킹 결과를 만들지 않는다. COUNTDOWN 이후는 기존 공통 `GAME_FORFEIT`로 먼저 종료한다. 종료 결과 닫기도 이 API를 사용한다.
- 화면 흐름은 **방 만들기 / 참가하기 → 이름·선택 비밀번호 입력 또는 가게 카드 목록 → 역할 선택 → 준비 완료**다. 역할/준비 화면의 X와 방 나가기 버튼은 공원 이동 없이 방 목록으로 돌아간다. 목록에서 이전 화면으로 돌아온 뒤 첫 화면의 X로 공원에 나간다. 취소한 방의 늦은 소켓·REST 응답은 클라이언트에서 무시한다.
- 서버는 현재 인증 소켓·맵 검증·공원 채널·위치·시설/착석 상태를 확인한다. 신규 입장은 generated 맵 시설의 위치·yaw에서 계산한 VR 입구를 사용한다. 이미 참가한 본인의 복구는 같은 채널에서 허용한다.
- 다른 게임의 `TableGame`, 판돈 테이블, `CommittedGameStartService`를 꼬치왕 방으로 재사용하지 않는다. 무료 경기의 시작은 두 사람의 서버 준비 상태로 확정한다.

### 공통 소켓

`GAME_RECONNECT_CHECK`, `GAME_STATE_CHECK`, `GAME_ACTION_SEND`, `GAME_FORFEIT`와 기존 인증 소켓을 재사용한다. 꼬치왕 전용 WebSocket 서버나 BroadcastChannel·localStorage로 두 사람을 동기화하지 않는다.

액션은 서버가 확인한 사용자·gameId·actionId·expectedVersion으로 처리한다. `expectedVersion`에는 publicState의 `actionVersion`을 보낸다. 바깥 `version`은 화면 상태/시계/이동 갱신 순서를 나타내며, 표시 틱이 전송 중인 입력을 무효화하지 않는다. `actionVersion`은 실제 업무 행동·접시/테이블 등 의미 있는 상태가 바뀔 때 증가한다. 같은 actionId/동일 내용은 기존 결과를 반환하고, 다른 내용으로 재사용하거나 낡은 행동 토큰을 보내면 거절한다. 프론트는 직렬 전송하고 상태를 다시 읽으며, 낡은 버전은 제한된 횟수만 재시도한다. 연속 이동은 최신 방향과 서버 시간·충돌로 처리한다. 클릭 이동은 서버가 목적지의 유효성과 실제 충돌 경로를 계산한다. 상호작용 가능 안내는 예측 위치 대신 서버 위치를 사용한다.

- publicState: 참가자 역할/준비/연결, 영업 단계·남은 시간·점수·서빙 수, 인사 상태, 랭킹 자격 표시. 주문 원본은 싣지 않는다.

- 현재 관전자는 입장/상태를 허용하지 않는다. 관전자 공통 채팅·핑은 이번 2인 연결 범위에 확장하지 않았다.

- 서버가 6개 테이블(1인 3·2인 3), 대기 손님, 주문과 접시 ID, 영업·식사·청소·세척 시계를 관리한다. 메뉴는 실제 음식 6종으로 조립 가능한 기존 여섯 레시피를 사용한다. 같은 비율의 난도 묶음을 섞는다.
- 전달한 메뉴 점수와 전체 완료 속도 보너스를 서버가 계산한다. 반납·보관·재수령은 접시 소유 위치만 옮기며 점수나 새 접시를 만들지 않는다. 자리 정리 2점·식기 수거 2점은 1.5초 청소 완료 시 확정하고, 세척기 투입은 테이블분당 3점을 확정한다. 취소·중복 투입은 추가 점수가 없다.
- 인사는 한 판에 두 번이다. 인사 중에도 영업 제한시간과 인사 응답 시계(최대 5초)는 진행한다. 영업시간이 0초면 인사보다 경기 종료가 우선한다. 입장·식사·청소·세척과 서빙 속도 측정은 기존처럼 인사 구간을 제외한다. 두 사람의 응답 중 느린 응답으로 보너스를 계산한다. VR 주방에도 공간의 준비/인사 버튼과 인사 안내를 표시한다.
- 한 명이 공원 연결을 잃으면 공동 진행을 정지한다. 30초 안에 같은 계정으로 복귀하면 주문·조립·운반·보관을 유지해 이어간다. 30초 경과 또는 기권은 한 번만 공동 종료한다.
- 요리사가 실제 WebXR 세션을 연결했는지 화면에서 보고하며, 시작 시 비VR이거나 경기 중 PC로 전환하면 해당 경기의 랭킹 자격 제외를 유지한다. 랭킹 저장은 서버 정산과 연결되며, 실기기 사용 보고에 대한 별도 하드웨어 증명은 없다.
- 공통 `GameEngineRouter`의 참가자/테이블 점유와 복구를 사용한다. 무료 엔진이 직접 확인한 세션에만 DB 예약 없는 복구를 허용하며, 기존 판돈 경기는 DB/엔진 일치 검사를 계속 적용한다.
- 엔진은 공통 GameLifecycle 판정 계약을 포함한 별도 무료 완료 알림을 만든다. 판돈 DB 정산 소비자로 잘못 전달하지 않는다. 서버 프로세스 재시작 후의 경기 복원은 구현하지 않았다.
