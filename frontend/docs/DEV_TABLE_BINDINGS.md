# 개발 사이트 테이블 연결

## M04 개발 감정표현 매핑 · 2026-10-25

`public/park-bindings.dev.json`의 `emotes`에 BE 확정 코드 `WAVE`, `CLAP`,
`APPLAUSE_REQUEST`, `TSK`, `FART`를 기존 FE 모션에 각각 연결한다.
정확히 `dev.on-top.world`에서 이 파일을 선택하는 기존 경로를 재사용한다.
기본/운영 `park-bindings.json`은 기존대로 두며, 운영 BE 코드 등록을 추정하지 않는다.
기존 서버 승인 이벤트·시각·쿨다운·이동 취소와 미연결 시 비활성 처리를 유지한다.
시설·수영·게임 중 정책, BE 설정/코드, 인증·테이블 매핑은 이 변경으로 수정하지 않는다.
실제 개발 서버 반영·송수신 검수는 FE 배포 후 별도로 확인한다.

## 기존 테이블 연결 기록

## 담당자 배포 항목

- `public/park-bindings.dev.json`: 위 두 테이블 매핑.
- `src/park/runtime/deployment.ts`: 정확히 `dev.on-top.world`에서 개발 매핑 파일을 선택.
- 개발 Vercel 프로젝트 `ontop-frontend-dev`에 프런트 변경만 배포한다.
- `public/park-bindings.json`은 기존 기본/운영 설정으로 유지한다.
- 백엔드 소스·실행 프로필·DB·인프라 변경은 없다. 배포는 사용자가 지정한 담당자가 진행한다.

실행 서버의 REST 목록에 해당 ID가 있어야 기존 `bindAnchor` 검증이 통과한다.
table-3 등 다른 화면 테이블과 channel-2는 이번 실제 응답에서 확인되지 않아 연결하지 않는다.
로컬 테스트 전용 프로필의 네 개 매핑은 일반 개발 배포에 복사하지 않는다.

## 배포 후 실제 서버 확인

1. `https://dev.on-top.world/park-bindings.dev.json`이 위 두 매핑을 반환하는지 확인한다.
2. 프런트 빌드도 함께 갱신한 뒤 새로고침한다. JSON 파일만 올리면 기존 프런트는 이를 선택하지 않는다.
3. 서로 다른 두 계정으로 개발 공원에 들어가 동일한 table-1 또는 table-2를 선택한다.
4. 각 계정에서 `앉기` → 서버 좌석 확정 후 `일어나기` 표시를 확인한다.
5. 첫 착석자가 `오목 선택`, 두 참가자가 `준비`를 누른다.
6. 준비 완료와 실제 시작을 구분한다. 실제 서버의 PLAYING 상태와 오목판 표시까지 확인한다.
7. 실패하면 화면의 서버 오류 코드와 발생 시각을 기록한다. 인증 헤더·Cookie·접속권은 공유하지 않는다.

로컬 계약 대역의 착석·오목 시작 테스트는 실제 개발 서버의 게임 시작/재화 연동 검증을 대신하지 않는다.
이 변경은 배포 전 상태이며, 개발 사이트의 두 계정 실검증은 담당자 배포 후 진행한다.
