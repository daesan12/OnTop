# 붕어빵 v4 FE 구현 및 BE 연결 경계

2026-10-26. 기준: 전달받은 GAME_PLAN/FE 작업명세/BE 작업명세 v4.
적용 대상은 OnTop 실제 FE이며, 시작점은 최신 카트 가림 수정이 포함된 dev `84afdb3`다.
푸시 전 최신 `origin/dev`의 `0b0f275`를 충돌 없이 fast-forward로 반영했다.
BE 소스·DB·운영 API 계약은 변경하지 않았다.

## 실행과 현재 공개 범위

`frontend/`에서 실행한다.

```powershell
pnpm dev:bungeoppang --host 127.0.0.1 --port 5195 --strictPort
```

기존 로그인·공원 연결을 이용해 카트 앞 E로 진입한다. 월드 서버 연결은 기존 환경 설정이 필요하다.
이 명시적인 Vite 개발 모드에서만 개인 미니게임이 v4 로컬 시뮬레이션으로 실행된다.
실제 엽전을 지급하거나 계정 지갑에 예상 보상을 더하지 않는다. 새로고침하면 미리보기 판은 사라진다.

기본 `pnpm dev`와 프로덕션 빌드는 기존 승인 v2 API를 유지한다.
API 실패 시 v4 목업으로 전환하지 않는다. BE 승인 전 v4 로그를 v2 완료 API에 보내지 않도록 방어했다.
따라서 이번 완료 범위는 **v4 FE 규칙·화면·수명주기·명시적 개발 미리보기**이며,
운영 v4 연결·인증된 주문 발급·실제 재계산/지급 검증은 BE 계약 이후 작업이다.

## 구현한 내용

| 범위 | 동작 |

| 쟁반 | 총 4자리, 선행 생산, FIFO 납품, 여분 보존, 완성품 폐기, 가득 찬 정상 꺼내기 거부 |

| 시점 | 최신 카트 시점/차양 복구 유지, 다른 플레이어 전체 아바타는 숨기지 않음 |

기존 인스턴스 메시·재질을 재사용하며 새 3D 에셋은 추가하지 않았다.
권장값 85~115%, 특수 주문 20%, 보너스 50%, 첫 주문 팥 2개는 `BUNGEOPPANG_V4`에 분리했다.
판 시작 시 규칙 설정을 복사·고정한다. 미리보기 불 400개/주문 64개는 운영 합의값이 아니다.
손님 이탈·벌점·재고 부패·랭킹은 추가하지 않았다.

## BE 담당자와 맞출 연결 지점

`service.ts`의 `BungeoppangService`/판별 `v4`/`nextOrder`는 **FE 내부 포트**이며 REST/DTO 명세가 아니다.
승인된 계약을 받으면 별도 어댑터로 판 원본·현재 주문·규칙 설정·정산 결과를 변환한다.
현재 FE 상태에는 미래 주문 배열이 없으며, 미리보기 발급 원본은 서비스 내부에만 둔다.
납품 확인/다음 주문의 실제 서버 원자성·승인 거부 시 복구 방식은 승인 계약이 필요하다.

- 난수 전달 길이/추가 발급/소진, 시간 정밀도와 마감 포함 여부, 입력 로그 한도
- 현재 주문 식별·납품 멱등 키·다음 주문 재요청·대기 중 타이머/추가 입력 정책
- 탭 비활성·단절·재접속·만료·포기/정산 경합 정책
- 실제 지급액·일일 누계·상한 귀속일·지갑 갱신 및 결과 재조회 계약

미리보기 정책은 납품 점수/재고를 즉시 **예상 반영**하고 다음 주문을 기다리며 타이머/조리는 계속한다.
요청 실패 시 같은 납품 직후 기록을 재사용한다. 이를 운영 확정 정책으로 간주하지 않는다.

언어 중립 참고 데이터: `tests/fixtures/bungeoppang-v4.json`.
입력 원본·로그·예상 점수뿐 아니라 불 소비 수·주문 위치·재고·콤보 기대값을 포함한다.
`rulesV4.ts`와 해당 fixture는 Java BE에서 같은 결과를 비교하기 위한 참고 자료이며 서버 구현을 대신하지 않는다.

## 검증 명령

```powershell
pnpm typecheck:tests
pnpm exec vitest run tests/unit/bungeoppangPresentation.test.ts tests/unit/bungeoppangV4.test.ts tests/unit/bungeoppang.test.ts tests/unit/bungeoppangService.test.ts tests/unit/bungeoppangSession.test.ts tests/unit/manual.test.ts tests/unit/cameraReturn.test.ts tests/unit/avatarMotion.test.ts
pnpm build
pnpm exec playwright test --config playwright.bungeoppang.config.ts
pnpm exec playwright test --config playwright.bungeoppang-legacy.config.ts
```

Browser plugin not available이므로 기존 Playwright/Edge를 사용한다.
v4 검증 흐름: 공원 E → 시작 → 재료/IME/F1 입력 → 서로 다른 속도의 양면 조리 → 쟁반 → 납품 → 37/40초 안내 → 실제 60초 종료 → 결과 → 재시작/포기/공원 복귀.
PC 1280×720·1440×900을 대상으로 하며 모바일은 지원/검증 범위가 아니다.
v2 회귀는 HTTP/월드 테스트 대역으로 기존 승인 API 동작을 확인한다. 실제 개발 DB 지급 검증은 별도다.

기존 빌드의 500kB 초과 청크 경고 및 Three.Clock/WebGL 셰이더 정밀도 경고는 남는다.
추가 기기·GPU·브라우저 성능, 실제 BE v4 계약/E2E·지갑 지급은 미검증이다.

## FE 연출 보강 — 2026-10-26

현재 주문·재고를 읽는 표시만 보강했다. 순수 게임 규칙·운영 API·실제 보상 정책은 바꾸지 않았다.

| 플레이어가 인지해야 하는 것 | 추가한 연출 |
| --- | --- |
| 손님이 오고 기다리는 느낌 | 주문 카드의 작은 SVG 손님이 걸어와 인사하고 대기한다. 주문이 준비되면 말풍선이 바뀌며, 납품한 손님은 봉투를 들고 떠난다. 다음 주문이 실제 도착한 뒤 새 손님이 들어온다. |
| 재료가 바뀐 사실 | 팥 적갈색·슈크림 노랑·피자 주황·초코 짙은 갈색을 실제 소 인스턴스와 모든 재료 마커에 함께 사용한다. 선택 테두리·도구 아이콘·현재 든 재료 안내가 키/휠/버튼에 동일하게 반응한다. |
| 칸마다 다른 불 | 약불/보통불/센불, 불꽃 1~3개, 배정 백분율과 현재 굽기 배율을 함께 표시한다. 40초 몰림부터는 같은 배정 불을 유지하면서 현재 배율이 높아진다. |
| 지금 뒤집거나 꺼낼 타이밍 | 익힘 게이지에 50/70/90 기준을 표시하고, 앞면/뒷면·설익음/황금/곧 탐/탐을 문자로 읽을 수 있다. 프레임마다 React 상태를 갱신하지 않고 기존 DOM refs를 사용한다. |
| 쟁반으로 실제 이동 | 정상 꺼내기에만 해당 빵이 철판에서 쟁반으로 날아가고, 2×2 쟁반에 재료 마커·보관 점수가 남는다. |
| 무엇을 버렸는지 | 철판 폐기·쟁반 폐기·실패 빵이 폐기함으로 이동한다. 뚜껑과 실제 폐기/실패 누계가 반응하며 이유와 무득점을 안내한다. 가득 찬 쟁반의 정상 꺼내기 거부는 성공 연출을 만들지 않는다. |
| 무엇이 손님에게 갔는지 | 납품에서 실제 소비한 재고만 손님 쪽으로 이동한다. 여분은 쟁반에 남는다. |

새 손님은 주문 카드 내부의 2D 연출이며 공개 월드 NPC/실제 아바타의 이동·점유 이벤트를 만들지 않는다.
새 모델·이미지·텍스처·재료별 메시를 추가하지 않았다. 소는 기존 단일 InstancedMesh의 인스턴스 색상을 사용한다.
밤에는 개인 반죽·빵·소의 색상을 유지하는 최소 밝기를 적용한다. 공원의 조명이나 다른 오브젝트는 바꾸지 않는다.
모션 감소 설정에서는 걷기·불꽃·이동·팝 애니메이션을 줄이고 문자·수량·선택 상태로 피드백을 유지한다.
연출용 큐는 판별로 초기화하고 개수를 제한한다. 화면 연출이 조리/납품 로그에 추가 행동을 만들지는 않는다.

### 화면/성능 확인

검증 장면: Windows, Headless Edge 156/WebGL 2, Intel Arc Graphics/Direct3D11, Low,
1280×720, 월드 fixture 4명, 동일 카트 시점·낮, 네 종류 소를 앞면 조리 중. 전후 각 90프레임의 짧은 표본이다.

| 측정 | 보강 전 | 보강 후 |
| --- | ---: | ---: |
| 장면 draw calls 중앙값 | 56 | 57 |
| 장면 triangles 중앙값 | 265,110 | 265,710 |
| 개인 철판 geometry/material 수 | 5 / 6 | 5 / 6 |
| 개인 철판 버퍼 추정 | 40,428 B | 40,500 B |
| 장면 geometry 버퍼 추정 | 42,355,434 B | 42,355,434 B |
| 장면 텍스처 추정 | 121,498,283 B | 121,498,283 B |
| RAF 프레임 간격 중앙값/p95 | 8.3 / 9.3 ms | 8.3 / 9.5 ms |

추가 1 draw call/600 triangles는 소를 투입 직후 잠깐만 보이던 방식에서 앞면 조리 중 계속 보여주는 기존 인스턴스 배치 비용이다.
추가 버퍼 72 B는 6개 소의 RGB 색상이다. 새로운 모델·텍스처 전송은 없다.
전체 GPU resource 수는 월드 스트리밍 시점에 따라 변동했으며, 이 차이를 개인 철판의 신규 자원으로 간주하지 않는다.
개발 서버의 전송량 표본은 약 7 MB로 캐시/모듈 재검증 영향을 받으므로 프로덕션 전송 최적화의 근거로 사용하지 않는다.
GPU 실행시간·별도 CPU 프로파일·장시간 자원 수명/누수·다른 장비의 성능 검증은 미완료다. FPS 보장이나 성능 개선 주장에 쓰지 않는다.

`presentation.spec.ts`는 소의 실제 인스턴스 색상, 도구 전환, 쟁반 보관·폐기·실패·납품·손님 퇴장,
밤/모션 감소, 몰림 배율과 오류 화면 부재를 확인한다. 기존 실제 60초·v2 서버 계약 회귀와 함께 사용한다.
보강 스냅샷/원시 측정은 Codex visualizations의 `bungeoppang-feedback/`에 있다.
