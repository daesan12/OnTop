# 붕어빵 v4 서버 시각 동기화와 DEV 검증 인계

작성일: 2026-10-27 (Asia/Seoul)

## 구현 범위

게임마다 서버가 발급한 `playStartsAt`을 사용한다. 플레이어들이 동시에 시작하는 기능이 아니다.
기존 `playStartsAt - Date.now()` 계산을 제거하고, 시작 POST 직후 본인 판 GET을 조회한다.
GET 송신/수신은 `performance.now()`로 측정하며, 수신 시 서버 시각을 `serverNow + RTT/2`로 추정한다.
이 관측을 브라우저의 단조 시계에 연결해 카운트다운·행동 t·40초 가속·60초 종료를 계산한다.
PC 날짜/시계가 달라도 판의 기준을 바꾸지 않는다. RTT 보정은 추정이며 비대칭 지연을 완전히 제거하지 않는다.

- `countdownStartsAt` 전에는 준비 중, 이후 실제 남은 카운트다운을 표시한다.
- 시작 응답이 늦으면 이미 지난 시간을 포함해 남은 시간부터 진행한다. 새로운 60초를 주지 않는다.
- POST 시작 영수증이 재생돼도 GET의 현재 상태를 확인한다. 완료된 판이면 확정 결과를 표시하고, 포기/만료 판은 플레이하지 않는다.
- RTT가 1초를 넘으면 같은 판 GET을 최대 3회 측정한다. 계속 느리면 같은 시작 키로 재시도할 수 있게 안내한다.
- 탭 복귀·온라인 복귀·납품의 `TIME_AHEAD` 복구에서는 시간을 재확인한다. 기존 로그와 납품 재시도 키는 변경하지 않는다.
- 재확인 중이거나 실패한 상태에서는 조리 입력을 막고, 기존 타이머는 계속 진행한다. 실패하면 시간 재확인 버튼을 제공한다.
- 뒤로 보정돼 이미 기록된 행동보다 현재 시간이 앞서 있으면 기존 입력 간격 검사가 합법 시점까지 새 기록을 막는다.
- 재동기화가 종료와 겹치면 입력은 닫고, 시각 확인 후 고정된 기록으로 정산한다. 이전 방문의 늦은 응답은 무시한다.
- v2 서비스와 명시적 v4 로컬 미리보기의 시간 흐름은 유지한다. BE 규칙·DB·보상 정책은 변경하지 않았다.

계약: [FE·BE v4 계약 §3](../../docs/minigame-bungeoppang-v4-contract.md).
페이지 새로고침이나 월드 연결 해제로 잃은 미승인 로컬 기록까지 복구하는 기능은 이번 작업 범위가 아니다.

## 실제 DEV 사전 조회 결과

2026-10-27 12:10 KST, 사용자가 전용 브라우저에서 직접 로그인한 회원 계정으로
`https://dev-api.on-top.world`에 실제 인증 요청을 보냈다. 이 조회에는 HTTP 응답 대역을 사용하지 않았다.

| 요청 | 실제 응답 |
| --- | --- |
| `GET /api/v1/wallets/me` | 409 `WALLET_NOT_READY` |
| `GET /api/v1/minigames/sessions?rulesVersion=v4` | 503 `MINIGAME_UNAVAILABLE` |

사용자에게 전달받은 BE 답변: DB 연결 이전에 생성된 계정에 지갑이 없으며, BE 담당자가 수정 중이다.
503의 상세 원인은 위 응답만으로 단정하지 않는다. 지갑 수정 후 두 조회를 함께 다시 확인해야 한다.
이 단계에서 **게임 시작·납품·완료·지급 요청은 보내지 않았으며**, DB나 회원 지갑을 직접 수정하지 않았다.
따라서 실제 DEV 납품·엽전 지급 검증은 미완료이고 BE 수정 이후 재개한다.
로그인 비밀번호·Access 토큰·쿠키는 검증 결과 파일이나 저장소에 기록하지 않는다.

## BE 수정 이후 재개 순서

1. 동일 개발 계정으로 로그인하고 위 두 GET이 200인지 확인한다. v4 지원, 지갑 준비, 일일 남은 한도를 확인한다.
2. 진행 중인 판이 있는지 확인한다. 다른 플레이 중인 판을 임의로 새 시작 요청으로 종료하지 않는다.
3. 지갑 잔액 W0와 오늘 미니게임 획득 C0를 기록하고, 로컬 최신 FE를 개발 API에 연결한다.
4. 실제 시작 POST → 본인 판 GET의 시각 보정 → 카운트다운 → 첫 주문 팥2 조리를 진행한다.
5. 실제 deliveries 200에서 승인·소비 빵·현재 다음 주문을 확인한다. 납품 시에는 지갑이 W0 그대로여야 한다.
6. 실제 60초 종료 후 complete의 서버 확정 점수, 납품 수, 계산/실제 지급액을 확인한다. 일일 상한을 함께 대조한다.
7. 지갑 GET의 잔액이 W0 + 실제 지급액인지 확인한다. 검증 중 다른 지갑 거래가 있었다면 해당 증감도 구분한다.
8. 결과 GET과 동일 키·동일 본문 완료 재조회에서 결과가 같고 추가 지급이 없는지 확인한다.
9. 종료 직전 납품과 완료 응답 유실 복구는 위 기본 흐름 이후 동일 판의 멱등성을 유지하며 검증한다.

일일 남은 한도가 0이면 0냥 정산은 확인할 수 있지만 양수 지급 성공으로 보고하지 않는다.
기존 격리 DB E2E는 전용 계정/DB를 가정하므로 공용 DEV에 그대로 실행하지 않는다.
공용 DEV 검증에서는 계정 생성·지갑 초기화·DB 시각 조정·데이터 삭제·보상 한도 초기화를 수행하지 않는다.
원장/DB 직접 대조가 필요하면 BE 담당자의 검증 결과와 구분해 기록한다.

## 검증 방법

```powershell
pnpm typecheck:tests
pnpm test
pnpm build
pnpm exec playwright test --config playwright.bungeoppang-legacy.config.ts
pnpm exec playwright test --config playwright.bungeoppang.config.ts
```

`legacy`는 설정 파일의 과거 이름이다. 현재 기본 v4 HTTP 어댑터와 시간 동기화 시나리오를 실행한다.
브라우저 테스트는 공원/인증/미니게임 HTTP fixture를 사용하므로 실제 DEV 지급 성공의 근거로 쓰지 않는다.
Browser plugin not available로 기존 Playwright/Edge를 사용한다. 앱 도구 런타임도 초기화 오류가 있어 전용 Edge로 실제 로그인을 진행했다.
