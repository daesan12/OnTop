# 소리함·익명 메모함 BE 요청 사항

작성일: 2026-10-29. 이번 FE 작업과 별도로 BE 담당자가 진행할 내용만 정리했습니다. 이 문서는 BE 구현 완료나 실제 환경의 저장 성공을 의미하지 않습니다.

## 무엇을 해주시면 되나요?

| 대상 | BE 담당 작업 | 완료 후 FE 동작 |
| --- | --- | --- |
| 익명 메모 주제 | 메모의 `category` 저장 및 작성·목록 응답 확장 | 사용자가 고른 주제가 새로 접속해도 유지됨 |
| 새 메모 알림 | 새 글의 DB 커밋 성공 시 변경 이벤트 전파 | 다른 사용자가 글을 쓴 순간에만 열린 목록 갱신 |
| 개발 환경 연결 | 기존 메모·소리함 API 활성화·배포 상태 확인 및 실저장 공동 검수 | 로컬 목업이 아닌 실제 서버에서 작성·조회 확인 |

소리함은 기존 비공개 의견 API를 그대로 사용하므로 신규 API·DB 필드를 요청하지 않습니다. 기와 에셋·펼치기·접기·만년필 연출도 FE에서 처리합니다. 기존 에셋 좌표와 충돌 범위를 유지했으므로 이번 디자인 때문에 맵 충돌 데이터를 바꿀 필요는 없습니다.

## 1. 익명 메모에 주제 추가

대상 API는 `POST /api/v1/notes`, `GET /api/v1/notes?channelId=...`입니다.

현재 저장소의 `NotesController`는 작성 요청을 정확히 세 필드로 제한하고, `NoteResponse`는 `id`, `text`, `createdAt`만 반환합니다. 선택적 `category`를 허용하도록 요청 검증·저장 모델·응답·관련 테스트를 함께 확장해주세요. DB 변경이 필요하면 기존 버전을 덮어쓰지 않고 팀의 마이그레이션 순서에 맞춰 추가해주세요.

| category | 화면 표시 |
| --- | --- |
| `daily` | 일상 |
| `cheer` | 응원 |
| `worry` | 고민 |
| `recommend` | 추천 |
| `free` | 자유 |

요청 예시의 operationId는 형식 설명용이며 실제 값은 FE가 작성 시점에 발급합니다.

```json
{
  "operationId": "1793206800000_0123456789abcdef",
  "channelId": "channel-1",
  "text": "오늘도 좋은 하루 보내세요!",
  "category": "cheer"
}
```

처리 규칙:

1. `category`를 생략한 기존 클라이언트와 기존 글은 `free`로 처리합니다. 명시적으로 잘못된 값을 보내면 업무 오류로 거절해주세요.
2. POST 성공 응답의 `note`와 GET의 각 메모에 저장된 `category`를 반환합니다. 기존 ISO 8601 시각과 `nextAllowedAt` 형식은 유지합니다.
3. 공개 메모 필드는 `id`, `text`, `createdAt`, `category`로 제한합니다. 작성자 정보는 반환하지 않습니다.
4. 중복 요청 비교에도 주제를 포함합니다. 같은 사용자·operationId·본문·주제는 기존 접수 결과를 반환하고, 같은 키로 주제만 바꾸면 `IDEMPOTENCY_CONFLICT`로 거절합니다.
5. 본문 1~300자, 정규화, 최신 120장, 작성 15초·조회 1초 제한, 서버 위치·높이·활동 검사와 인증·익명성 정책은 유지합니다. 주제 때문에 본문 길이를 줄이지 않습니다.

FE는 호환성을 위해 `VITE_NOTES_CATEGORIES=false`를 기본으로 사용합니다. 현재 일반 서버 모드에서는 기존 세 필드만 전송하고 주제 선택은 비활성화합니다. BE 구현·공동 검수 후 **FE 빌드 환경**에 `VITE_NOTES_CATEGORIES=true`를 설정해 다시 빌드·배포해야 선택과 전송이 켜집니다. BE 환경변수만 설정하면 켜지는 기능은 아닙니다.

## 2. 다른 사용자의 작성 알림

2초 주기 조회는 FE에서 제거했습니다. 현재 본인 글은 POST 성공 응답으로 즉시 목록에 합치며, 다른 사람의 글은 메모함 다시 열기·새로고침으로 확인합니다. 자동 갱신을 완성하려면 생성 알림 계약과 후속 FE 연결이 필요합니다.

새 메모를 DB에 저장한 뒤에만 변경 알림을 발행해주세요. 이벤트 이름·전달 경로·revision 규칙을 먼저 공유해주세요. 아래는 합의 전 제안입니다.

```json
{"type":"NOTES_CHANGED","payload":{"revision":"1234"}}
```

- 이벤트에는 본문·작성자 ID·닉네임·IP·추적값을 담지 않습니다.
- 게시판은 현재 전 채널 공용입니다. 여러 채널·서버 인스턴스의 적절한 구독자에게 변경 알림이 도착하도록 해주세요.
- 저장 실패에는 알림을 보내지 않습니다. 동일 요청 재확인으로 글이나 생성 알림이 중복되지 않게 해주세요.
- 폴링을 복원하는 방식은 피해주세요. 읽기 제한을 유지하고 이벤트가 모이면 FE에서 합쳐 조회할 수 있게 합니다.

FE 후속 작업은 합의된 이벤트를 `notesService.subscribe()`에 연결하는 것입니다. 현재 실제 REST 서비스의 구독은 no-op이며 이벤트 수신이 구현된 상태가 아닙니다. FE에 열린 방문만 갱신하고 조회를 합치며 닫기·단절 시 정리하는 포트는 준비되어 있습니다. 이벤트 연결 후에도 작성 중인 원문·선택·커서를 보존하고 기존 목록을 지우지 않아야 합니다.

## 3. 기존 API 활성화와 실제 환경 검수

기존 구현을 새로 만드는 요청이 아닙니다. 현재 개발 환경에 다음 API가 활성화·배포되어 있는지 확인해주세요.

- 소리함: `POST /api/v1/feedback`, 관리자용 `GET /api/v1/admin/feedback`.
- 익명 메모함: `GET /api/v1/notes`, `POST /api/v1/notes`.

메모 API는 저장소 기준 opt-in 설정과 별도 DB 마이그레이션 경로를 사용합니다. 필요한 `NOTES_ENABLED`, `NOTES_PRIVACY_SECRET`, `classpath:db/notes`와 적용 이력은 기존 실행 명세에 따라 BE 담당자가 확인해주세요. 비밀키 값은 문서나 전달 메시지에 적지 않습니다. 과거 404 기록만으로 현재 환경의 원인을 단정하지 않습니다.

소리함은 관리자만 읽는 비공개 의견이며 5~600자를 유지합니다. 소리함의 선택 주제는 현재 `[게임 개선]` 같은 본문 접두사로 전달되고 600자에 포함됩니다. 별도 `category` 필드 추가나 일반 사용자에게 공개하는 API는 요청하지 않습니다.

구현·배포 후 아래 정보를 FE에 알려주세요: 적용 커밋·환경·배포 시점, category 요청·응답 예시, 생성 이벤트 이름·전달 경로·payload·revision 규칙, 기존 클라이언트 호환 결과. 새 비밀값을 전달할 필요는 없습니다.

## 완료 확인 순서

1. 주제를 선택해 작성한 메모가 재조회·새 접속·다른 사용자에서도 같은 주제로 표시됩니다. 기존 글은 자유로 나옵니다.
2. 저장 실패에는 성공 연출·생성 알림이 없고, 응답 유실 후 같은 키로 재시도하면 중복 글이 생기지 않습니다. 같은 키로 주제만 바꾸면 충돌합니다.
3. 두 사용자가 목록을 열고 기다려도 정기 GET이 발생하지 않습니다. 한 명이 작성하면 본인은 ACK 병합, 다른 사용자는 합의된 이벤트로 갱신합니다.
4. 위 이벤트 연결은 FE 후속 작업까지 완료한 뒤 공동 검수합니다. category 플래그를 켜는 것만으로 실시간 갱신이 되지는 않습니다.
5. 소리함 의견의 실제 저장과 관리자 조회를 확인하고, 일반 사용자에게 의견이 노출되지 않는지 확인합니다.
6. 인증·거리/높이·활동·읽기/쓰기 제한과 메모 익명성, 실패 시 초안 보존을 함께 확인합니다.

참고: [FE 구현·연동 상세](../NOTES_BOARD_BE_REQUEST.md), 저장소 루트의 `docs/notes-api.md`, `docs/feedback-api.md`. 기존 API 문서의 “2초 폴링”은 과거 설명이며 이번 FE는 사용하지 않습니다. BE 계약 확장 시 해당 설명도 함께 갱신해주세요.
