# 감정표현·테이블 착석 피드백: BE 연동 대기

작성일: 2026-10-27 (KST). 작업본: `OnTop/frontend-avatar-feedback`, 보존 브랜치: `wip/frontend-emote-seat-be-pending`, 기준 커밋: `d387c94`.

**상태: BE 연동 대기 — 이 브랜치는 dev 머지·배포 대상이 아닙니다.** 감정표현과 공개 착석의 FE 시안 및 BE 요청 문서를 별도로 보존합니다. 아래 BE 항목의 계약 확정·구현과 실제 두 계정 검수 후 dev를 다시 반영하고 통합 검증해야 합니다.

수영 팔 방향 수정과 그 테스트는 최신 dev `2930a56`에서 만든 별도 브랜치 `fix/frontend-swim-forward`로 분리했습니다. 이 보존 브랜치의 수영 구현은 변경하지 않았으며, 아래 수영 관련 설명과 기존 검증 숫자는 분리 전 통합 시안의 이력입니다.

이번 변경은 FE 코드와 테스트, 전달 문서만 포함합니다. BE·DB·인프라 코드는 수정하지 않았으며 서버 배포도 진행하지 않았습니다. 아래 BE 분석은 해당 커밋의 소스 기준이며 현재 운영 배포본을 실측한 결과는 아닙니다.

## 먼저 확인할 내용

| 사용자 피드백 | FE 작업 | BE 후속 작업 |
| --- | --- | --- |
| 수영할 때 팔이 뒤로 돌아감 | 양쪽 팔이 앞으로 회전하도록 수정 | 신규 작업 없음 |
| 방귀 동작이 이동하면 끊김 | 이동 입력·이동 좌표 수신 중에도 기존 시작 시각으로 계속 재생 | `FART`에 이동 취소 예외 적용 필요 |
| 감정표현 취소 후 다른 표현을 바로 쓰고 싶음 | 취소 시 FE 쿨다운·요청 잠금 해제, 이전 응답 격리 | 취소된 표현의 서버 쿨다운 해제 정책 변경 필요 |

수영 방향은 별도 수영 브랜치의 FE 배포로 반영됩니다. 이 보존 브랜치의 나머지 세 항목은 FE 변경만 배포하면 실서버에서 완전히 해결되지 않습니다. 특히 FE는 서버가 보낸 `WORLD_EMOTE_CANCELLED`를 계속 적용하므로 기존 BE가 방귀를 취소하면 화면에서도 종료됩니다.

## 1. 방귀는 걸어도 계속 재생하도록 변경해주세요

### 현재 원인

`TableHub`는 이동 요청 처리와 월드 물리 갱신 경로에서 `cancelEmote(userId, "MOVEMENT")`를 호출합니다. `WorldEmoteService.cancel()`은 표현 종류를 구분하지 않고 마지막 이벤트를 제거하고 취소 이벤트를 생성합니다.

그래서 FE의 이동 취소만 제거해도 BE에서 `WORLD_EMOTE_CANCELLED`가 도착하면 다시 끊깁니다.

### 요청 작업

- 승인된 표현의 코드가 `FART`이고 취소 사유가 `MOVEMENT`일 때는 재생을 취소하지 말아주세요. `lastEvents`도 제거하지 말고 취소 이벤트도 방송하지 않아야 합니다.
- 이동 요청 경로와 물리 갱신 경로 양쪽에 동일하게 적용해주세요. 가능하면 `WorldEmoteService`의 공통 정책에서 처리해 경로별 차이를 방지해주세요.
- `FART` 이외의 표현은 기존 이동 취소 동작을 유지해주세요. 시설 이용 시작·채널 이탈·접속 종료 같은 상태 변경 취소도 유지합니다.
- 단순히 이미 시작한 방귀가 걷기·달리기·점프 때문에 끊기지 않게 하는 요청입니다. 이동 중 새 감정표현을 시작하는 기능이나 무한 재생 요청은 아닙니다.
- 입수·수영 전환은 기존 활동 충돌 정책을 유지합니다. 필요하면 취소 사유를 활동 변경으로 명확히 구분해주세요.

FE는 현재 재생 중인 방귀와 승인 대기 중인 방귀를 이동 때문에 지우지 않고, `sentAt`을 유지합니다. 재전송하거나 매 이동마다 재생을 처음부터 시작하지 않습니다. 다른 사용자가 움직이는 경우에도 동일하게 처리합니다.

## 2. 취소한 감정표현의 긴 재사용 대기를 해제해주세요

### 현재 원인

`WorldEmoteService.create()`는 사용자별 `lastSent`에 `max(minimumInterval, 표현별 cooldown)`을 저장합니다. 기본 최소 전송 간격은 코드상 1초이며 설정으로 변경할 수 있습니다. `cancel()`은 마지막 표현을 제거하지만 `lastSent`의 재사용 제한을 유지합니다. `WAVE`·`CLAP`은 현재 설정상 5초이므로, FE 버튼을 열어도 BE가 `EMOTE_TOO_FREQUENT`로 거절할 수 있습니다.

### 요청 작업

- 실제로 현재 표현이 취소되면, 그 표현에 묶인 5초/1.8초 재사용 대기가 다음 표현을 막지 않도록 해주세요. 취소 후 멈춘 사용자가 다른 표현을 바로 선택하면 승인되어야 합니다.
- 표현 재사용 제한과 서버 보호용 전송 제한을 분리해 검토해주세요. 기존 1초 전송 제한이 새 표현까지 막으면 사용자 요청의 “즉시 사용”은 충족되지 않습니다. 유효한 취소 직후 다음 표현을 허용하는 정책과 별도의 과다 요청 제한을 정하고 실제 적용값을 회신해주세요.
- 이미 끝난 표현이나 오래된 취소가 새 표현의 쿨다운·이벤트를 제거하지 않도록 현재 이벤트 ID와 재생 유효 기간을 확인해주세요. 현재 `lastEvents`에는 만료된 이벤트도 남을 수 있어, 이동마다 무조건 `lastSent`를 지우는 방식은 피해주세요.
- 기존 `WORLD_EMOTE_CANCELLED`의 `emoteEventId`, `reason`, `sentAt` 계약은 유지해주세요. FE는 정확히 일치하는 이벤트에만 서버 취소를 적용합니다.
- 재생을 정상 완료한 경우의 기존 쿨다운은 유지합니다. 시설 이용 중·수영 중 등 표현을 시작할 수 없는 상태 제한도 유지합니다.

FE는 이동 등으로 취소되면 `readyAt=0`, `pending=false`로 변경하고 이전 요청의 세대와 request ID를 격리합니다. 이전 승인·거절·비동기 종료가 늦게 도착해도 새 선택의 대기시간, 오류, 재생 상태를 덮어쓰지 않습니다. 실제 이동 중에는 기존처럼 “잠시 멈춘 뒤 사용” 안내를 유지합니다.

이번 FE에서 새로운 임의 취소 요청 API는 추가하지 않았습니다. 사용자가 별도 버튼으로 명시적으로 취소하는 기능까지 추가하려면 현재 서버 계약에 해당 요청이 있는지 별도 합의가 필요합니다.

## 3. 테이블에 참여하지 않은 주변 사용자에게도 착석 상태를 보내주세요

### 재현과 원인

1. A와 B가 같은 공원 채널에 있습니다.
2. A만 테이블에 앉으면 A는 자기 화면에서 앉아 있습니다.
3. B는 아직 테이블에 참여하거나 관전하지 않아 A를 서 있는 것으로 봅니다.
4. B도 같은 테이블에 앉으면 `TABLE_STATE`를 받아 A와 B가 모두 앉은 모습으로 보입니다.

현재 `TableHub.publish()`는 해당 테이블 참가자에게 `TABLE_STATE`, 관전자에게 `TABLE_WATCH_STATE`를 보냅니다. 일반 주변 사용자는 대상이 아닙니다. `WorldChannelRegistry.Avatar`와 FE `WorldState`에는 현재 테이블·좌석 번호가 없고, 테이블 요약의 인원수만으로는 누구의 어느 좌석인지 알 수 없습니다. 위 현상은 이 구조와 일치합니다.

### 요청하는 공개 데이터 계약 — 신규 제안, BE 적용 필요

기존 `WORLD_STATE.payload.avatars[]`에 아래 `tableSeat` 필드를 추가하는 안으로 FE 수신 처리를 준비했습니다. **현재 BE가 이미 제공하는 필드가 아닙니다.** 다른 명세를 사용한다면 확정 후 FE를 그 명세에 맞춰야 합니다.

```json
{
  "userId": "101",
  "position": {
    "lastInputSeq": 7,
    "x": 0,
    "y": 0.8,
    "z": 34,
    "yaw": 0,
    "moving": false,
    "running": false,
    "swimming": false
  },
  "tableSeat": {
    "tableId": "실제-서버-tableId",
    "seatNumber": 1
  }
}
```

이 예시는 아바타 한 항목입니다. 나머지 기존 프로필·장비 필드는 기존 계약대로 유지합니다.

| 값 | 의미 / FE 처리 |
| --- | --- |
| `tableSeat: { tableId, seatNumber }` | 서버가 승인한 공개 착석 상태. `seatNumber`는 기존 `TABLE_STATE`와 동일한 **1부터 4까지의 정수** |
| `tableSeat: null` | 테이블에 앉아 있지 않음. 이전에 받은 원격 착석 자세도 해제 |
| 필드 생략 | 이전 BE와의 호환용. 기존 `TABLE_STATE`/`TABLE_WATCH_STATE`에 의존하므로 주변 사용자 문제는 해결되지 않음 |

### BE 구현 범위

1. 서버가 보유한 `seating`과 실제 `TableRoom` 좌석에서 사용자별 공개 착석 값을 구성해주세요. FE가 사용자 ID·좌석·최종 좌표를 보내서 결정하는 방식은 사용하지 않습니다.
2. 같은 채널의 **테이블에 참가·관전하지 않은 사용자**도 받는 `WORLD_STATE`에 넣어주세요. 새 필드가 켜진 뒤에는 서 있는 사용자도 반드시 `tableSeat:null`을 보내야 과거 착석 표시가 남지 않습니다.
3. 착석·퇴장·강제 퇴장·접속 종료 등 좌석 변경 시 월드 버전을 증가시키고 다음 방송에 반영해주세요. 좌표 변화가 없더라도 좌석만 바뀌면 변경으로 취급해야 합니다.
4. 채널 최초 입장·재접속의 초기 전체 스냅샷에도 이미 앉은 사용자들의 상태를 포함해주세요. A가 앉은 뒤 들어온 B에게도 첫 화면부터 착석이 보여야 합니다.
5. `tableId`는 해당 채널의 실제 테이블 ID를 사용해주세요. FE는 기존 `park-bindings` 매핑과 `tableSeats()`를 사용해 좌석 위치·방향·모션을 표시합니다. 알 수 없는 ID를 거리나 테이블 목록 순서로 추측하지 않습니다.
6. 테이블/시설 상태와 일관된 시점의 공개 상태를 구성해주세요. 한 스냅샷에서 같은 테이블의 같은 좌석에 두 사용자가 있거나, 시설과 테이블을 동시에 사용하는 상태를 보내지 말아주세요.
7. 공개 착석 정보에는 `tableId`·`seatNumber`만 넣고 참가 권한·준비·배팅·비공개 게임 정보는 기존 계약에 남겨주세요. 이 필드를 받았다고 FE가 테이블 참가나 게임 관전 요청을 보내지 않습니다.

FE에서는 이 공개 정보를 **다른 사람의 표시 전용**으로 사용합니다. 내 테이블 참가 상태와 버튼 권한은 계속 `TABLE_STATE`로만 결정하므로 늦게 온 공개 스냅샷이 내 착석 승인을 취소하지 않습니다. 이전 BE처럼 필드가 없는 경우는 기존 동작을 유지합니다.

## 합동 검수 기준

- 남녀 캐릭터 모두 이동 수영에서 양팔이 앞으로 번갈아 회전하고, 정지 수영·입출수 동작은 유지됩니다.
- A가 방귀를 시작한 뒤 걷기·달리기·점프해도 A/B 화면에서 같은 `sentAt`으로 자연스럽게 끝납니다. 이동 반복으로 시작 시간이 갱신되거나 취소 이벤트가 오지 않아야 합니다.
- 손 인사 중 이동해서 취소한 후 멈추고 즉시 박수를 선택하면 새 요청이 승인됩니다. 이전 표현의 5초 대기나 취소한 요청의 늦은 응답이 새 재생을 방해하지 않아야 합니다.
- A만 앉고 B는 주변에 서 있어도 B에게 A가 실제 좌석에서 앉은 모션으로 보여야 합니다. B가 테이블에 참여·관전할 필요가 없어야 합니다.
- A가 앉은 뒤 들어온 C와 재접속한 B도 초기 상태부터 같은 모습을 봅니다. A가 일어나거나 강제 퇴장/접속 종료하면 다른 화면에도 앉은 잔상이 남지 않습니다.
- 다른 채널의 상태, 오래된 월드 버전, 같은 좌석 중복, 이전 감정표현의 취소 이벤트가 현재 표시를 덮어쓰지 않아야 합니다.

- 브라우저 회귀 검증 **12개 시나리오 통과**. 동일 밀리초 승인과 정상 재생 완료 후 쿨다운 보존을 보완한 최종 코드에서 관련 핵심 **5개 시나리오를 다시 실행해 모두 통과**했습니다.
- 환경: Windows, Edge headless, `http://127.0.0.1:5287/park`, 1920×1080·1366×768·390×844. Browser 플러그인/스킬이 제공되지 않아 저장소의 Playwright 테스트를 사용했습니다 (`Browser plugin not available`).
- 수영: 남녀 실제 rig의 30/60fps 단위 테스트에서 손의 어깨 기준 회전 방향을 검사했습니다. 브라우저에서도 남녀 rig 각각 걷기 속도/달리기 속도 수영의 양팔 회전 방향과 정지 수영 복귀를 확인했습니다.
- 감정표현: 키보드 이동 중 방귀 유지, 손 인사 이동 취소 → 멈춤 → 즉시 박수 선택, 서버 취소의 이벤트 ID 일치 여부, 이전 승인·거절이 새 요청을 덮어쓰지 않는 동작을 확인했습니다. 같은 밀리초에 취소와 다음 승인이 와도 새 표현을 허용하고, 이미 정상 종료한 표현의 쿨다운은 유지하는 테스트도 포함합니다.
- 착석: 두 브라우저 화면에서 A가 착석한 뒤 B에게 **제안한 공개 필드를 보내는 fixture**로 검증했습니다. B는 참가·관전 요청 없이 A의 굽힌 허벅지/무릎 모션을 표시했고, `tableSeat:null` 수신 후 서 있는 자세로 돌아왔습니다. 실제 BE가 이 필드를 방송하는지 검증한 것은 아닙니다.

## BE 담당자에게 그대로 전달할 글

> 수영 팔 방향은 독립적인 FE 수정으로 별도 MR에서 처리합니다. 이동 중 방귀 유지, 감정표현 취소 후 즉시 다른 표현 사용, 주변 사용자 착석 표시는 FE 시안과 수신 처리를 별도 브랜치에 보존하고 BE 연동 대기 중입니다. 이 세 항목은 BE 구현 및 실제 두 계정 검수 전 dev 머지를 보류합니다. BE 코드는 변경하지 않았습니다.
>
> BE에서는 세 가지 작업을 부탁드립니다. 첫째, `FART`는 이동 요청과 물리 갱신의 `MOVEMENT` 취소 대상에서 제외해주세요. 둘째, 취소된 감정표현의 긴 쿨다운이 다음 표현을 막지 않도록 `WorldEmoteService`의 재사용 제한 정책을 변경해주세요. 기존 1초 최소 전송 간격도 즉시 사용을 막을 수 있어, 유효한 취소 후 다음 표현은 허용하되 과다 요청은 별도로 제한하는 정책을 확인 부탁드립니다.
>
> 셋째, 지금은 테이블 참가자·관전자만 좌석 상세 상태를 받아 주변 사람에게 착석이 보이지 않습니다. 같은 채널 전체의 `WORLD_STATE.avatars[]`에 `tableSeat:{tableId,seatNumber}` 또는 `null`을 제공해주세요. 좌석 번호는 기존과 같은 1-based이며, 착석·퇴장 때 좌표가 안 바뀌어도 월드 버전/방송이 갱신되고 입장·재접속 초기 스냅샷에도 포함되어야 합니다. FE는 이 제안 필드의 수신·검증·표시를 준비했습니다. 필드명과 제공 방식을 확정해주시고, 적용 후 두 계정으로 함께 검수 부탁드립니다.
