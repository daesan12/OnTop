## 결론

**개발 서버 이동을 ‘끊김 없이 부드러움’으로 판정할 수 없다. 실측 당시 첫 실제 이동에서 프레임·입력 공백과 승인 이동 중지가 재현됐다.** 이후 걷기·달리기와 반복 구간은 안정적이었다. 이 결과는 실제 인증 계정과 개발 BE를 사용한 기록이며 로컬 fixture 결과가 아니다.

15:32 공개 파일과 16:05~16:06 종료 재확인 파일에는 모두 `inFlight`로 응답을 기다리고 완료 뒤 60ms를 더 기다리는 이전 전송 코드가 있다. 그사이에 entry 파일이 `index-DuQZ4z2w.js`에서 `index-D4z8I1y3.js`로 바뀌었다. 종료 시점 새 entry에도 응답 대기와 이전 월드 시각 코드가 남아 있다. 이번 FE 수정 브랜치가 배포됐다는 근거는 없다. 배포 Git 커밋은 확인하지 못했다.

실측 harness가 그 창에 로드된 entry hash를 별도 저장하지 않아 6회 실측을 두 hash 중 하나로 엄밀하게 귀속할 수는 없다. 실측은 15:44~15:46 KST의 당시 화면에 대한 결과이며, 종료 때 확인한 새 배포본의 첫 이동을 다시 검수한 결과로 표기하지 않는다. 다음 재검수에는 로드된 script URL/hash도 함께 고정해야 한다.

새로 제안했던 수신 시각 기반 좌표 이력 보간도 실측 재생에서 속도 변동을 키웠다. 따라서 **최종 FE는 이 변경을 제외하고 프로토타입의 120ms 끝점 보간을 유지**한다. 기존 전송 대기 제거 수정은 유지한다. 최종 로컬 버전의 실제 배포 후 이동 검수는 아직 아니다.

## FE에서 처리할 부분

### 1. 응답 대기 제거 — 로컬 수정·검증 완료, 미배포

`frontend-motion-clock/frontend/src/network/movementInput.ts`에서 응답과 분리해 로컬 60ms 간격으로 최신 의도를 보낸다. 정지·점프 1회·재접속/채널/활동 경계 처리를 보존한다. 지연 뒤 과거 입력을 몰아 재전송하지 않는다.

이 수정은 응답 대기에 의한 추가 간격을 줄인다. **340ms 동안 메인 스레드가 막히면 같은 스레드의 타이머도 실행되지 않으므로, 이 수정만으로 첫 이동 멈춤이 모두 해결되지는 않는다.**

### 2. 좌표 이력 보간 제안 철회 — 로컬 반영 완료

실제 스트림에는 입력 확인과 방송이 1ms 미만 간격으로 서로 다른 좌표를 전달하는 경우가 있다. 수신 간격을 그대로 시간축으로 사용한 제안은 이 간격을 과도한 순간 속도로 바꿨다.

같은 실서버 기록을 60fps 렌더 시각에 재생한 비교(새 물리/예측 없음):

| 구간 | 기존 보간 속도 변동계수 | 제외한 이력 보간 변동계수 | 기존 / 제외안 최대 표시 속도(m/s) |
| --- | ---: | ---: | ---: |
| 우 걷기 | 0.080 | 0.322 | 7.65 / 14.92 |
| 우 달리기 | 0.118 | 0.413 | 11.51 / 24.68 |
| 반복 우 걷기 | 0.080 | 0.315 | 6.97 / 15.10 |

숫자는 화면 표시 좌표를 60fps로 재생한 속도이며 실제 서버 이동 속도를 변경/측정한 값이 아니다. 최종 FE는 기존 프로토타입 보간을 유지해 위 역효과를 배제한다. 비식별 실측 좌표를 회귀 fixture로 추가했고, 동일 기록에서 9m/s 달리기 표시 속도가 24m/s대로 튀는 변경을 차단한다.

이 재생은 **이미 받은 스트림에 대한 표시 알고리즘 비교**다. 전송 대기 제거 후의 실제 입력/서버 스트림을 대신하는 A/B 검수가 아니다.

### 3. 첫 이동의 긴 프레임 작업 — FE 미해결, 프로파일링 필요

- 후속 담당은 FE다. 이동 시작/새 구역 노출/낮밤 전환에서 CPU trace와 WebGL program·texture upload 기록을 함께 수집해 Long Task의 호출 경로를 특정해야 한다.
- 초기 SceneReady에 `compileAsync`가 있지만, 뒤늦게 나타나는 재질/조명/LOD/텍스처의 최초 처리까지 보장하지는 않는다. 이 항목들은 조사 후보이며 이번 기록으로 원인을 확정하지 않았다.
- 원인 확인 뒤 해당 자원의 사전 준비나 작업 분산을 적용하고, 같은 경로의 첫 이동을 반복 검수한다. 이번에는 근거 없이 조명·모델·서버 속도나 전역 하드웨어 가속 설정을 바꾸지 않았다.

## BE 요청사항

1. **2026-10-26 15:44:43~15:44:48 KST**, 개발 채널/검수 회원 `test`의 입력 수락 시각·seq·입력 만료 시각·이동 정지 사유·물리 step 소요·broadcast 생성/송신 시각을 대조해달라. FE 측 3회 입력 공백과 `moving=false`가 입력 만료인지 확인이 필요하다. 계정의 내부 ID는 담당자가 기존 계정으로 확인한다.
2. 실제 배포 설정이 최소 입력 간격 50ms, 입력 만료 250ms, 물리 30Hz, 변화 시 약 100ms 방송인지 공유해달라. 이번 측정에서 rate limit 오류는 없었으므로 **MOVE_TOO_FREQUENT 발생을 신규 사실로 주장하지 않는다.**
3. WORLD_STATE에 **좌표 생성 시각 또는 물리 tick 식별자**를 제공할 수 있는지 명세를 협의해달라. 수락 순번 `lastInputSeq`와 계산 완료 시각은 구분해야 한다. 입력 확인/방송/프로필 갱신이 같은 물리 좌표를 담을 때도 원래 좌표 생성 시점을 구별할 수 있어야 한다.
4. 최대 확인 RTT 299.2ms가 순수 BE 지연이라는 근거는 없다. FE Long Task도 관측됐으므로 서버 수락→응답 생성 시간과 물리 thread 대기 시간을 별도로 확인해달라. 제한/만료 시간을 무조건 확대하는 요청은 아니다.
5. 별도 기존 요청인 **KST(`Asia/Seoul`) 공통 월드 시각·한국 자정 epoch·낮밤 30분 주기와 재동기화 계약**은 유지한다. 16:05~16:06 KST에 확인한 공개 FE에는 접속 시점의 60% 위상에서 시작하는 이전 코드가 있었다. 타임스탬프는 Unix ms를 사용하고 9시간을 중복 가산하지 않는다.
