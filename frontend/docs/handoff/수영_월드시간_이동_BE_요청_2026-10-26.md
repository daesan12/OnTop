## 1. 공통 낮·밤 시각 계약 요청 — 필요

현재 Spring `WorldState(channelId, version, avatars, mapVersion)`와 FE 프로토콜에는 월드 시간 정보가 없다. 원본은 월드 스냅샷의 서버 현재 시각·공통 epoch·주기를 읽고 측정된 pong RTT로 보정한다. 이관 FE는 사용자마다 접속 시점부터 낮·밤을 시작해 차이가 났다.

FE는 한국 시간 `Asia/Seoul`의 공통 기준 시각으로 위상을 계산하도록 변경했다. 접속 시점 차이는 없어지지만 기기 시계가 틀린 사용자는 여전히 차이가 날 수 있다.

BE 회신 요청:

- 모든 사용자에게 적용할 **서버 현재 시각(ms), 한국 시간 기준 epoch(ms), 낮밤 한 주기(ms)**의 제공 위치와 의미를 확정해달라. 시간대는 `Asia/Seoul`이다. `serverTime/worldEpochMs/dayDurationMs`는 원본 참조 이름이며 확정된 Spring 필드명이 아니다.
- FE 기준값은 **`epoch=2026-01-01T00:00:00+09:00`(KST), Unix ms `1767193200000`, 주기 30분**으로 반영했다. BE도 이 기준을 공유하고 설정 제공 경로를 확정해달라. 서버 재시작·채널 변경·멀티 인스턴스에도 동일 epoch/주기를 유지해달라.
- 타임스탬프 전송·경과 시간 계산은 Unix ms를 사용한다. 위 기준 시각과 `2025-12-31T15:00:00Z`는 동일한 순간이다. 서버 현재 시각이나 `Date.now()`에 9시간을 더하지 말고, 사람이 읽는 시각 표기에는 KST/`+09:00`를 명시해달라.
- 게임 낮밤 24시간은 실제 30분 주기로 유지한다. 한국의 실제 시각과 게임 시각을 1:1로 대응시키는 24시간 주기 변경은 이번 요청에 포함하지 않는다. 기존 epoch와의 9시간 차이는 30분 주기의 18배이므로 기준 시간대 명시만으로 시각 연출이 9시간 이동하지 않는다.
- 입장·재접속 직후 초기 동기화와 긴 탭 숨김 후 재보정에 사용할 요청/응답을 합의해달라. RTT 측정용 왕복과 응답 생성 시각의 의미가 필요하다.
- 기존 WebSocket 제어 Ping/Pong은 브라우저 JS에서 시각을 읽을 수 없다. 현재 `docs/websocket-heartbeat.md` 계약을 유지하고 임의 JSON heartbeat를 FE가 추가하지 않았다. 시계 동기화는 합의된 별도 경로/기존 응답 확장으로 명세를 요청한다.
- 수용 기준: 입장 시점·기기 시계/시간대·재접속이 다른 두 사용자도 같은 서버 시각에 한국 시간 기준의 같은 낮밤 위상을 표시. 공동 검수 시 허용 오차를 합의한다.

## 2. 이동 좌표의 생성 시각·운영 지연 확인 요청

확인한 문서/소스: `docs/world-websocket-api.md` 이동 절, `WorldChannelRegistry.java`, `WorldPhysics.java`.

- 현재 문서: 물리 30Hz, 변화 시 약 100ms 전체 방송, 입력 최소 50ms, 250ms 무입력 시 수평 이동 정지.
- 입력 응답 WORLD_STATE 좌표는 마지막 계산 좌표일 수 있다. lastInputSeq는 **수락 번호**이며 물리 계산 완료 번호가 아니다.
- FE에서 매 입력 응답 뒤 60ms를 추가 대기하던 구조를 제거했다. 예를 들어 RTT 200ms이면 기존 간격은 약 260ms라 입력 만료에 걸릴 수 있었다. 이제 응답과 독립적으로 기존 60ms 간격을 지킨다. 정지·점프 취소·연결 경계와 기존 payload를 보존했다.
- 표시 좌표는 실측 재생에서 더 안정적이었던 프로토타입의 120ms 끝점 보간을 유지한다. 수신 시각 기반 이력 보간 제안은 제외했다. 서버 좌표를 넘어 예측하지 않으며 동일 좌표 응답은 보간을 다시 시작하지 않는다.

BE 회신/확인 요청:

1. 개발 서버에 위 설정이 실제 적용됐는지, 설정이 다르다면 실제 값을 공유해달라.
2. **좌표 생성 시각 또는 물리 tick ID**를 스냅샷에 넣을 수 있는지 협의해달라. 입력 확인·프로필/시설 갱신에 같은 물리 좌표가 실릴 때도 원래 생성 시점을 구별할 수 있어야 한다. 필드명·갱신 규칙은 BE 계약으로 확정하고 FE를 연결하겠다.
3. 동일 채널 두 사용자 걷기/달리기/수영에서 RTT·jitter, 입력 도착 간격과 `MOVE_TOO_FREQUENT`, 250ms 만료 발생, 물리 thread 스텝 지연과 방송 간격을 측정해달라. 테스트할 때 부하와 서버 인스턴스도 함께 기록해달라.
4. FE는 60ms 간격을 지키지만 네트워크에서 묶여 도착하면 50ms 최소 간격 거절은 남을 수 있다. 지연된 패킷의 rate limit 처리와 최신 입력 채택 방식을 확인해달라. 입력 만료나 제한 값을 근거 없이 늘리거나 서버 물리를 FE로 대체하는 요청은 아니다.

## 3. 수영은 FE 모션 수정 완료, 서버 물리는 공동 검수

- 원본의 수영 중 이동 phase와 무릎·팔꿈치 움직임이 이관 과정에서 빠진 것을 복원했다. 남녀 실제 rig의 30/60fps 수영 주기를 테스트했다.
- 서버의 swimming·moving·running, 수면 높이·부력·수영 속도·충돌은 변경하지 않았다. 이 항목에 신규 BE 모션 개발을 요청하지 않는다.
- 실제 서버에서 일반/달리기 수영, 정지 수영, 입수/출수, 징검다리·점프 전환을 확인해달라. 승인 상태가 반복 토글되거나 위치 자체가 튀면 해당 시간의 WORLD_STATE와 물리 로그를 공유해달라.

## 검증 경계

FE 단위/브라우저 fixture, 기존 배포본 실측, 최종 로컬 FE 배포 후 검증을 구분한다. 기존 배포본에서 한 계정의 실제 이동은 측정했으나 두 계정을 제어한 상호 검수·네트워크 부하·Minie/Rapier 물리 동등성·최종 FE 실배포 A/B는 미검증이다. FE 첫 이동 Long Task 원인과 BE 입력 만료 사유는 후속 확인이 필요하다. 자세한 FE 원인 비교와 검증은 `../MOTION_CLOCK_FE_REVIEW_2026-10-26.md`와 최신 실측 정리에 있다.
