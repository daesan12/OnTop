## 범위와 현재 상태

- FE에서 캐릭터·텍스처 요청을 인증 확인과 함께 시작하고, 채널·배치·프로필 조회와 WebSocket 접속권 발급을 병렬화했다. 설정·프로필 검증 후 소켓을 열고, 기다리는 동안 접속권 유효기간이 임박하면 다시 발급받는다.
- 붕어빵 종료 후 800ms 조작 잠금을 제거했다. 카메라 복귀만 240ms로 실행한다. 진행 중인 판 포기는 기존처럼 서버 승인 후 종료하며, 실패 시 게임 화면과 재시도를 유지한다.
- BE 코드, 충돌 맵, DB, 보상 규칙은 수정하지 않았다. 아래 내용은 BE 담당자가 검증·수정해야 한다.

## 1. 점프맵 낙하 중 이전 발판으로 돌아가는 현상 — 우선 확인

### 사용자 증상

점프맵에서 발판을 벗어나 떨어질 때 이전 위치로 갑자기 되돌아간다.

### 코드상 유력 원인

`backend/src/main/java/com/ssafy/ontop/world/movement/WorldPhysics.java`의 `space.update(DT, 0)` 직후 복구 분기를 확인해 달라.

```java
if (!Vector3f.isValidVector(position)
    || position.y < scene.groundHeight(position.x, position.z)
        + number("halfHeight") + number("radius") - .35) {
    a.body.warp(a.lastSafe);
    // ... 속도와 입력 정지
}
// ...
if (a.body.onGround()) {
    a.lastSafe.set(x, position.y, z);
}
```

높은 발판에 서면 `lastSafe`가 그 발판 위치로 갱신된다. 이후 낙하 중 지형 관통 판정이 발생하면 해당 위치로 워프한다. 코드는 이 동작을 설명하지만 **실서비스 재현 시 서버 좌표·복구 로그로 이 분기가 실제 실행됐는지 확인해야 한다.** FE 보간은 서버 좌표 사이만 보간하며 이전 발판을 저장하거나 그곳으로 이동시키지 않는다.

맵·코스 연동은 별도로 확인해야 한다. 기준 브랜치에는 기존 VR 발판이 있고, 별도 작업의 `c1-fe-draft1` 코스는 승인되지 않은 초안이다. 이번 요청은 초안 코스의 서버 배포를 요구하지 않는다. 재현한 서버의 맵 버전·코스와 좌표를 기준으로 진단해 달라.

### 요청하는 진단 정보

- 재현 환경, 맵 버전, 발판·코스 식별자, 낙하 전후 서버 tick/좌표.
- 복구 직전 좌표, 지형 높이, `lastSafe`, 접지·수영 상태, 수직 속도, 복구 사유.
- 실제 관통인지, 지형 높이와 충돌 메시의 불일치인지, 별도 점프맵 복귀 규칙인지 구분.
- 30Hz와 최대 낙하 속도에서 지면·얇은 발판 착지가 안정적인지 확인.

### 수정 기준

1. 정상 낙하는 중력으로 이어지고, 실제 지면·발판·물의 충돌 및 수영 규칙으로 처리되어야 한다.
2. 유효한 맵 내부 좌표의 지면 관통 복구와 NaN/무한대·월드 이탈 복구를 분리해 달라. 관통 복구 때문에 높은 이전 발판으로 돌아가면 안 된다.
3. 관통 시 안전한 착지 지점을 복원할 필요가 있다면 현재 수평 좌표 주변의 실제 충돌체와 캡슐 공간을 검사해 달라. 지형 높이만 사용해 구조물 내부·막힌 공간·물 위에 임의 배치하지 않는다.
4. 잘못된 좌표·월드 이탈·명시적 끼임 복구는 안전한 위치 복구를 유지한다. 보호 분기를 통째로 제거하거나 수치만 크게 완화하지 않는다.
5. 점프맵 실패 판정·낙하/복귀 유예·보상 정산이 있다면 해당 계약과 일치시켜 달라. 정상 낙하를 FE에서 숨기거나 보상 판정을 FE로 옮기지 않는다.

### 공동 검수

- 낮은 발판과 높은 발판에서 각각 걷기 이탈·달리기 이탈·점프 실패 후 낙하.
- 수직 낙하·대각선 낙하·높은 곳에서 낮은 발판 착지·가장자리 접촉.
- 지면 착지·물 진입·구조물 옆 낙하에서 이전 높은 발판으로 되돌아가지 않음.
- 의도적으로 지면 아래에 놓인 유효 좌표와 비정상 좌표 복구를 각각 회귀 검사.
- 월드 경계 보호, 끼임 복구, 수영, 좌석/시설 이동, 따라가기, 점프맵 보상·종료 중복 방지 유지.
- 실제 서버가 보낸 좌표와 FE 화면을 함께 기록해 복구 주체 확인.

## 2. 로그인 후 공원 진입 지연 — 서버 구간 실측 요청

로컬 HTTP/WS fixture에서 배포용 FE 빌드를 검사했다. 실제 OAuth, 개발·운영 서버, DB·네트워크 지연은 포함되지 않는다. 사용자에게 보고된 약 5초를 모두 서버 지연으로 판정한 것은 아니다. 로컬에서도 정적 3D 형상 생성과 GPU 첫 준비 비용이 남아 있다.

아래 구간의 서버 처리 시간과 네트워크 시간을 분리해 공유해 달라.

| 구간 | 확인 사항 |
|---|---|
| OAuth callback 교환 / access refresh | 인증 처리, 외부 공급자·DB 지연 |
| `GET /api/v1/channels` | 채널 목록 조회·직렬화 비용 |
| `GET /api/v1/users/me` | 프로필·의상 등 추가 조회 비용 |
| `POST /api/v1/auth/websocket-ticket` | 접속권 발급·인증 처리, 응답의 `expiresIn` 계약 |
| WebSocket 연결 → `CONNECTED` | handshake·사용자 초기화 시간 |
| `CHANNEL_JOIN` → 첫 `WORLD_STATE` | 물리 월드 초기화·충돌 맵 로드·첫 입장과 기존 채널 재입장 차이 |

첫 사용자와 이미 생성된 채널의 후속 사용자를 나눠 측정하고, 물리 월드 생성이 병목이면 생명주기와 메모리 비용을 검토해 서버 쪽 재사용/준비 방식을 결정해 달라. 인증·맵 일치·권한 검증은 유지한다.

## 전달 시 확인할 점

FE 수정은 FE 머지·배포 후 반영된다. 낙하 위치가 서버에서 되돌아가는 문제는 BE 수정·배포와 실제 서버 검수까지 필요하다. 이 문서 작성은 BE 수정 완료나 요청 메시지 전송을 의미하지 않는다.
