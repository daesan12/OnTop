# BE 요청: 브라우저 조작을 전제로 한 게임 무결성 검증

작성일: 2026-10-28 · 상태: BE 확인·보완 요청, 이번 작업에서 BE 코드/DB/인프라는 수정하지 않음

최신 FE 통합 및 요청 정리: 2026-10-29

## 그대로 전달할 요청 글

안녕하세요. FE에서 운영 게임 화면에 F11/F12, 개발자 도구·소스 보기·저장·인쇄·새로고침 단축키의 기본 동작 취소를 시도하고, 해당 입력 및 창 이탈 시 이동·마우스 고정·이모트 휠·주사위 컵의 일시적 조작을 정리했습니다. 로그인/관리자 화면과 로컬 디버깅은 유지했습니다.

다만 개발자 도구는 브라우저 메뉴·사전 실행·원격 연결로 접근할 수 있고, FE 코드와 전송 데이터는 사용자가 수정할 수 있습니다. 따라서 단축키 차단을 보안 근거로 사용하지 않고, 아래 항목이 기존 HTTP/WS 경로에서 서버 기준으로 보장되는지 확인 부탁드립니다. 이미 구현된 항목은 중복 개발하지 않고 담당 코드와 테스트 증거를 공유해 주시면 됩니다. 미충족 항목만 보완하고, 계약 변경이 필요하면 요청/응답·오류 코드·버전·복구 정책을 먼저 전달해 주세요. FE는 합의된 계약에 맞춰 후속 반영하겠습니다.

특히 타인/관전자 행동 거부, 비공개 손패·눈의 수신자별 분리, 서버 차례·시간 판정, 미니게임 조리 기록의 서버 재검산, 중복 지급 방지, WS 재전송/다중 탭 검증을 우선 부탁드립니다. 개발자 도구 탐지·F11 사용·탭 이탈만으로 제재하는 기능은 요청하지 않습니다.

## 담당 개발자가 진행할 순서

1. **기존 구현 확인:** 아래 표의 항목별로 서버 검증 코드와 테스트가 있는지 먼저 확인해 주세요. 이미 보장되는 기능은 새로 만들지 않고 근거를 회신해 주시면 됩니다.
2. **권한과 비공개 정보 우선 보완:** 예를 들어 관전자가 플레이어의 행동 요청을 직접 보내면 서버가 거절해야 하고, 다른 플레이어의 손패/비밀 눈은 관전자 응답 JSON에 없어야 합니다.
3. **시간·점수·재화 검증 보완:** 브라우저에서 남은 시간을 늘리거나 `clientScore`를 큰 값으로 바꿔 보내도 서버 결과에는 영향을 주지 않아야 합니다. 같은 판의 완료 요청을 두 탭에서 동시에 보내도 보상은 한 번만 지급되어야 합니다.
4. **부정 요청 테스트 추가:** 정상 요청 하나와 변조/중복/차례 밖 요청을 짝으로 검증하고, 실패 응답뿐 아니라 실제 게임 상태·지갑 원장이 바뀌지 않았는지도 확인해 주세요.
5. **FE 연동이 필요한 차이만 전달:** 응답 필드나 오류 코드가 달라져야 한다면 변경 전후 JSON 예시와 배포 순서를 알려 주세요. 이번 FE는 기존 API를 유지하므로 BE 작업 완료 전에 신규 API를 호출하지 않습니다.

산출물은 `항목별 충족 여부 + 보완 코드/테스트 링크 + API 변경 유무`입니다. 단축키 차단의 배포와 서버 무결성 검증의 완료는 별도로 판단합니다.

## 현재 FE 계약에서 특히 확인할 지점

- 공원 입력은 기존 `parkRuntime.move/stopMovement`와 WS 이동 계약을 유지한다. 입력 정리는 브라우저가 협조할 때의 편의 기능이며 변조 클라이언트의 정지 통지를 신뢰하지 않는다.
- 수동 기권은 기존 `GAME_FORFEIT { gameId, actionId }`를 유지한다. 탭 이탈·F11/F12 사용을 기권으로 바꾸지 않는다.
- `src/features/bungeoppang/service.ts`, `serviceV4.ts`, `serviceV5.ts`의 완료/배달/체크포인트 및 멱등 계약을 기준으로 확인한다. 버전별 제공 기능이 달라 새 엔드포인트를 임의로 가정하지 않는다.
- v4 완료 요청은 `clientScore`, 행동 기록과 prefix hash를 전달한다. 해시를 클라이언트도 계산할 수 있으므로 해시 일치만으로 기록의 정당성이 증명되지 않는다. 서버가 발급/승인한 체크포인트와 시간·상태 전이 검증이 함께 필요하다.
- 종료 시 모아서 받는 기록의 재생 검증은 규칙 일관성을 확인할 수 있지만 실제 사람이 그 시각에 입력했다는 증거는 아니다. 봇/합성된 합법 기록까지 막아야 한다면 서버 권한의 진행 승인·수신 시각·빈도 정책과 허용 UX를 별도로 합의해야 한다.
- API가 성공했다는 사실만으로 보안 검증 완료로 기록하지 않는다. 정상/비정상 요청 쌍과 지급/차감 전후 상태를 함께 확인한다.

## 회신 요청 형식

각 항목에 `충족 / 보완 필요 / 합의 필요`, 담당자, 관련 서버 코드/테스트, 재현 결과를 부탁드립니다. 계약 변경이 필요한 경우 기존/변경 후 요청·응답 예시, 오류 코드, 멱등/재접속 정책 및 배포 순서를 함께 공유해 주세요. 이번 FE 작업은 새 보안 텔레메트리 API·개발자 도구 탐지 API·자동 제재를 추가하지 않았습니다.

## 공동 완료 기준

1. 개발자 도구를 미리 열고 FE 버튼·Zustand 상태·시간·요청 payload를 바꿔도 서버 권한과 재화/게임 상태를 임의 변경할 수 없다.
2. 비공개 정보는 권한 없는 클라이언트에 도착하지 않는다.
3. 네트워크 실패·중복 전송·다중 탭·동시 완료에서도 정산은 한 번이고 서버 원장이 일치한다.
4. 정상 사용자의 전체화면·확대/축소·IME·탭 이탈·접근성 조작을 부정행위로 판정하지 않는다.
