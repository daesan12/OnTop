# 관리자 이벤트 관리 화면

`/admin/events`는 KST 월요일 시작일을 기준으로 응모권 추첨, 붕어빵·점프맵 1위, 엽전 보유량 행사를 조회합니다. 미니게임상은 `2026-11-02`, 엽전상은 `2026-11-09` 회차만 현재 서버 설정에서 지원합니다. 응모권은 `2026-11-02` 이후 주차를 조회할 수 있습니다.

- `ADMIN_READ_IDS`: 회차별 마감·확정·발표 상태와 확정 결과, 당첨자 목록 및 연락처 제출 상태 조회
- `ADMIN_OPERATION_IDS`: 마감 후 결과 확정 요청. 응모권은 사전 추첨 결과를 검토한 뒤 해당 시도 ID로 확정해야 합니다.
- `ADMIN_CONTACT_IDS`: 당첨자별 연락처 원문을 명시적으로 열람. 서버가 열람 감사 기록을 남깁니다. 화면에서는 30초 후 원문을 숨기며, 회차·필터 변경이나 페이지 이탈 시에도 지웁니다.

후보 수와 GM 제외 건수는 서버가 저장한 집계입니다. 응모권은 사전 추첨 후 검토 화면에서 표시하며, 다른 부문은 확정 후 표시합니다. `candidateCount`는 GM을 제외하기 전의 총량이며, 화면은 제외 후 총량도 함께 보여줍니다. 응모권 추첨 결과 API에도 저장된 성공 이력의 `candidateCount`와 `excludedGmCount`를 추가했습니다. 응모권의 수량 단위는 **회원 수가 아닌 응모권 수**입니다.

확정 요청이 네트워크에서 끊겨 결과를 받지 못하면 화면이 해당 회차를 다시 조회합니다. 서버가 이미 확정했다면 기존 결과를 표시하고, 재추첨 버튼은 사라집니다. 최종 확정 여부가 불명확하면 운영자가 결과를 새로고침한 뒤 판단합니다. 확정 API의 멱등성과 동시 실행 방지는 서버에서 보장합니다.

응모권 관리자 화면은 [raffle-review-api.md](raffle-review-api.md)의 사전 추첨 → 검토 → 선택적 재추첨 → 최종 확정 흐름을 사용합니다. 검토 결과는 서버에 저장된 현재 시도를 조회하며 새로고침 후에도 복구됩니다. 재추첨에는 1~500자의 사유가 필요하고, 확정 직전 현재 시도 ID를 다시 확인합니다. 다른 관리자가 시도를 바꿨으면 이전 화면의 확정은 중단하고 최신 시도를 보여줍니다. 서버도 오래된 ID의 요청을 거절합니다. 응답을 받지 못한 요청은 자동 재시도하지 않고 저장 상태를 다시 조회합니다. 확정된 회차에는 재추첨·확정 버튼을 표시하지 않습니다.

당첨자 목록에는 연락처 마스킹 값과 제출 상태만 기본 노출합니다. 원문은 별도 권한이 있고 `SUBMITTED`인 당첨자의 버튼을 누를 때에만 API에 요청합니다. 브라우저 새로고침이나 필터 변경 후 원문을 유지하지 않습니다.

## 당첨자 닉네임과 경품 지급 기록

관리자 당첨자 목록은 `winnerId`, `userId`와 현재 닉네임을 함께 반환합니다. 응모권 사전 추첨·확정 결과와 미니게임·자산상 결과에도 닉네임을 반환합니다. 닉네임은 표시용이며, 지급 대상 식별은 변경되지 않는 내부 ID로 합니다.

경품을 실제 전달한 뒤 운영 권한(`ADMIN_OPERATION_IDS`)이 있는 관리자는 `PUT /api/v1/admin/events/winners/{winnerId}/delivery`에 `{ "expectedUserId": 31 }`을 보냅니다. 서버는 당첨 건의 회원 ID와 확정 여부를 확인하고 `event_prize_deliveries`에 실행자와 시각을 기록합니다. 같은 당첨 건의 재요청은 기존 기록을 반환하며 `alreadyDelivered: true`로 구분됩니다. 한 회원에게 여러 상품이 있으면 각 `winnerId`를 별도로 지급 처리합니다. 이미 확정된 2026-11-02 회차도 동일한 API를 사용합니다.

관리자 당첨자 목록에는 `deliveryStatus`, `deliveredByUserId`, `deliveredAt`이, 회원의 당첨 내역에는 `deliveryStatus`, `deliveredAt`이 포함됩니다. `PENDING`은 아직 수동 지급 완료 기록이 없다는 뜻입니다. 관리자 화면의 지급 버튼 연결과 당첨 알림 표시 제어는 후속 화면 작업에서 진행합니다.
