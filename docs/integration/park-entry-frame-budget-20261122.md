## 원인과 수정

실제 정적 에셋과 API/WS fixture만으로도 입장 직후 정체가 재현됐다. 이번 정체는 서버 응답을 기다리는 구간보다 클라이언트 메인 스레드의 생성·셰이더 초기화에서 확인됐다. 실제 dev 서버의 모든 지연이 없다는 판단은 아니다.

독립 Chrome의 공개 Playwright `startTracing`으로 CPU 추적을 수집했다. 추적 자체에 따른 비용이 있으므로 아래 성능 표에는 추적을 끈 별도 기록만 사용했다.

1. `DirectionSigns`가 첫 화면 이후 표지판 8개의 지오메트리·문자 텍스처를 한 번에 생성했다. CPU 추적에서 해당 생성 묶음에 약 280ms가 잡혔다. 입구 20m 안의 기존 표지판만 입구 준비 경계에 포함하고, 나머지는 기존 `FacilityOnApproach`(44m + 시설 반경)로 생성한다. 원본 factory 옵션·문구·방향·좌표를 유지한다.
2. 랭킹판, 원거리 표지판 글자, 우체통, 돌탑, 비둘기, 운동 기구의 일부 재질이 첫 draw에서 새 프로그램을 사용했다. 추적 중 개별 draw에 랭킹판 약 170ms, 표지판 약 152ms, 우체통 다른 기록에서 약 207ms가 잡혔다. 셰이더 링크 이후 첫 uniform reflection도 `WebGLUniforms`에서 메인 스레드를 막았다. 첫 이동에 필요한 재질 변형만 작은 비표시 메시로 입장 전에 컴파일·reflection한다. 특히 양면·평면 음영·인스턴스/색상 유무를 실제 재질과 맞춘다. 준비용 재질은 캔버스 종료까지 유지하여 프로그램이 조기 폐기되지 않게 하고, 종료 시 한 번만 해제한다. 준비용 메시를 실제 씬에는 부착하지 않는다.
3. `ScenicDetails`와 `Buildings`의 모듈 평가가 첫 이동 중 실행됐다. 추적에서 각각 약 203ms/394ms였다. 필수 월드·지형 로딩과 함께 선택적으로 선행 import한다. 선행 import 완료를 진입 조건으로 기다리지는 않는다. 돌탑의 원본 캐시 지오메트리도 scale별 이벤트 루프 양보 후 준비하여 나중 마운트에서 재사용한다.
4. 랭킹판은 이미 모듈에 생성된 `rankingBoardArt`가 있는데 마운트 때 같은 art를 다시 생성했다. 기존 공유 art를 재사용한다. 랭킹판·우체통·원거리 GLB 시설·점프맵은 접근할 때 준비한다. 이미 첫 준비 경계에 있는 정자·운세방·복권방·가챠·두더지·대여소·분수·운동 구역·수목·겨울 장식은 첫 화면에 유지한다. 점프맵은 56m 접근 또는 진행 중인 run으로 준비하며, 셰이더 제출은 기존 배치 기능을 사용한다. 아직 생성하지 않은 원거리 시설도 해당 거리 안에 접근하면 생성되는 것을 확인했다.

전체 원거리 씬을 한 번에 셰이더 준비하는 중간 후보는 화면 밖 프로그램 reflection까지 첫 이동에 실행하여 제외했다. 최종본은 필요한 변형만 입장 전에 준비한다. 새 `useFrame` 렌더 우선순위를 추가하지 않았다. 기존 수동 렌더 소유자와 `.75` 준비 순서를 유지한다. NPC의 원본 모델 표시·실패 재시도 정책도 유지하며 로우 폴리 대체 모델을 추가하지 않았다.

## 재측정

조건: Chrome 1440×900, DPR 1, 새 브라우저를 각 3회 실행하여 첫 진입과 새로고침을 연속 측정. HTTP 캐시는 Playwright route로 비활성화했다. GPU는 Intel Arc/ANGLE D3D11이며 소프트웨어 렌더링이 아니다. GPU 드라이버 캐시와 다른 데스크톱 작업의 CPU/GPU 부하는 통제하지 않았다. 기준 3회 후 최종본 3회 순서이며 교차 무작위 비교가 아니다.

프로덕션 `park-integration` 번들, 실제 맵/정적 에셋, 기존 API/WS fixture를 사용했다. 주민 3명의 상태를 200ms 간격으로 보내고 기존 심사위원도 포함했다. 실제 인증·DB·외부 네트워크·dev 배포 성능은 포함하지 않는다.
