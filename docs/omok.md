# 오목 실행 계약

2026-10-27 화면 후속 구현: [고정 시점·관전 참여 UX](omok-ux-plan.md), [FE 명세](../frontend/docs/OMOK_UX_FE_SPEC.md), [관전자 채팅·핑 확정 계약](websocket-api/10-game-spectator-events.md)을 함께 사용한다. 아래 렌주·착수·30초·종료·복구 규칙은 그대로 유지한다.

제품 기준은 OnTop v0.4, 시간 정책은 2026-10-21 사용자 확정이다. 2026-10-21 사용자 요청으로 자유룰에서 **렌주 금수 판정**으로 변경했다. 15×15, 흑 선공이며 흑은 정확히 5목, 백은 5개 이상 연결하면 승리한다. 흑의 삼삼·사사·장목은 금수로 거절한다. 판이 모두 차고 승자가 없으면 무승부로 판정하며 재화 처리는 하지 않는다.

## 흑 금수와 승리 판정

- 열린 3 두 개(33), 서로 다른 4 두 개(44), 6개 이상 연속(장목)을 검사한다. 같은 열린 4의 양 끝은 한 개로 세고, 같은 방향의 서로 다른 4는 각각 센다.
- 열린 3은 합법적인 다음 흑 착수로 열린 연속 4를 만들 수 있어야 한다. 판 끝·백돌·장목/44/33 금수 때문에 확장 불가능한 가짜 3은 제외하며 33 확장은 재귀 검사한다.
- [RIF 정의·9.2·9.3](https://gomoku.renju.net/rifrules/) 기준으로 같은 수에서 정확한 5목을 완성하면 금수보다 승리를 우선한다. 백은 금수 제한이 없다.
- 온라인 입력 정책: 금수는 `GAME_ACTION_FORBIDDEN_MOVE`로 거절한다. 판·수순·버전·마지막 수·차례·기존 turnDeadline을 바꾸거나 패배 처리하지 않는다. 흑은 남은 시간 안에 다른 위치에 착수한다. 판정 중 가상 돌도 원복한다.
- 적용 범위는 금수/승리 판정이며 대회용 오프닝 교환·첫 수 중앙 강제·패스는 도입하지 않는다. 기존 흑백 배정과 30초 정책은 유지한다.

## 금수 사전 표시와 판 확대

- 공개 상태에 `forbiddenMoves: [{"x":7,"y":7,"kind":"33"}]`를 전달한다. kind는 삼삼 `33`, 사사 `44`, 장목 `6`이다. 흑의 빈칸 후보만 기존 서버 RenjuRules로 검사하며 착수·무르기 때 캐시를 무효화한다. 조회·타이머·연결 수마다 같은 판을 다시 계산하지 않는다.
- 흑 차례의 집중 화면에서 금수 위치에 빨간 원과 `33·44·6`을 표시하고, 흑의 클릭 요청을 차단한다. 백은 이 제한을 받지 않는다. 프론트 표시와 별도로 서버의 최종 착수 검증은 유지한다. 이전 x/y 전용 응답은 ×로 표시한다.
- 구서버의 필드 생략은 허용한다. 이때 사전 표시는 없으며 서버가 금수를 거절하면 구체적인 렌주 안내를 표시한다. 새 API·DB 스키마·시간 정책 변경은 없다.
- 넓은 화면(1120px 이상)은 내 돌·상대·남은 초와 줄어드는 착수 막대를 왼쪽 사이드에, 요청·행동·관전자 수는 오른쪽 사이드에 배치해 판의 세로 공간을 확보한다. 실제 채팅·요청 카드·연결 오류 경계를 측정하며 양쪽 좌석·관전자 시점을 함께 처리한다. 작은 화면은 상하 배치와 접는 채팅창을 사용한다.

## 시간과 종료

- 한 수 30초, 총시간 제한 없음. 서버가 정한 `turnDeadline`에 도달한 입력부터 거절하고 해당 차례 사용자가 시간패한다. 매 착수 성공 후 상대의 새 30초가 시작된다.
- 재접속은 기존 판·버전·턴 마감을 그대로 읽는다. 끊김·조회·재연결로 턴 시간을 멈추거나 늘리지 않는다. 재접속 유예가 남아 있어도 턴 마감이 먼저면 경기 종료다.
- 스케줄러가 약 200ms마다 검사한다. 늦게 검사해도 `endedAt`은 원래 마감 시각이다. 착수도 같은 경기 잠금 안에서 서버 시각을 검사하여 스케줄러 지연으로 마감 후 착수할 수 없다.
- 종료 사유는 `FIVE_IN_ROW`, `BOARD_FULL`, `TURN_TIMEOUT`, `RECONNECT_EXPIRED`다. 종료 후 새 착수를 거절하며 이미 반영한 actionId의 같은 요청 재확인은 기존 결과를 반환한다.

## 기존 WebSocket으로 착수

새 연결/URL은 만들지 않는다. 기존 인증된 `/ws/tables`와 `GAME_ACTION_SEND`를 사용한다.

```json
{
  "requestId": "move-1",
  "type": "GAME_ACTION_SEND",
  "payload": {
    "gameId": "실제-경기-ID",
    "actionId": "착수별-새로운-ID",
    "expectedVersion": 0,
    "input": { "x": 7, "y": 7 }
  }
}
```

`x`는 열, `y`는 행이며 각각 0~14 정수다. 3D 월드의 x/y/z와 다른 **오목판 좌표**다. 착수 input은 x/y만 허용한다. 무르기는 아래 별도 input을 사용한다. 돌 색·userId·승패·시각을 클라이언트가 지정하지 않는다. 서버는 참가자·차례·버전·빈칸·마감 시각을 원자적으로 검사한다. 오류는 기존 `GAME_ACTION_*`를 사용한다.

같은 사용자/경기/actionId와 같은 expectedVersion·input은 중복 착수하지 않고 기존 `GAME_ACTION_RESULT`를 반환한다. 내용이 다르면 `GAME_ACTION_ACTION_ID_CONFLICT`다. 새 행동은 새 actionId를 사용한다. 재조회가 아니라 새 착수라면 최신 GAME_STATE.version을 사용한다.

## 상대 동의 무르기 (2026-11-03 사용자 확정)

로컬 구현·검증 단계이며 배포·실제 계정 공동 검수는 별도다. 내 차례에 착수가 두 수 이상 쌓였을 때만 요청한다.
상대가 동의하면 **내 직전 돌과 상대 응수 두 돌**을 제거하고 내 차례를 유지한다. 횟수 제한은 없으며,
흑은 두 돌만 남은 상태에서 빈 판까지, 백은 흑 첫 돌을 남기는 상태까지 반복할 수 있다. 상대 동의 없이 제거하지 않는다.

기존 `GAME_ACTION_SEND.payload.input`에 다음 형식을 사용한다. 매 행동의 actionId는 새 값이고 expectedVersion은 최신 상태다.

```json
{"kind":"undoRequest"}
```

```json
{"kind":"undoRespond","requestId":"요청자의-actionId","accept":true}
```

`accept:false`는 거절이다. 응답은 요청 상대만 할 수 있으며 요청자는 스스로 승인하지 못한다.
요청 중 착수·추가 요청은 차단한다. 응답 마감은 요청 후 최대10초와 원래 착수 마감 중 빠른 시각이다.
**응답 대기·거절·만료·재접속은 원래 착수 시계를 유지한다. 유효한 수락이 확정되면 서버 현재 시각부터 새 30초를 부여한다(2026-11-04 사용자 변경).**
동시 만료는 시간패가 우선이다. 응답 마감만 지나면 EXPIRED로 정리하고 원래 차례로 계속한다.
거절 후 재요청은 가능하며 요청만으로 시계가 늘어나지는 않는다. 동일 actionId의 수락 재확인도 마감을 다시 늘리지 않는다. 종료된 판·승패·기권·정산은 무르지 않는다.

공개 상태의 `undo`는 null 또는 `{requestId,requesterUserId,deadline}`이며 ID는 문자열, deadline은 서버 UTC ISO다.
`undoDecision`은 null 또는 `{requestId,status:ACCEPTED|REJECTED|EXPIRED}`다. 다음 착수·새 요청·종료 때 결과 안내를 정리한다.
참가자·승인 관전자·재접속 복구에 같은 상태를 보낸다. 상태 version은 무르기에도 증가하며 moveCount와 독립적이다.
같은 actionId 재확인은 이전 영수증만 반환한다. 무르기 전 착수 요청을 재전송해도 제거한 돌을 다시 놓지 않는다.
기존 STALE_VERSION / ACTION_ID_CONFLICT / NOT_YOUR_TURN / ACCESS_DENIED / INVALID_ACTION 오류를 재사용한다.

FE는 작은 사이드 카드에 요청·수락/거절·초 단위 응답 기한과 줄어드는 진행 막대를 표시한다.
모달이나 전체 화면을 가리지 않으며 만료 후 서버 확정을 기다리고 임의로 판을 되돌리지 않는다.
`undo` 필드가 없는 구서버에서는 버튼을 노출하지 않는다.

## 상태 전송

기존 `GAME_STATE`의 `publicState`에 아래 값을 담는다. 참가자·관전자 모두 privateState는 빈 객체다. 관전은 기존 인증·채널·20m 범위 검사와 함께 적용한다.

| 필드 | 내용 |
| --- | --- |
| gameCode / status | OMOK / PLAYING 또는 FINISHED |
| boardSize / board | 15, 15×15 배열. board[y][x]: 빈칸0/흑1/백2 |
| blackUserId / whiteUserId | 서버가 정한 흑·백 내부 계정 ID 문자열 |
| turnUserId / turnDeadline | 현재 차례 ID·UTC 마감. 종료 후 null |
| moveCount / lastMove | 착수 수, 마지막 {x,y,stone:BLACK 또는 WHITE}. 최초 lastMove=null |
| winnerUserId | 승자 ID 문자열. 진행 중/무승부는 null |
| endReason / endedAt | 종료 사유·UTC 종료 시각. 진행 중 null |

외부 gameId/version/role/publicState/privateState 포맷은 유지한다. 오목 모듈은 내부 tableId도 GameStateView에 전달하지만 외부 JSON에는 노출하지 않는다. 서버의 시간 만료는 GameStateChanged를 발행하므로 사용자 입력 없이도 상태가 전송된다.

## 서버 활성화·시작 연결

기본값은 꺼짐이다. `local`/`dev` 또는 운영 `prod,db`에서 `ontop.games.omok.enabled=true`로 실제 오목 엔진을 등록한다(운영과 local/dev 혼합 시 제외). dev/prod 환경변수는 `GAME_OMOK_ENABLED=true`이며 실제 시작에는 [예약 Gateway 연결](committed-game-start.md#켜는-조건)도 필요하다. 인증된 경기 통신에는 기존 `ontop.websocket.authenticated=true`와 실제 사용자 검증기가 필요하다. 테스트 헤더를 운영 코드에 추가하지 않았다.

참가 확정·차감 커밋을 확인한 **서버 내부 코드**가 `OmokEngine.create(gameId, tableId, blackUserId, whiteUserId)`를 호출한다. 흑/백은 이 호출자가 정해 전달한다. 같은 내용의 같은 경기 생성은 기존 판을 초기화하지 않는다. 다른 내용의 동일 ID, 같은 테이블/참가자의 다른 진행 오목 경기는 거절한다. 외부 임의 생성 API는 없다.

전원 준비→실제 시작 트랜잭션→이 생성 메서드 연결은 기존 시작 계약의 정식 연동 경계다. `start-rehearsal`은 dev 대역용이며 이 옵션을 켜서 실제 오목을 시작하는 방식이 아니다. 실제 차감·참가 기록·흑백 배정·종료/정산 후 다음 판 허용은 참가 확정 담당 코드가 연결해야 한다.

`OmokEngine`은 입력/상태/복구 Gateway를 구현한다. [공통 라우터](game-engine-routing.md)가 서버에 등록된 gameId로 분기하므로 [주사위 엔진](farkle.md)과 함께 켤 수 있다. 참가자·테이블의 중복 진행은 엔진 사이에서도 차단한다.

## 승패와 정산 구분

`OmokGameFinished`는 서버 승패 판정의 내부 알림이며 GameResultCommitted가 아니다. 재화 담당이 결과 저장·정산을 확정한 뒤 기존 GameResultGateway/GameResultCommitted로 전달해야 한다. 오목 모듈은 엽전 차감·지급을 하지 않고 가짜 SETTLED나 잔액을 만들지 않는다. 무승부의 재화 정책은 기존 미확정 항목으로 남긴다.

경기·중복 기록은 메모리이며 종료 판도 재조회용으로 보존한다. 재시작·다중 서버·DB 영속성·종료 이벤트 전달 보장을 제공하지 않는다. 알림 실패는 착수 실패로 바꾸지 않으며 GAME_STATE_CHECK/복구 조회로 확정 상태를 다시 읽을 수 있다. 이벤트 소비자의 영속 저장·재처리와 종료 경기 보존/정리는 정식 저장 연동에서 마련해야 한다.

## 한 번에 검증

눈으로 직접 플레이할 때는 [오목 브라우저 테스트](omok-demo.md)를 사용한다. 흑·백·관전자 화면과 테스트 전용 실행 방법을 안내한다.

`backend/`에서 `.\gradlew.bat flowTest`를 실행한다. OmokFlowTests는 실제 오목 규칙·Spring 서버·소켓·거리 서비스를 사용하여 착수/관전/중복/heartbeat 복귀/승리와 자동 시간패를 검사한다. 인증·참가 확정과 시간 경계는 테스트 대역/제어 시계이며 DB·지급 성공이나 실제 30초 대기 시험이 아니다.

금수 회귀도 같은 명령에 포함된다. 삼삼·사사·장목 각각의 소켓 거절 뒤 상태 불변·합법 재착수를 확인하며, 별도 연속 흐름에서는 금수 → heartbeat 단절 → 같은 판/마감으로 복귀 → 29초 진행 → 원래 30초 시간패 → 참가자/관전자 종료 수신·추가 입력 차단을 검증한다. 금수나 복귀가 시간을 늘리지 않는지 확인하는 검사이며 새 API를 추가하지 않는다.

## 상대 동의 무승부 요청 (2026-11-03 사용자 확정)

로컬 구현·미배포다. 기존 GAME_ACTION_SEND의 `input={"kind":"drawRequest"}`로 내 차례에만 요청한다. 돌을 두기 전에도 가능하며 **각자 경기당1회**다. 유효 요청 접수 시 거절·무응답에도 횟수를 쓰고, 잘못된 차례/버전/필드로 거절된 요청은 쓰지 않는다.

상대 참가자만 `input={"kind":"drawRespond","requestId":"요청 actionId","accept":true}`로 응답한다. false는 거절이다. 응답 기한은 요청 후10초와 원래 turnDeadline 중 빠른 시각이다. 원래30초 착수 시계는 대기·거절·만료·복구에도 계속 흐른다. 무르기 수락은 착수 시계만 새 30초로 바꾸며 무승부 사용 횟수는 되돌리지 않는다.

응답 대기 중에는 착수·추가 요청·무르기를 겹칠 수 없다. 기권은 기존 정책으로 종료하고, 착수 시간이 먼저 끝나면 시간패가 동의보다 우선한다. 수락 시 돌 배치를 보존한 채 FINISHED/winnerUserId=null/endReason=AGREED_DRAW, 공통 GameFinished의 양측 DRAW를 한 번 확정한다. 거절·무응답은 판/차례를 유지한다.

공개 상태의 새 선택 필드는 다음과 같다.

```json
{
  "draw": {"requestId":"draw-1","requesterUserId":"101","deadline":"2026-11-03T00:00:10Z"},
  "drawDecision": null,
  "drawRequestsUsed": ["101"]
}
```

draw는 대기 없으면 null, drawDecision은 null 또는 `{requestId,status:ACCEPTED|REJECTED|EXPIRED}`다. 사용 ID는 흑/백 순서로 최대2명, 새 경기는 빈 배열이다. 참가자·관전자·재접속이 같은 값을 받고, 상태 version은 계속 증가한다. 새 행동은 새 actionId/최신 expectedVersion, 같은 행동 재확인은 같은 ID/내용/요청 버전으로 멱등 처리한다. 기존 GAME_ACTION_* 오류를 사용한다. 관전자·본인 승인·다른 요청 ID·만료 뒤 응답·종료 뒤 새 행동은 거절한다.

UI는 오른쪽 아래의 작은 무르기·무승부 버튼으로 시작한다. 서버 승인 요청이 대기 중일 때만 같은 자리에 응답 카드·남은 초·진행 막대를 표시한다. 상대에게는 무르기(또는 무승부)/거절만, 요청자에게는 응답 대기만 보인다. 지난 결과는 재접속 때 다시 알리지 않고 새 응답 결과만 잠시 표시한다. 구서버에 draw/사용 기록이 없으면 숨긴다. 두 기능은 공간을 공유하고 동시 요청은 표시하지 않는다. 착수 시계·횟수·권한 정책은 그대로다.

종료 저장 입구 VerifiedGameFinish는 AGREED_DRAW를 허용하고 참가자 전원이 DRAW인지 검증한다. 기존 무승부 정산 경로로 전달하며 DB 스키마·차감/지급 계산은 변경하지 않는다. 엔진 이벤트의 검증 통과와 실제 개발 서버의 DB 정산 인수는 구분한다.
