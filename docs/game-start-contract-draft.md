# 게임 시작 연동 계약 초안

상태: 팀원 검토 전 초안 · 관련 이슈: [S15P31B105-26](https://ssafy.atlassian.net/browse/S15P31B105-26)

백엔드 A가 준비한 참가자 목록을 B에게 넘기고, B가 참가 검증·판돈 차감·게임 기록 생성을 끝내면 A가 게임을 시작하는 경계를 정한다. 정식 차감·경기 연동은 제안 단계다. 일부 메서드와 결과 처리는 DB 없는 [시작 연동 검증](game-start-rehearsal.md)으로 구현했으며, 기본 대기 WebSocket 명세와 구분한다.

## 현재 상태와 확정된 기준

| 구분 | 내용 |
| --- | --- |
| 현재 구현 | DB 없이 연결·착석·퇴장·준비를 동기화한다. `allReady=true`여도 게임을 시작하지 않는다. |
| 현재 사용자 | 연결별 `dev-UUID`다. 실제 계정 ID와 다르므로 재화 차감에 사용할 수 없다. |
| 현재 인원 | 개발용 테이블은 2석이다. 정식 인원 규칙은 게임 종류별로 검증해야 한다. |
| 확정된 판돈 | 게임 시작 시 참가자마다 기본 판돈 1엽전을 낸다. |
| 확정된 경기 중 종료 정책 | 연결 종료만으로 환불·기권 처리하지 않는다. AI가 같은 참가자의 경기를 이어간다. |
| 담당 분담 | A는 실시간 상태·시작 알림, B는 참가 조건·재화·게임 및 참가 기록·중복 시작 방지를 맡는다. |

추가 베팅·정산·AI 행동 구현은 이 계약의 범위 밖이다. 아래 시작 중 연결 종료 처리는 경기 중 AI 대행 정책과 충돌하지 않도록 제안한 경계다.

## 담당자가 주고받을 것

| 단계 | A 실시간 담당 | B 데이터와 재화 담당 |
| --- | --- | --- |
| 준비 완료 | 게임 선택·인원·준비 상태 확인, 참가자와 좌석 확정 | 게임 종류·인원 규칙의 기준 제공 |
| 시작 요청 | 서버에서 시작 시도 ID를 발급하고 확정 목록 전달 | 같은 시작 시도인지 확인 후 참가 가능 여부·잔액 검증 |
| 시작 확정 | B의 성공 결과를 기다림 | 게임·참가 기록·전원 판돈 차감·원장을 하나의 트랜잭션으로 반영 |
| 성공 수신 | 게임 ID와 확정 참가자로 실행 상태 연결, 사용자에게 시작 알림 | 같은 요청에 같은 확정 결과 반환 |
| 거절 수신 | 대기 상태 복귀·준비 초기화와 실패 안내 | 일부 참가자만 차감되거나 게임 기록만 남지 않도록 처리 |
| 결과 불명 | 새 요청으로 재시작하지 않고 동일 시작 시도 조회 | 처리 중·성공·확정 거절을 구분해 결과 제공 |

트랜잭션은 여러 DB 변경을 모두 성공시키거나 모두 취소하는 처리 단위다. A의 메모리 상태 변경과 B의 DB 트랜잭션이 하나로 묶인다고 가정하지 않는다.

## 정상 시작 순서 제안

1. 실제 계정 인증과 게임 선택을 완료한 참가자가 게임별 필요 인원만큼 착석하고 모두 준비한다.
2. A가 해당 테이블의 대기 상태와 참가자 구성을 확인하고 `WAITING → STARTING`으로 한 번만 전환한다.
3. A가 새 `startAttemptId`와 참가자·좌석·게임 종류·대기 버전을 확정한다. 게임 실행에 필요한 준비도 확인한다.
4. A가 상태 잠금을 해제한 뒤 B의 시작 처리를 호출한다. DB 작업을 기다리는 동안 테이블 잠금을 잡지 않는다.
5. B가 참가 조건과 잔액을 확인하고 게임·참가 기록, 1인당 1엽전 차감, 원장을 원자적으로 반영한다.
6. B는 DB 커밋이 끝난 뒤에만 `SUCCEEDED`와 게임 ID를 반환한다.
7. A는 반환된 시작 시도 ID가 테이블의 현재 시도와 같은지 확인하고 `STARTING → PLAYING`으로 전환한다.
8. A가 참가자에게 시작과 게임 초기 상태를 알린다. 개인 손패 등 비공개 상태는 해당 사용자에게만 보낸다.

`WAITING`, `STARTING`, `PLAYING`은 정식 경기 흐름의 상태 이름 제안이다. 개발용 `TableStartAttempt`는 `WAITING`·`STARTING`·`CONFIRMED`로 연동 결과만 관리한다. 현재 `TableRoom`에는 실제 경기 상태나 게임 선택 기능이 없다.

## 호출 방식과 요청 제안

같은 Spring Boot 앱 안의 서비스 메서드 호출을 우선 제안한다. 백엔드 담당자가 두 명이라는 이유로 HTTP 서버를 둘로 나누지 않는다. JSON은 전달할 데이터를 이해하기 위한 예시이며 브라우저가 보내는 WebSocket 메시지나 새 HTTP 엔드포인트가 아니다.

```text
A → B: startGame(command)
A → B: findStartResult(startAttemptId)
```

```json
{
  "startAttemptId": "2b119ea2-fd96-4efe-9d46-56d848a1ebc3",
  "tableId": "table-1",
  "tableVersion": 4,
  "gameCode": "OMOK",
  "participants": [
    { "userId": "101", "seatNumber": 1 },
    { "userId": "102", "seatNumber": 2 }
  ]
}
```

| 필드 | 제안 규칙 |
| --- | --- |
| `startAttemptId` | A가 서버에서 생성한 UUID. 같은 시작 시도의 중복 처리 방지 키다. 기존 WebSocket `requestId`와 다르다. |
| `tableId` | A가 관리하는 테이블 식별자. DB의 `room_id`와 어떻게 연결할지는 B와 확인한다. |
| `tableVersion` | A가 참가자를 확정할 때 관찰한 버전. 현재처럼 재시작 시 초기화될 수 있어 영속적인 중복 방지 키로 쓰지 않는다. |
| `gameCode` | 서버가 허용한 게임 코드. `OMOK`은 예시이며 최종 코드·선택 방식은 확인한다. |
| `participants` | 서버가 확인한 실제 계정 ID와 게임에 사용할 좌석 순서. 중복 사용자·좌석을 허용하지 않는다. |

`userId`는 JSON 예시에서 문자열로 표현했다. 실제 Java 타입과 B의 계정 PK 매핑은 인증 계약에 맞춰 정한다. 클라이언트가 참가자 목록·userId·차감액을 지정하게 하지 않는다. 기본 판돈은 B가 확정 정책인 1엽전을 적용하며 요청 금액을 신뢰하지 않는다.

## 성공과 거절 결과 제안

성공은 게임 기록과 전원 차감이 DB에 반영됐다는 뜻이다. WebSocket 알림이 모든 브라우저에 도착했다는 뜻은 아니다.

```json
{
  "startAttemptId": "2b119ea2-fd96-4efe-9d46-56d848a1ebc3",
  "outcome": "SUCCEEDED",
  "gameSessionId": "501",
  "entryFeePerPlayer": 1,
  "totalPot": 2,
  "participants": [
    { "userId": "101", "seatNumber": 1 },
    { "userId": "102", "seatNumber": 2 }
  ]
}
```

```json
{
  "startAttemptId": "2b119ea2-fd96-4efe-9d46-56d848a1ebc3",
  "outcome": "REJECTED",
  "code": "INSUFFICIENT_BALANCE",
  "message": "게임을 시작할 엽전이 부족합니다."
}
```

| 결과 또는 오류 | 의미와 처리 제안 |
| --- | --- |
| `SUCCEEDED` | 게임·참가·차감·원장 커밋 완료. A는 같은 게임 ID로 이어간다. |
| `REJECTED` | 이 시작 시도의 생성·차감이 반영되지 않았고 이후에도 성공으로 바뀌지 않는 확정 거절. A가 대기로 복귀한다. |
| `PENDING` | 같은 시도가 처리 중이다. A는 시작 중 상태를 유지하고 새 시도를 만들지 않는다. |
| `CONFLICT` | 기존 시도·경기와 충돌한다. 실패 확정으로 간주하지 않고 기존 결과와 참가자를 대조한다. |
| `INSUFFICIENT_BALANCE` | 한 명 이상 기본 판돈 부족. 전원 시작을 거절한다. |
| `PARTICIPATION_RESTRICTED` | 실제 계정의 참가 제한 등으로 시작 불가. |
| `INVALID_PARTICIPANTS` | 인원·중복·계정·좌석 구성이 유효하지 않음. |
| `GAME_UNAVAILABLE` | 게임 코드가 잘못됐거나 사용할 수 없음. |
| `ALREADY_IN_GAME` | `CONFLICT`의 사유. 테이블의 미종료 경기 또는 참가자의 다른 진행 경기와 충돌함. 기존 게임에 임의 합류시키지 않고 확인한다. |
| `IDEMPOTENCY_CONFLICT` | `CONFLICT`의 사유. 같은 시작 시도 ID를 다른 내용에 재사용함. 기존 시도의 결과를 덮어쓰지 않는다. |

오류 이름과 공개 범위는 제안이다. 참가 제한·잔액 같은 개인 사유는 B→A 내부 결과와 본인 안내에만 사용하고 테이블 전체에 사용자별 상세 정보를 노출하지 않는다.

`CONFLICT`는 `REJECTED`와 구분한다. 원래 시도가 이미 성공했을 수 있으므로 대기로 복귀해 새 시작을 허용하지 않는다. B와 기존 시도·경기의 연결을 확인한 뒤 복구 또는 확정 거절로 정리한다.

## 중복 차감과 결과 불명 처리 제안

멱등성이란 같은 시작 요청을 여러 번 받아도 게임 생성·차감을 한 번만 반영하는 성질이다.

- A는 같은 시작 시도에 같은 `startAttemptId`와 같은 내용을 사용한다. 준비 이벤트가 겹쳐도 시작 중 테이블에 새 ID를 발급하지 않는다.
- B는 처리 중이면 `PENDING`, 끝났으면 기존 확정 결과를 반환한다. 같은 ID의 다른 내용은 충돌로 거절한다. 중복 요청 때문에 게임·원장·차감을 추가하지 않는다.
- 새 ID로 들어오는 중복도 고려한다. B는 동일 테이블의 미종료 경기와 참가자의 다른 진행 경기 충돌을 검사한다. 검증과 기록 사이의 동시 요청도 막아야 한다.
- **타임아웃·예외·결과 조회에서 기록을 찾지 못한 것만으로 차감 실패를 확정하지 않는다.** 아직 실행 중인 원래 처리가 뒤늦게 커밋될 수 있다.
- 결과가 불명이면 A는 `STARTING`을 유지하고 같은 ID로 결과를 확인한다. B가 확정 거절을 보장하기 전에는 준비를 초기화해 새 게임 시작을 허용하지 않는다.
- 확정 거절 뒤 사용자가 다시 준비하면 새 시작 시도 ID를 발급한다. 이미 성공한 ID를 새 판에 재사용하지 않는다.
- B는 재시작 후에도 처리 결과를 판별할 근거가 필요하다. A도 시작 시도와 테이블의 연결을 복구해야 한다. 저장 방식·결과 조회 재시도 간격·처리 기한·수동 확인 절차는 협의 항목이다.

현재 메모리의 테이블 버전이나 기존 메시지 `requestId`만으로 이 보장을 제공하지 않는다. 중복 방지 기록의 테이블·필드·락 방식은 ERD 담당자가 선택한다.

## 시작 중 입력과 연결 종료 제안

| 상황 | 제안 동작 |
| --- | --- |
| `WAITING`에서 연결 종료 | 현재 동작처럼 좌석 제거·남은 참가자 준비 초기화. |
| B 호출 전에 확정 참가자의 종료를 감지 | 시작 시도를 중단하고 대기로 복귀. B에게 차감을 요청하지 않음. |
| `STARTING`에서 추가 착석·명시적 퇴장·준비 변경 | 확정 참가자가 바뀌지 않도록 거절. 강제로 브라우저를 닫는 경우까지 막을 수는 없음. |
| B 처리 중 실제 연결 종료 | 연결 없음만 기록하고 확정 참가자·시작 시도를 유지. B 결과를 기다림. |
| B가 확정 거절 | 대기로 복귀하고 전원 준비 false. 연결이 끊긴 사용자의 좌석을 정리. |
| B가 성공했는데 일부 연결 종료 | 확정 참가자를 경기에서 제거하거나 자동 환불하지 않음. 경기 연결·AI 대행 경계로 넘김. |
| B 성공 후 실행 상태 연결 또는 알림 실패 | 새 게임·차감을 만들지 않고 같은 게임 ID로 복구. 서버 장애 보상·환불은 별도 예외 정책으로 결정. |

B의 성공 커밋을 재화·참가 확정 경계로 삼는 안이다. 이 경계와 AI 인계 준비 조건은 팀원과 확인한다. 실제 경기/AI 처리와 복구가 준비되기 전에는 차감이 포함된 자동 시작을 활성화하지 않는다.

## 현재 코드에 연결할 위치

| 현재 파일 | 계약 확정 후 필요한 연결 |
| --- | --- |
| `TableHub.ready()` | 준비 처리 후 시작 조건을 확인하고, 한 번의 시작 시도만 생성하는 조정 로직에 연결. |
| `TableRoom` | 대기·시작 중·게임 중 구분, 게임 선택·확정 참가자·현재 시작 시도/게임 참조 추가 검토. |
| `TableHub.disconnect()` | 대기 중 좌석 제거와 시작 중·경기 중 처리를 구분. 현재 로직을 그대로 재사용하지 않음. |
| `TableProtocol`·개발 화면 | 사용자에게 보여줄 시작 중·시작 성공·실패 알림을 별도로 명세한 뒤 반영. |

현재 `TableHub.receive()`는 상태 잠금 안에서 `ready()`를 호출한다. 그 안에서 B의 DB 처리를 바로 기다리지 않고, 상태 확정 → 잠금 해제 → B 호출 → 현재 시작 시도 확인 후 결과 반영으로 나누는 방향이다. 구체적인 클래스와 실행 방식은 구현 단계에서 정한다.

| 시작 중 입력 | 참가자 목록 고정, 입력 거절 | A·B: UX·오류 코드·커밋 경계·종료 시 AI 인계 |
| 확정 거절 | 대기 복귀·전원 준비 false | A·B: 준비 초기화·개인 사유 안내 범위 |
| 중복·동시성 | 동일 시도 한 번만 차감·미종료 경기 충돌 방지 | B: 영속 기록·트랜잭션·락·확정 결과 보존 범위 |
| 장애·결과 불명 | 같은 시도 조회·임의 재차감 금지 | A·B: 재시작 복구·조회 기한·담당자 확인·보상 정책 |
| 프론트 알림 | 현재 메시지는 유지, 신규 규격 별도 작성 | A·프론트: 시작 중·성공·실패 표시와 공개/개인 정보 구분 |

## 계약 확정 후 검증할 시나리오

- 정상 시작에서 참가자 N명의 잔액이 각각 1 감소하고, 판돈이 N이며 게임·참가·원장 기록이 일치한다.
- 한 명이라도 잔액 부족·참가 제한이면 전원 차감·게임 기록이 부분 반영되지 않는다.
- 같은 시작 시도의 순차·동시 중복 요청이 같은 게임 ID를 반환하고 추가 차감하지 않는다.
- 같은 ID의 다른 참가자 요청과 다른 ID로 들어온 동일 테이블의 중복 시작을 거절한다.
- 준비 이벤트가 겹쳐도 A가 한 번만 시작을 요청하고, DB 처리 중에도 상태 잠금을 점유하지 않는다.
- 응답이 늦거나 예외가 나도 새 ID로 재차감하지 않으며, 뒤늦은 성공을 기존 게임에 연결한다.
- 시작 중 연결 종료·확정 거절·성공 후 AI 인계가 각 경계에서 일관되게 동작한다.
- 이전 시작 시도의 지연 결과가 다른 판이나 새 참가자 구성에 적용되지 않는다.
- 커밋 직후 프로세스 종료·실행 상태 연결 실패·알림 실패에서 같은 게임을 복구하며 중복 차감하지 않는다.

위 검사는 향후 구현의 완료 기준이며 아직 실행한 테스트 결과가 아니다.
