# 공원 공지 관리 API

상태: 2026-11-04 구현·단위/브라우저 계약 검증. 사용자가 V148의 팀 공유·사용 번호·적용 순서 확인 완료를 알렸고, 최신 dev 기반 MR 준비 범위를 승인했다. 이번 작업에서 실제 DB 적용·DEV/운영 배포는 수행하지 않았다.

## 권한과 화면

- `/admin/announcements`: 기존 운영 관리자(`canOperate`)만 편집. 조회 전용 관리자는 편집 불가.
- 공원: 회색 반투명 배너를 맨 위 정중앙에 고정해 표시 순서→ID 순으로 반복한다. 클릭·팝업·일시정지·Tab 포커스가 없는 보기 전용이다. 위치·낮밤·시간은 왼쪽 채널 정보 아래에 별도로 표시한다. 모션 감소 설정에서는 흐름 대신 전체 문구를 줄바꿈한다. 기존 점검 안내는 유지한다.
- 관리자 화면: 내용만 입력하고 공지 올리기를 누르면 즉시 게시한다. 관리용 제목은 비워두면 본문 앞 30자로 자동 생성하며, 기간·숨김 저장은 추가 설정에서 선택한다. 전체/게시·예약/지난 공지 분류와 제목·내용 검색을 제공하며, 지난 공지는 숨김 또는 기간 종료된 공지(삭제 제외)다. 숫자 입력 대신 전체 목록의 카드 손잡이 드래그 또는 위·아래 버튼으로 순서를 바꾸고 순서 저장으로 일괄 반영한다. 변경 중에는 본문 편집과 분류·검색을 잠시 막으며 되돌리기 또는 새로고침으로 취소한다. 목록에서 수정·숨김/게시·삭제 확인을 제공한다. 수정 중에는 숨김 토글을 막아 미저장 입력을 보존한다. 기존 API 필드·권한은 유지하고 순서 일괄 저장 경로를 추가했다. 새 공지는 마지막 순서에 추가한다.
- 게시 기간은 서버 시각 기준 `[startsAt, endsAt)`. 관리자 화면 입력은 기기 현지 시간→UTC 변환.
- 정기 재조회는 2~10초 간격이며 서버 예약 경계가 더 가까워도 최소 2초를 둔다. 따라서 새 예약 게시 노출은 경계 후 다음 조회까지 지연될 수 있다. 이미 받은 공지의 종료는 별도 로컬 경과시간 검사로 처리한다. 탭 복귀 즉시 조회. 마지막 성공 후 30초가 지나면 오래된 배너를 숨긴다. 종료 시각은 서버 시각+수신 후 경과시간으로 판단한다.

## 요청·응답

모든 API는 기존 Access JWT Bearer 인증, `Cache-Control: no-store`.

| 메서드 | 경로 | 권한 / 결과 |
| --- | --- | --- |
| GET | `/api/v1/announcements` | 회원 / 게시 중인 공지의 본문만 |
| GET | `/api/v1/admin/operations/announcements` | 운영 관리자 / 삭제되지 않은 전체 목록 |
| POST | `/api/v1/admin/operations/announcements/{id}` | 운영 관리자 / 생성, 같은 UUID·내용 재시도 중복 방지 |
| PUT | 위 경로 | 운영 관리자 / `expectedVersion` 일치 시 수정 |
| DELETE | 위 경로 + `?version=0` | 운영 관리자 / 버전 검사 후 삭제 표시, 204 |
| PUT | `/api/v1/admin/operations/announcements/order` | 운영 관리자 / 전체 카드 순서 일괄 저장, 204 |

생성 UUID는 브라우저에서 생성해 응답 유실 재시도에도 유지한다. 생성 후 변경/삭제된 ID를 새 공지로 재사용하면 409. 삭제는 DB 행을 즉시 제거하지 않는 soft delete다.

생성·수정 공통 JSON:

```json
{
  "title": "행사 안내",
  "text": "오늘도 즐거운 온탑 공원!",
  "published": true,
  "displayOrder": 1,
  "startsAt": null,
  "endsAt": null,
  "expectedVersion": 0
}
```

제목 1~80자, 본문 1~1000자, 순서 0~9999. 일반 텍스트이며 HTML을 실행하지 않는다. 시작/종료는 선택 사항, 둘 다 지정하면 종료가 더 늦어야 한다. 편집 응답은 `id, title, text, published, displayOrder, startsAt, endsAt, version, updatedAt`.

회원 조회 예시:

```json
{
  "serverTime": "2026-11-04T03:00:00Z",
  "refreshAt": "2026-11-04T03:00:10Z",
  "announcements": [
    {
      "id": "a78baf0b-0246-4391-adef-a247f90ac50a",
      "text": "오늘도 즐거운 온탑 공원!",
      "endsAt": null,
      "version": 0
    }
  ]
}
```

400 `ANNOUNCEMENT_INVALID`: 본문/기간 오류. 409 `ANNOUNCEMENT_CONFLICT`: 버전 충돌 또는 UUID 충돌. 401 미인증, 403 권한 없음. 저장소 비활성 또는 DB 조회 실패는 503. DB 내부 오류 상세는 공개하지 않는다. 실패 시 입력은 남기고, 409는 목록을 다시 읽은 뒤 수정한다. JPA `@Version`이 실제 동시 수정 충돌을 검사한다.

## 카드 순서 일괄 저장

전체 관리자 목록에서 삭제되지 않은 모든 공지의 ID·버전을 원하는 순서대로 보낸다. 숨김·기간 종료 공지도 포함한다.

```json
{
  "items": [
    { "id": "a78baf0b-0246-4391-adef-a247f90ac50a", "expectedVersion": 0 },
    { "id": "b78baf0b-0246-4391-adef-a247f90ac50a", "expectedVersion": 1 }
  ]
}
```

ID 중복·형식 오류·음수 버전은 400, 목록 누락·추가·버전 불일치는 409. ID 순으로 행 잠금을 잡고 전체 목록·버전을 먼저 검증한 뒤 하나의 트랜잭션에서 0부터 순서를 부여한다. 본문·게시 여부·기간은 변경하지 않는다. 성공 204 후 목록을 다시 조회해 새 버전을 사용한다. 동시 수정 충돌·실패 시 부분 순서 저장을 방지하는 구조이며 실제 DB 잠금/롤백 검증은 아직 미실행이다. 응답 유실 시 재조회해 적용 순서를 확인한다.

Postman 로컬 생성 예제의 03 목록 조회는 announcementOrder 배열을 저장한다. 배열을 원하는 순서로 바꾸고 06 일괄 저장을 실행한 뒤 다시 03을 조회한다. 기존 공지 수정/삭제 이후에도 03을 먼저 조회해야 한다.

## 저장·적용 경계

V148은 신규 `announcements` 테이블만 추가한다. 기존 테이블·인증·정산·점검 모드는 변경하지 않는다. `local/dev + db` 및 기존 PRODUCT_FEATURE_WITH_DB 조건에서 저장 서비스가 등록된다. 로컬 테스트 대역 검증은 실제 MySQL 저장·JPA 동시성 검증을 대신하지 않는다.

공유 확인: 2026-11-04 사용자가 V148 사용·적용 순서 확인 완료를 알렸다. V148만 신규 추가하며 기존 마이그레이션·데이터는 변경하지 않는다. MR 검토·병합과 실제 DB 적용/배포 결과는 별도로 확인한다.
