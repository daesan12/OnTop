# 붕어빵 v5: 새 판을 2분으로 변경 요청

작성일: 2026-10-29 · FE 브랜치: `feat/bungeoppang-two-minute-round` · 기준 dev: `bbbcd2f`

## 요청 요약

사용자 플레이테스트 결과 3분 진행이 길게 느껴져 **새 판은 120초, 마지막 30초는 가속**으로 변경한다.
FE 작업만으로 실서버 판의 종료 시각을 앞당기지 않는다. BE 소스·DB·서버 설정은 이번 FE 작업에서 변경하지 않았다.

| 항목 | 기존 판 | 새 판 요청 |
| --- | --- | --- |
| 플레이 | 180000ms | 120000ms |
| 가속 시작 | 150000ms | 90000ms |
| FE 가속 예고 | 147000ms | 87000ms |
| 유효 행동 시각 | `0 <= t < 180000` | `0 <= t < 120000` |
| 카운트다운 | 3500ms | 유지, 플레이 120초와 별도 |
| 보관 / 손님 | 10개 / 최대 3명 | 유지 |
| 가열 / 익힘 | FILL부터, 평시 8초 / 가속 6초 | 유지 |
| 불 원본 / 로그 한도 | 2048개 / 3600건 | 이번 요청에서는 유지 |
| 제출 유예 / 처리 여유 | 15000ms / 10000ms | 유지 |
| 보상 / 일일 한도 | 기존 정책 | 유지 |

## FE에서 준비한 내용

- 미리보기는 02:00부터 시작하고 01:30 경과 시 가속, 02:00 경과 시 입력 종료·정산한다.
- 실서버 어댑터는 `(durationMs, rushFromMs)`가 `(120000,90000)` 또는 기존 `(180000,150000)`인 판만 받는다.
  기존 서버가 3분 판을 발급하면 그대로 3분을 진행한다. 서버 판정을 우회해 2분에 완료하지 않는다.
- 시간 동기화·행동 로그·checkpoint 복구는 각 판의 서버 규칙을 사용한다. 2분 새 판에서 `t=120000`은 전송 전 거절한다.
- 기존 BE 공통 fixture `frontend/tests/fixtures/bungeoppang-v5-flow.json`는 변경하지 않았다.
  새 2분 fixture `frontend/tests/fixtures/bungeoppang-v5-2min-flow.json`를 추가했다.
  두 fixture는 동일한 납품·점수·재고를 검증하며 가속 구간 행동만 90초 기준으로 이동했다.
- 전체 랭킹의 고정 `3분 도전` 문구는 `전체 기간`으로 변경했다. 기존 랭킹 데이터는 변경하지 않았다.

## BE 담당자 작업

1. `backend/src/main/java/com/ssafy/ontop/minigame/service/BungeoppangV5Spec.java`의 **새 판** 규칙·timing을
   120000ms와 가속 90000ms로 발급한다. `playEndsAt = playStartsAt + 120000ms`가 되어야 한다.
2. 새 규칙에는 기존과 다른 `configVersion`을 사용한다. 예: `v5-20261029.1`(FE 테스트용 제안 식별자).
   저장된 기존 판의 `configVersion`, 규칙 JSON, 타임라인·해시 seed를 덮어쓰지 않는다.
3. **상수 두 개만 바꾸면 기존 판의 재계산이 깨질 수 있다.** 현재 `BungeoppangV5Rules.replay()`는
   `BungeoppangV5Spec.calculationRules()`를 사용한다. 납품·복구·완료의 재계산이 각 판에 저장된 규칙을 사용하도록 확인한다.
   기존 3분 판의 120초 이후 행동과 150초 가속도 원래대로 인정해야 한다.
4. `MinigameService`의 시작·선택 납품·checkpoint·시간 검증·완료·멱등 재시도에서 새 2분 판과 기존 3분 판을 함께 검증한다.
   `playEndsAt` 이전 완료는 `TOO_EARLY`, 이후 완료는 기존 보상 정책으로 한 번만 정산한다.
5. OpenAPI 설명·최대 행동 시각·테스트·실행 문서를 새 판 규칙에 맞춘다.
   기존 `rulesVersion=v5` 요청 형식은 FE가 유지한다. 다른 rulesVersion이 필요하다면 FE와 먼저 계약을 맞춘다.

## BE 반영 결과 (2026-10-29)

- 새 판: `configVersion` `v5-20261029.1`, `durationMs=120000`, `rushFromMs=90000`, `playEndsAt = playStartsAt + 120000ms`.
  `rulesVersion=v5` 요청·응답 형식은 바꾸지 않았다.
- 기존 판: `v5-20261027.1` 판은 판 원본에 저장된 180초·150초 규칙, 해시 seed, 타임라인으로 계속 진행·복구·정산한다.
  납품·완료·시작 재시도의 재계산은 전역 상수가 아니라 판에 저장된 규칙을 쓴다.
- 상세 계약·시간표: [v5 REST 계약 7절](../minigame-bungeoppang-v5-contract.md). 두 fixture는 BE 규칙 replay와
  격리 MySQL HTTP 테스트에서 각각 2분 판·3분 판으로 검증한다.

## 랭킹 확인 사항

현재 전체 랭킹은 `rulesVersion` 기준이다. 3분 기록과 2분 기록을 같은 v5 랭킹에서 비교하면 플레이 시간 차이가 생긴다.
기존 기록을 삭제하거나 초기화하지 말고, 새 시간대 기록을 분리할지 먼저 협의한다.
분리에 새 API 필드·규칙 버전이 필요하면 응답 예시와 함께 FE에 공유한다. 이번 FE 작업은 랭킹 API를 임의로 변경하지 않았다.

> BE 반영(2026-10-29): v5 랭킹을 판에 저장된 플레이 시간으로 분리했다. 기본 2분(`durationMs` 생략·120000),
> 기존 3분은 `durationMs=180000`. 결과 화면은 판의 `rules.durationMs`를 보낸다. 상세: [v5 REST 계약 8절](../minigame-bungeoppang-v5-contract.md).

## 완료 확인 기준

- 새 판 응답: `durationMs=120000`, `rushFromMs=90000`, timing 차이 120000ms.
- 89999ms 평시 / 90000ms 가속, 119999ms 입력 가능 / 120000ms 입력 불가.
- 가속 경계에 걸친 익힘, 세 손님 선택 납품·충원·탄 빵 폐기가 기존과 동일하게 동작.
- 새 2분 fixture의 납품 3건·완료·해시·통신 재시도·복구 검증.
- 기존 3분 fixture와 진행 중 3분 판의 납품·완료 검증 유지.
- DEV에 배포한 후 FE에서 새 판이 02:00으로 시작하고, 00:30부터 가속되며 정상 정산되는지 함께 확인.

## FE 검증 범위

- 전체 단위 테스트 1045건 및 이후 추가한 기존 3분 판 유지 회귀 테스트 통과.
- 프로덕션 빌드, 테스트 포함 타입 검사, 마이그레이션 경계 검사 통과.
- Headless Edge에서 실제 시간으로 2분을 진행하며 02:00 시작 → 남은 00:30 가속 → 120초 종료·결과를 확인했다.
  이 검증은 보상 없는 FE 미리보기이며 실제 서버 배포·DB·보상 검증은 아니다.
- 손님 순차 입장·일반 구간의 충원 대기·90초 이후 연속 충원·복귀 시 정리 시나리오도 통과했다.
- BE 코드·DB·서버 설정은 변경하지 않았다. 서버 전환 전에는 실제 서비스가 계속 3분 판을 발급할 수 있다.

## 전달용 채팅

> 붕어빵 게임을 테스트해 보니 3분이 길게 느껴져, 새 판을 2분으로 줄이려고 합니다.
> FE는 120초 진행·마지막 30초 가속에 맞춰 수정했고, 기존 서버의 3분 판도 처리하도록 호환성을 유지했습니다.
> BE에서 새 판의 durationMs를 120000, rushFromMs를 90000으로 발급하고 timing·입력 검증·정산을 맞춰 주세요.
> 기존 3분 판은 원래 규칙으로 끝날 수 있어야 하므로, 전역 상수 변경만으로 기존 판의 재계산 규칙이 바뀌지 않도록 확인 부탁드립니다.
> 상세 요청과 두 시간대 검증 fixture는 이 문서에 정리했습니다. 기존 랭킹은 삭제하지 말고 2분 기록 구분 방법도 함께 확인 부탁드립니다.
