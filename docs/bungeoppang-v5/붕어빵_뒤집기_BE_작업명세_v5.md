# 붕어빵 뒤집기 BE 작업명세 v5

> 2026-10-28 변경: 사용자 요청으로 가열 시작을 소 투입(FILL)으로 되돌렸습니다. 반죽만 있는 동안은 불·익힘·불 cursor가 진행되지 않습니다. BE 담당자에게는 사용자가 별도 전달했으며, BE 완료 후 최종 응답/fixture를 대조합니다. 이번 구현은 FE 변경입니다.

작성일: 2026-10-27 · 담당: 미니게임 서버·DB·월드 이용 상태 담당

기준: [최종기획 v5](붕어빵_뒤집기_최종기획.md) · FE: [FE 작업명세 v5](붕어빵_뒤집기_FE_작업명세_v5.md) · 현행: [v4 REST 계약](../minigame-bungeoppang-v4-contract.md)

**향후 작업명세이며 구현 완료 문서가 아니다.** 사용자 확정 요구는 소 투입부터 가열, 쟁반 10개, 동시 손님 최대 3명, 실제 180초·마지막 30초 가속, 탄 빵 뒤집기 금지·즉시 폐기다. 이 문서의 v5 버전명·DTO 확장·저장 구조·기술 한도는 이를 구현하기 위한 **제안 계약**이다. FE와 확정한 뒤 OpenAPI·공통 fixture를 함께 갱신한다.

## 1. 변경 범위와 기존 정책

현재 `BungeoppangV4Spec`은 60초·40초 가속·쟁반 4개를 정의하고, `BungeoppangV4Rules`는 FILL 때 불을 소비한다. `MinigameService`는 최근 발급 주문 하나만 납품 대상으로 허용한다. 상수만 바꾸면 가열 시점과 세 주문의 검증·복구가 맞지 않는다.

| 변경 | 필요한 서버 책임 |
| --- | --- |
| 소 투입부터 가열 | 성공 FILL에서 불 소비·앞면 원점 저장, POUR는 반죽만 올림 |
| 쟁반 10개 | 재계산·checkpoint·폐기·납품에서 상한 10 적용 |
| 손님 최대 3명 | 활성 주문 집합·자리·선택 납품·충원 원자성 관리 |
| 3분·마지막 30초 가속 | 180000ms 마감, 150000ms 구간 계산, 기한·입력/본문 한도 재산정 |
| 탄 빵 즉시 폐기 | 탄 상태 TURN/FILL 거절, DISCARD로 무득점 제거 |
| 이용 상태 말풍선 | 서버 `playEndsAt`까지 유지하고 완료·포기·만료 시 해제. 이번 MR에는 FE 수신·표시만 포함 |

다음은 기존 정책을 유지한다: 회원당 활성 판 1개, 서버 발급 난수·주문, 종류별 FIFO, 부분 납품 없음, 납품 중 무지급, 최종 완료에서 멱등 지급, 일일 100냥·최초 성공 정산 KST 날짜 기준, 탭 비활성/통신 대기에도 시간 진행, 커밋 이후 공개 이용 상태 방송.

3D 손님 경로·애니메이션·불꽃·쓰레기통 모델은 FE 책임이다. 별도 공개 NPC API·공개 손님 WebSocket 이벤트·FastAPI 서비스·브라우저 물리 권한은 추가하지 않는다.

## 2. BE-01 — 버전과 판별 규칙 스냅샷

### 버전 분리

- [제안] 신규 요청은 명시적 `rulesVersion="v5"`로 선택한다. 버전 미지정과 v2/v4는 기존 동작을 유지한다.
- 세션의 저장된 버전으로 GET·납품·완료·포기를 dispatch한다. 진행 중 v4를 v5로 바꾸지 않는다.
- 기존 v4 `configVersion`의 값을 덮어쓰지 않는다. 예시 `v5-20261027.1`은 미배포 제안 식별자다.
- 시작 멱등 키를 다른 버전으로 재사용하면 기존처럼 충돌 처리한다. 같은 키 재시도는 같은 판·시각·불·초기 세 주문을 반환한다.
- 최초 시작 응답 재생과 현재 세션 조회는 구분한다. 이미 종료된 판이라도 시작 영수증을 새로 작성하지 않는다.
- 로그 정규화·prefix hash의 버전 구분도 v5로 분리한다. 기존 `BUNGEOPPANG/v4` seed를 새 규칙에 그대로 쓰지 않으며 FE·BE가 동일한 바이트 규격과 공통 해시 fixture를 사용한다.

### 판별 설정 제안

| 필드/의미 | v5 기준 |
| --- | --- |
| `slots` | 6 |
| `durationMs` | 180000 |
| `countdownMs` | 기존 3500 |
| `sideMs`, `rushSideMs` | 기존 8000, 6000 유지안 |
| `rushFromMs` | 150000 |
| `heatAssignment` | 제안: `FILL` |
| `heatMin`, `heatMax` | 기존 85, 115 |
| `trayCapacity` | 10 |
| `maxActiveOrders` | 제안: 3 |
| `maxOrderItems` | 기존 4, 세 주문 합계 상한이 아님 |
| 주문 분포·보너스 | 기존 특수 20%, 특수 빵별 50%, 첫 발급 주문 팥2 |
| 품질·콤보·보상 | 기존 v4 값 유지 |
| `minGapMs`, `sameSlotGapMs` | 기존 50, 300 |
| `maxLogEntries` | 설계안: 3600, §9에서 근거·검증 조건 명시 |

단위와 정수 범위를 FE에 명시한다. 서버 스냅샷과 checkpoint가 해당 규칙 버전으로 복원 가능해야 한다.

## 3. BE-02 — 소 투입 가열·익힘·탄 빵

### 행동 재계산

| 행동 | 전제 | 변경 |
| --- | --- | --- |
| `POUR(slot)` | 빈 칸 | phase=batter, since=0, heat=100(미배정), 불 소비/가열 없음 |
| `FILL(slot,filling)` | 반죽, 불 원본 잔여 | 다음 불 1개 소비, 소 확정, phase=front, 앞면 since=t |
| `TURN(slot)` 앞면 | 소가 있고 현재 면이 BURNT 아님 | 앞면 익힘 고정, phase=back, 뒷면 since=t |
| `TURN(slot)` 뒷면 | 현재 면·고정 앞면이 BURNT 아님 | 기존 양면 판정, 정상만 쟁반 저장, RAW 실패 규칙 유지 |
| `DISCARD(slot)` | 비어 있지 않은 칸 | 현재 시점 탄 여부 계산, 칸 비움, 불 반환 없음 |
| `TRAY_DISCARD(breadId)` | 실제 보관 중인 빵 | 정확히 한 개 제거 |
| `DELIVER(orderId,deliveryKey)` | 서버 발급 활성 주문, 재고 전체 충족 | §4·§6의 원자 처리 |

탄 상태는 별도 클라이언트 이벤트 없이 해당 행동 시점의 시간으로 판정한다. 반죽만 있는 동안은 익거나 타지 않는다. 가열 후 익힘 100 이상인 앞면/뒷면의 FILL과 TURN을 거절한다. 서버는 `TURN`을 임의로 `DISCARD`로 바꾸지 않는다. FE가 탄 칸의 일반 조작을 명시적인 DISCARD 로그로 전환한다.

### 계산과 상태 보존

```text
N = 현재 면의 시작 시각~행동 시각 중 [0, 150000) 구간 ms
R = 같은 구간 중 [150000, 180000) 구간 ms
level = floor(h × (N×6000 + R×8000) / (8000×6000))
```

- 앞면 시작은 성공 FILL, 뒷면 시작은 정상 TURN이다. POUR는 가열을 시작하지 않는다.
- Java 중간 곱은 충분한 정수 폭을 사용하고 마지막에 한 번 내림한다.
- 품질 49/50/69/70/90/91/99/100 경계와 기존 점수·콤보를 유지한다.
- 쟁반 10개 상태의 정상 꺼내기는 부분 변경 없이 거절한다. 이 거절은 빵을 식히거나 시간을 정지시키지 않는다.
- 탄 빵은 쟁반에 저장하지 않으므로 쟁반이 꽉 차도 DISCARD가 가능하다.
- 잘못된 재료·없는 대상·TURN/FILL 불가·간격 위반은 불 cursor·로그 승인 위치·콤보·재고를 바꾸지 않는다.
- 가열 전 반죽 checkpoint는 heat=100(미배정), since=0이며 불 cursor는 증가하지 않는다. 가열한 앞면/뒷면은 실제 heat·since를 보존하고 복구 시 재배정하지 않는다.

### 결과 집계 제안

기존 통계 필드를 재사용하되 v5의 의미를 문서화한다. 일반 폐기는 wasted/grillDiscarded 또는 trayDiscarded를 1 증가시킨다. **탄 철판 빵의 직접 폐기는 failed와 wasted/grillDiscarded를 각각 1 증가**시키고 made/successfulMade/served는 늘리지 않는 안이다. failed와 wasted는 중첩될 수 있으므로 합으로 총 생산량을 만들지 않는다. 필요하면 `burntDiscarded`를 별도 확장한다. v4 결과 필드의 의미를 소급 변경하지 않는다.

## 4. BE-03 — 활성 주문 최대 3건과 빈자리 충원

### 주문 식별과 발급

- 판 안에서 고유한 `orderId`를 발급한다. `customerSlot`은 0..2의 표시 자리이며 주문 ID가 아니다.
- 발급 순번은 단조 증가한다. 기존 `orderIndex`를 유지하더라도 “현재 처리할 단일 주문 위치”로 해석하지 않는다.
- [설계안] 시작 트랜잭션에서 세 주문을 발급·저장한다. 첫 발급 주문만 팥2, 나머지는 기존 분포를 적용한다.
- `ACTIVE → DELIVERED`는 한 번만 성공한다. 활성 자리에는 최대 한 주문만 연결한다.
- 세 주문은 서버가 발급한 현재 활성 주문이므로 FE에 모두 공개한다. FE는 이 주문을 받아 손님을 한 명씩 표시할 수 있으며, 아직 화면에 나타나지 않았어도 이미 발급된 활성 주문은 이 집합에 포함한다. 아직 발급하지 않은 미래 주문·미래 시드/목록은 제공하지 않는다.
- 주문마다 수량 합 1..4를 검증한다. 전체 3주문의 합이 10을 넘어도 합법이다.
- [설계안] 활성 세 주문 중 어느 주문이든 먼저 납품할 수 있다. 전역 FIFO는 강제하지 않으며 **빵의 종류별 FIFO**는 유지한다.

### 충원

납품 승인과 같은 트랜잭션에서 대상 주문을 완료하고, 그 빈자리에 새 주문을 최대 한 건 발급한다. 다른 활성 두 주문은 그대로 유지한다. 멱등 재시도는 새 주문을 다시 추첨하지 않는다.

충원 여부는 납품 HTTP 처리 시점의 우연한 지연에 따라 달라지지 않도록, 합법한 DELIVER의 상대 시각 `t<180000`을 기준으로 같은 영수증에 결정·저장하는 안을 사용한다. 유예 중 뒤늦게 승인되어 충원 기록이 생겨도 새 입력 시간은 열리지 않고 FE는 종료 화면에 새 손님을 등장시키지 않는다. 이후 만료/완료에서 남은 활성 주문을 종료 처리한다.

납품 애니메이션 종료·GET 조회·화면 재진입을 주문 재발급 조건으로 사용하지 않는다. 서버의 별도 입장 지연/손님 이탈 시스템은 추가하지 않는다. FE는 승인된 주문에 대해 첫 손님 1명·평소 약 6초 간격·교체 손님 최소 2.5초 대기·마지막 30초 약 0.7초 충원 연출을 적용한다. 이 간격은 서버 발급 시각이나 납품 검증 시각을 변경하지 않는다.

## 5. 제안 API 확장과 복구 데이터

기존 `/api/v1/minigames/sessions`와 세션별 GET·`deliveries`·`complete`·`abandon` 경로를 버전 선택으로 확장하는 안이다. **새 구현이나 승인 완료 DTO가 아니라 FE·BE가 맞출 구체 제안이다.** 기존 인증·소유권·no-store·CORS·키 형식·오류 공통 계약은 보존한다.

### 활성 주문 표현

v5 checkpoint에는 단일 `currentOrder` 대신 `activeOrders`를 사용한다. 아래는 주문 관련 필드만 발췌한 예시다.

```json
{
  "rulesVersion": "v5",
  "configVersion": "v5-20261027.1",
  "checkpoint": {
    "revision": 0,
    "activeOrders": [
      { "orderId": "1", "customerSlot": 0, "availableAfterSeq": 0, "items": { "bean": 2, "custard": 0, "pizza": 0, "chocolate": 0 } },
      { "orderId": "2", "customerSlot": 1, "availableAfterSeq": 0, "items": { "bean": 0, "custard": 1, "pizza": 0, "chocolate": 0 } },
      { "orderId": "3", "customerSlot": 2, "availableAfterSeq": 0, "items": { "bean": 1, "custard": 0, "pizza": 1, "chocolate": 0 } }
    ]
  }
}
```

- `revision`, `throughSeq`, `prefixHash`, `heatCursor`, `lastAt`, `slots`, `tray`, `stats`는 기존 역할을 유지한다.
- 위 예시의 생략 필드는 실제 응답에서 누락하라는 뜻이 아니다. 슬롯/쟁반/통계·판 원본·시간 필드를 기존 역할에 맞게 포함한다.
- `orderId`, `minigameSessionId` 등 서버 BIGINT 식별자는 십진수 문자열로 전달한다. `breadId`의 wire 타입도 JS 안전 범위와 기존 계약을 확인해 고정한다.
- `customerSlot`과 서버 발급 이력을 검증하되, FE가 보낸 자리 번호·주문 내용으로 서버 주문을 덮어쓰지 않는다.
- FE 선행 구현의 제안 어댑터는 각 주문에 `availableAfterSeq`를 사용한다. 초기 주문은 0, 충원은 직전 승인 DELIVER의 seq이며 현재 checkpoint의 throughSeq 이하여야 한다. 다른 필드 표현으로 확정하면 FE 어댑터도 함께 맞춘다.
- 완전한 checkpoint 조회로 판 원본·현재 세 주문·기승인 로그·영수증·결과를 복구할 수 있어야 한다.

### 납품 요청/응답

기존 로그의 `DELIVER`에 대상 `orderId`·`deliveryKey`를 사용한다. 세 손님마다 임의 별도 로그를 만들지 않고 **판 전체의 단일 행동 순서**를 유지한다.

납품 응답에는 대상 주문, 소비한 빵 ID, 점수/보너스 변화, 승인 prefix, 새 revision, 전체 활성 주문을 담은 checkpoint를 포함한다. `replacementOrder` 같은 별도 편의 필드를 추가하면 checkpoint와 반드시 일치해야 한다. v4의 `nextOrder` 한 필드로 세 주문을 표현하지 않는다.

과거 멱등 응답은 최초 snapshot을 그대로 재생할 수 있다. FE가 과거 revision으로 현재 상태를 덮지 않도록 계약에 명시하고, 현재 상태는 GET으로 조회하게 한다.

오류는 기존 공통 envelope를 유지한다. 타 버전·해시 불일치·변경된 멱등 본문·이미 납품한 주문·부족한 재고·상충 prefix·기한 초과를 구분하고, 탄 상태 FILL/TURN에는 판정 detail을 추가하는 안을 사용한다. 정확한 HTTP 상태·코드명·checkpoint 포함 여부는 v5 OpenAPI에서 고정하며, 단순 규칙 거절로 Wallet을 변경하지 않는다.

## 6. BE-04 — 납품·재고·충원의 원자성과 경합

현재 v4의 Wallet/판 잠금과 영수증 기반을 확장한다. 저장 판 버전을 확인한 뒤 인증·소유권 검사를 먼저 수행한다.

1. 같은 키 영수증이 있으면 같은 의미 본문인지 검사하고 최초 결과를 재생한다. 새 검증·재고 소비·충원을 하지 않는다.
2. 승인된 prefix가 요청 로그의 prefix와 일치하는지 확인한다. 시간·불·반죽·쟁반을 처음부터 같은 규칙으로 재계산한다.
3. 대상 주문이 이 판에서 발급되어 **해당 로그 위치에서 활성**인지 확인한다. 이미 납품한 주문·없는 주문·이전 자리의 주문을 거절한다.
4. 주문 전체 수량을 확인하고 종류별 가장 오래된 빵 ID부터 소비한다. 부족하면 전체 거절하고 일부 재고를 먼저 빼지 않는다.
5. 점수·납품 통계·대상 주문 완료·빈자리 한 건 충원·승인 prefix/revision·최초 영수증을 같은 트랜잭션에 저장한다.
6. 실패/롤백은 위 변경을 모두 취소한다. 규칙 거절 영수증·복구 checkpoint는 기존 정책처럼 일관되게 제공한다.

다른 손님 주문에 같은 빵을 사용하는 병렬 요청도 동일한 판 순서로 검증한다. 한 요청이 먼저 소비한 재고를 다음 요청이 다시 쓸 수 없다. 상충하는 prefix는 복구 가능한 거절로 처리하며, 서버가 로그를 임의 병합해 승인하지 않는다.

FE 기본안은 판당 납품 한 건만 전송하는 방식이다. 서버는 잘못된 클라이언트나 재시도로 병렬 요청이 생겨도 무결성을 유지해야 한다. 세 주문의 납품을 별도 독립 지갑 처리로 나누지 않는다.

### 재계산에 필요한 발급 이력

초기 세 주문은 seq=0에서 활성이다. 충원 주문은 어떤 DELIVER 승인 뒤에 발급됐는지 보관한다. 제안 필드 의미는 `availableAfterSeq`/`replacesOrderId`다. 현재 상태만 저장해 과거 로그에 미래 주문을 끼워 넣지 않는다.

전체 로그 재계산은 승인된 발급 이력과 순서를 함께 사용한다. 최초 납품의 t보다 이른 위치에서 그 충원 주문을 납품하는 로그는 거절한다. 재생 검증 과정에서 새 난수를 추첨하지 않는다.

## 7. BE-05 — 180초 시간·마감·최종 정산

기존 미래 시작 원점과 상대 시간 검증 구조를 유지한다.

| 시각/구간 | v5 제안 |
| --- | --- |
| `countdownStartsAt` | issuedAt + 기존 준비 여유 1000ms |
| `playStartsAt` | countdownStartsAt + 3500ms |
| `playEndsAt` | playStartsAt + 180000ms |
| `submitDeadline` | playEndsAt + 기존 유예 15000ms |
| `expiresAt` | submitDeadline + 기존 drain 10000ms |
| 합법 행동 t | 정수 `0 <= t < 180000` |
| 가속 구간 | `150000 <= t < 180000` |

- 제출/처리 유예는 새로운 게임 입력 시간을 늘리지 않는다. 서버 미래 입력 오차 검증은 기존 정책을 유지한다.
- `179999`는 시간 범위상 유효, `180000`은 거절한다. `149999/150000`은 구간 경계이며 이전 시간을 소급 가속하지 않는다.
- 179.9초 DELIVER의 응답이 180초 이후 도착해도 유예 안의 동일 요청을 한 번 검증한다. 완료가 먼저 처리돼도 최종 로그의 마지막 미승인 납품을 같은 계약으로 반영한다.
- FE 한 건 전송 기본안에 맞춰 최종 미승인 DELIVER 최대 1건 정책을 유지하는 안이다. 이를 늘리려면 공통 로그·영수증·완료 복구를 함께 설계한다.
- 완료·납품·포기·만료 경합은 기존처럼 같은 잠금 아래 최초 유효 terminal 커밋으로 수렴한다. 롤백은 성공 종료가 아니다.
- 최종 점수·일일 누계·Wallet 원장 지급은 기존 멱등 트랜잭션에서 한 번만 반영한다. 납품 때 실제 엽전을 지급하지 않는다.
- KST 자정 전후에도 최초 성공 정산일 귀속과 동일 판 재지급 방지를 유지한다.

## 8. BE-06 — 저장 구조와 공개 이용 상태

### 저장 구조

새 판의 규칙·시간·불·최대 3활성 주문·발급 인과관계·승인 prefix·checkpoint·영수증·최종 결과를 영속 보관한다. 서버 재시작이나 응답 유실 후 주문을 재추첨하지 않는다.

현재 v4 주문 테이블은 단일 현재 주문과 발급 순서를 전제로 한다. **v4 테이블 이름만 v5에서 재사용하면 된다고 간주하지 않는다.** BE/DB 담당은 신규 v5 구조 또는 호환 가능한 공용 구조를 선택해 ERD·migration을 작성한다. 권장안은 기존 v4 판을 건드리지 않는 v5 분리 구조다.

필수 제약/불변식:

- 판별 주문 ID·발급 순번 고유
- 활성 자리 0..2, 한 자리 한 활성 주문, 활성 개수 최대 3
- `(session, operation, key)` 영수증 고유, 주문당 승인 납품 한 번
- 규칙/configVersion·불 원본 불변, 같은 시작 키의 초기 주문 불변
- 슬롯·재고·주문·승인 로그·점수·영수증의 트랜잭션 일치

이미 적용된 V124~V126 migration은 수정하지 않고 저장소의 다음 사용 가능한 버전을 사용한다. 공유 DB 검증·배포 순서·이전 FE 호환 여부를 명시한다.

### 이용 상태 말풍선

최신 dev `165c155`에는 이용 상태 BE 기능이 없으며 이번 FE 전용 MR에도 BE 변경은 포함하지 않는다. 이전 브랜치의 참고 구현에는 `WorldChannelRegistry.minigameActivity()`의 120초 상한이 있었지만 이를 가져오지 않았다. BE 구현 시 v5는 시작 승인부터 카운트다운 포함 약 184.5초가 남을 수 있으므로 서버 `playEndsAt`까지 유지하도록 한다.

- 서버가 발급한 `playEndsAt`까지 공개 `activity=BUNGEOPPANG`을 유지하도록 제한을 판별 최대 기간에 맞춘다. 상한을 두면 준비 여유·카운트다운을 포함해 충분하게 정하고 테스트한다.
- 종료·포기·무효·시간 만료·채널 퇴장·단절 정리, AFTER_COMMIT, 이전 세션 지연 이벤트 방지를 유지한다.
- 공개 payload는 기존 이용 상태 코드만 유지한다. 개인 손님·3건 주문·재고·불·입력 기록을 공개 월드에 추가하지 않는다.

## 9. BE-07 — 불 목록·로그·본문·검증 비용

3분에 맞춰 행동/본문 한도를 확인한다. 불은 성공 FILL에만 소비하며 기존 512개 목록의 충분성도 새 시간·로그 한도에서 확인한다.

### 초기 기술 한도 제안

- 로그 최대 `L=3600`: 180000ms 구간에서 전체 최소 간격 50ms인 행동의 이론적 상한에 맞춘다. 정확한 경계 검사와 요청률 제한은 별도 유지한다.
- 불 목록 2048개 유지안: 성공 FILL 수를 F라 하면 각각 POUR도 필요하고 최초 6칸 이후에는 제거가 필요하므로 L >= 3F-6, F <= floor((3600+6)/3)=1202다. 2048개는 이 보수적 상한을 포함하며 가열 전 반죽 폐기는 불을 소비하지 않는다.
- 불은 85..115 정수로 생성하고 성공 FILL에만 소비한다. 가열 전 반죽 폐기는 불을 소비하지 않고, 가열 후 폐기는 사용한 불을 반환하지 않는다.
- 본문 제한은 v5에 한해 **최대 1MiB를 초기 제안**으로 둔다. 3600개 최악 길이 유효 로그를 실제 직렬화해 여유를 확인하고, 앱·프록시·파서·DB 한도를 함께 맞춘다. 기존 256KiB가 충분하다고 가정하지 않는다.

이 수치는 사용자 확정 밸런스가 아니라 기술 설계안이다. 입력 상한·행동 형식·주문 식별 길이를 바꾸면 불 개수·본문·메모리·재생 비용을 다시 계산한다. 소진 시 FE 추첨/재활용은 허용하지 않는다.

납품마다 전체 prefix를 재검증하는 현행 구조에서 로그 증가와 손님 세 명이 만든 납품 횟수 증가를 함께 측정한다. 요청/판별 잠금 시간·DB 저장 크기·완료 지연·복구 GET 크기를 기록한다. 증분 검증으로 최적화한다면 승인 prefix 불변과 전체 재생 동일 결과를 별도 검증한다. 한도만 올리고 처리시간 검증을 생략하지 않는다.

## 11. 작업 순서와 인계물

1. **계약 확정:** v5 선택, 활성 주문 구조/충원 인과관계, burnt 통계, 시간·기술 한도를 FE와 확정한다.
2. **순수 규칙:** FILL 가열·앞면 원점 저장·10개 재고·선택 주문·탄 빵 폐기와 공통 fixture를 구현한다.
3. **저장·서비스:** migration, 세 주문 발급·멱등 납품/충원·checkpoint·조회/재시작 복구를 구현한다.
4. **종료·지급:** 180초 마감·마지막 미승인 납품·경합·Wallet 정산을 검증한다.
5. **월드 상태:** 이용 말풍선 기간 제한과 정리를 수정한다.
6. **통합 검증:** 실제 dev 두 계정, 실제 DB 지급, 공원 복귀, FE 180초 플레이를 확인한다.

인계물은 OpenAPI/JSON 예시·규칙/configVersion, migration·DB 적용 방법, 공통 fixture, 오류/재시도/복구 안내, 테스트 결과, 비용 측정, 배포 커밋·활성 설정·회귀 결과다. 기존 local/dev+db 및 `ontop.minigames.enabled` 조건을 확인하며, 이 기획만으로 prod 활성 범위를 확대하지 않는다.

담당 범위 요약: **BE는 세 주문·불·시간·재고·확정 점수를 신뢰할 수 있게 처리하고, FE는 그 결과로 개인 3D 장면을 표현한다.**

## 12. FE 선행 구현의 연동 지점 — 2026-10-27

FE에 v5 순수 규칙, 개인 3D 카트 장면, 명시적 개발 미리보기와 제안 REST 어댑터를 작성했다. 기본 서비스는 v4를 유지하며, v5 오류를 미리보기로 자동 대체하지 않는다. **실제 v5 BE/DB 연동 완료를 뜻하지 않는다.**

- 실행 미리보기: frontend에서 `pnpm dev:bungeoppang:v5` (실제 지갑·엽전 지급 없음)
- 실제 서버 전환 조건: BE가 제안 계약을 확정·배포한 뒤 FE 빌드 설정 `VITE_BUNGEOPPANG_RULES_VERSION=v5`
- 어댑터: `frontend/src/features/bungeoppang/serviceV5.ts`
- 공통 입력/기대값: `frontend/tests/fixtures/bungeoppang-v5.json`
- 시작 규칙: 기존 rules 필드와 `heatAssignment="FILL"`, `maxActiveOrders=3`
- 시작/납품/복구: `checkpoint.activeOrders[]` 및 기존 슬롯·쟁반·통계·prefix 필드
- 로그: DELIVER는 `orderId`, TRAY_DISCARD는 `breadId`, 나머지 조리 행동은 `slot`, FILL만 `filling`
- 해시: 기존 action tuple 체인을 유지하되 초기 seed를 `BUNGEOPPANG/v5` + 줄바꿈 + 세션 ID + 줄바꿈 + configVersion + 줄바꿈으로 구분

현재 어댑터의 단위 테스트는 제안 계약의 응답 대역으로 검증한다. BE 담당은 실제 API 예시·오류·checkpoint·hash fixture를 확인해 회신하고, 배포 후 실제 두 계정·공유 DB 검증을 함께 진행한다.

## 13. 최신 FE 연출 변경과 BE 확인 범위 — 2026-10-28

손님 6종의 모델·대기/걷기·입퇴장, 구름 말풍선의 인사→주문→이미지/수량 요약, 캐릭터별 랜덤 대사 72개, 순차 입장, 야간 조명은 FE에서 처리한다. 대사 API·NPC 상태 저장·개인 주문의 월드 방송은 추가하지 않는다. 주문 문장은 승인된 `activeOrders[].items`를 그대로 사용한다.

서버는 시작 시 최대 세 활성 주문과 납품 후 교체 주문을 기존 제안 계약대로 발급하면 된다. FE가 표시 시점과 선택 가능 여부를 관리하므로 서버에 6초/0.7초 입장 타이머는 요청하지 않는다. 입장 시각까지 서버가 검증해야 하는 규칙은 이번 범위가 아니며 별도 합의가 필요하다.

`heatAssignment=FILL` 변경은 사용자가 BE 담당에게 이미 전달했다. 구현이 완료되면 반죽만 있는 동안 불 cursor/익힘이 진행되지 않고 FILL부터 가열되는지 실제 응답·공통 fixture로 확인한다. 기존 v5 작업을 중복 요청하는 것이 아니라 최종 계약과 완료 여부를 맞추기 위한 확인이다.

현재 상태·담당자 체크 목록·전달용 채팅 문구는 [BE 전달 요약](BE_전달_요약_2026-10-28.md)에 모았다. 해당 문서의 확인 기준은 로컬 체크아웃이며 다른 작업 브랜치나 개발 서버의 v5 배포 완료를 단정하지 않는다.
