# 공통 서버 시각·공원 진단

2026-10-27 FE 요청 기준. 코드/로컬 검사 범위이며 개발 서버 시간 측정·운영 성능 개선이 검증됐다는 뜻은 아니다.

## 공통 낮밤 시각

CONNECTED.payload.time과 WORLD_TIME_CHECK 응답은 같은 WorldClock을 사용한다. 인증 연결 후 맵 확인 전에도 시간은 읽을 수 있지만 채널 입장·맵 확인·경기 복구 권한은 바꾸지 않는다.

```json
{"requestId":"time-1","type":"WORLD_TIME_CHECK","payload":{}}
```

```json
{
  "requestId": "time-1",
  "type": "WORLD_TIME_STATE",
  "payload": {
    "serverNow": 1793062800000,
    "cycleEpochMs": 1767193200000,
    "cycleDurationMs": 1800000,
    "timeZone": "Asia/Seoul"
  }
}
```

serverNow는 현재 Unix ms, cycleEpochMs는 2026-01-01 00:00 KST의 고정 기준, 주기는 30분이다. 이미 Unix ms이므로 +9시간을 다시 더하지 않는다. 연결·재접속·탭 복귀 시 조회한다. 클라이언트는 요청 전후 단조 시계로 왕복시간을 재고 서버 시각+RTT/2를 수신 시점 추정값으로 사용할 수 있다. 네트워크 비대칭/브라우저 스케줄 지연 오차가 남는다. 단순히 Date.now와 비교해 기기 오차를 확정하지 않는다. 값 주입/추가 필드는 INVALID_PAYLOAD. 조회는 준비·턴·재접속 만료시각을 변경하지 않는다.

## 이동·점프·수영 현재 계약

- 이동 입력 최소 간격은 서버 설정 `ontop.world.movement.minimum-interval`(기본50ms). FE60ms는 기본 제한을 충족하지만 네트워크 묶음 도착 시 MOVE_TOO_FREQUENT 가능. 클라이언트가 제한을 변경할 수 없다.
- 마지막 유효 입력은250ms 후 만료. 서버 물리는30Hz, 지연 시 최대3스텝 보정, 월드 방송 준비는100ms 간격. 요청 ACK가 실제 물리 적분 완료·화면 도착 시각이라는 뜻은 아니다.
- 접지 또는 수영일 때만 jump를 큐에 둔다. 공중 점프는 승인하지 않는다. 기존 부력·충돌·수영 속도는 유지한다. 코요테 타임·착지 전 버퍼는 값/도입 미확정이며 이번 변경에 넣지 않았다.
- WS 좌표 필드·순번 의미는 유지한다. 새 좌표 생성시각/tick 공개 필드는 이번에 추가하지 않았으며 서버 내부 진단 tick과 입력seq를 구분한다.

## 낙하 복구

정상 공중 낙하는 물리 중력으로 현재 XZ 아래의 지면에 착지한다. 유효한 좌표가 지형을 관통했을 때는 현재 XZ 주변 실제 충돌 지지면을 ray/capsule 검사해 복구한다. 이전 고층 lastSafe로 무조건 되돌리지 않는다. 유효하지 않은 위치/근처 지지면 없음은 기존 lastSafe도 충돌 재검사하고, 실패하면 안전한 스폰 후보를 검사한다. 검사 실패를 임의 좌표로 우회하지 않는다.

WorldFallRecoveryTests는 높은 발판의 lastSafe를 만든 뒤 서버 전용 fixture로 지형 관통을 주입해 수정 전 높은 발판 복귀/수정 후 같은 XZ 지면 복구를 비교한다. 자연 낙하가 복구를 발생시키지 않는 것도 확인한다. 실제 개발 서버의 FE 신고가 반드시 같은 원인이라는 결론은 서비스 재현 로그 확인 전에는 내리지 않는다.

## 서버 진단 로그

다음 클래스의 DEBUG 로그를 진단할 환경에서 선택 활성화하면 된다. 이번 작업은 배포 설정을 바꾸지 않았다. 토큰·회원 ID·채팅/메모 본문을 진단 로그에 추가하지 않는다.

- WorldPhysics: 점프 입력seq/physics tick/QUEUED 또는 NOT_GROUNDED/접지·수영, 입력 만료 이동 정지, 복구 사유와 from/to/lastSafe/terrain/수직속도. 마지막 복구 한 건은 `lastRecovery`로만 내부 조회하며 공개 WS에 노출하지 않는다.
- WorldChannelRegistry: 채널 물리 초기 준비(cold)/추가 사용자 준비(warm)의 실제 경과 ms, tick/처리시간/스케줄 지연/방송 준비 건수. `lastTickTiming`은 마지막 내부 결과 한 건만 보관한다.
- TableHub: WS 등록 후 채널 join 준비 완료까지, join/물리 준비 완료 경과 ms. 사용자 조작/맵 확인 대기가 포함될 수 있다. 첫 WORLD_STATE 큐 등록 직전 경계이며 실제 네트워크 송신 완료·FE 렌더링·OAuth HTTP 시간은 포함하지 않는다.

로그인 HTTP→티켓→핸드셰이크→CONNECTED→채널 입장→첫 WORLD_STATE→화면 준비 전체를 비교하려면 FE와 같은 실행의 브라우저 타이밍을 함께 확인해야 한다. 기존 FE5.1→2.95초는 팀원 측 측정이며 이 서버 수정의 전후 성과로 사용하지 않는다. 실제 개발 서버 배포 후 기존 로그/브라우저로 연결 확인할 항목이다.
