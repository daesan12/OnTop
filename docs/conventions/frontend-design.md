# OnTop FE 디자인 컨벤션

> 6명이 게임을 병렬로 개발해도 하나의 공원 안에 있는 서비스처럼 보이고, 같은 방식으로 조작할 수 있게 만들기 위한 실무 가이드입니다.
>
> 작성일: 2026-10-30 · 기준: 로컬 `dev` 브랜치 `b80188d4`의 FE 소스 · 대상: FE 디자인을 처음 맡는 풀스택 개발자를 포함한 팀 전체

이 문서는 **기존 FE에서 확인한 디자인을 정리하고, 새 게임에 적용할 기본 규칙을 제안**합니다. 현재 모든 화면이 아래 규칙에 맞게 통일되어 있다는 뜻은 아닙니다. 이 문서를 작성하면서 앱 코드나 공통 스타일을 변경하지 않았습니다.

문서의 경로는 별도 설명이 없으면 `frontend/` 기준입니다. 파일 링크는 이 문서 위치에서 바로 열 수 있습니다. 다른 작업 브랜치에서는 파일이나 동작이 달라질 수 있으므로, 실제 작업 브랜치의 구현과 서버 계약도 함께 확인합니다.

## 1. 처음 작업하는 사람을 위한 시작 순서

처음부터 색과 배치를 모두 새로 정하지 않습니다. 내 게임과 비슷한 기존 화면을 하나 골라 기준으로 삼으면 결정할 일이 줄어듭니다.

1. **같은 작업 브랜치에서 기존 화면을 먼저 봅니다.** 로그인 → 공원 → 테이블 착석 → 게임 선택 → 준비 → 플레이 → 결과 순서로 확인합니다. 참가자와 관전자는 별도로 봅니다.
2. **화면을 목록으로 적습니다.** 준비, 내 차례, 상대 차례, 요청 중, 오류, 결과, 정산 대기까지 적습니다. 정상 플레이 화면만 만들면 연동할 때 배치를 다시 해야 합니다.
3. **참고 화면을 고릅니다.** 공원 메뉴는 HUD, 게임 선택은 태블릿, 결과는 종이 팝업, 실시간 조작은 기존 게임 HUD를 참고합니다.
4. **글부터 배치합니다.** 게임 이름, 현재 상태, 남은 시간, 다음 행동, 부가 설명 순서로 HTML을 만듭니다. 마지막에 그림과 장식을 더합니다.
5. **아래 기본값으로 스타일을 입힙니다.** 처음에는 색을 추가하거나 폰트를 설치하지 않습니다.
6. **작은 화면·긴 이름·요청 실패를 확인합니다.** 성공 화면과 같은 수준으로 확인합니다.
7. **PR에 화면과 검수 결과를 남깁니다.** 디자인 의도가 코드 작성자 머릿속에만 남지 않도록 합니다.

### 먼저 결정할 다섯 가지

| 질문 | 기본 답 |
| --- | --- |
| 사용자가 지금 꼭 봐야 하는 것은? | 내 차례 여부, 남은 시간, 해야 할 행동 |
| 가장 중요한 버튼은? | 지금 할 수 있는 주 행동 하나 |
| 3D 장면에서 가리면 안 되는 곳은? | 판, 손패, 조작 대상, 상대의 핵심 행동 |
| 요청에 시간이 걸리면? | 해당 행동을 잠그고 처리 중 문구 표시 |
| 오류가 나면 어떻게 돌아오나? | 입력·선택을 가능한 한 보존하고 재시도 또는 상태 확인 제공 |

## 2. 디자인 방향과 통일 범위

### 2.1 기존 FE의 세 가지 표현

| 영역 | 현재 표현 | 참고 구현 |
| --- | --- | --- |
| 로그인·공원 | 공원 배경, 명조 글꼴, 반투명한 어두운 HUD, 엽전색 강조 | [styles.css](../../frontend/src/styles.css), [park.css](../../frontend/src/park/park.css), [hud.css](../../frontend/src/features/parkMenus/hud.css) |
| 게임 선택·준비·결과 | 한지·크림색 바탕, 짙은 녹색 글자와 버튼, 황토·금색 테두리 | [tablet.css](../../frontend/src/features/tableLobby/tablet.css), [paperPopup.css](../../frontend/src/features/tableLobby/paperPopup.css) |
| 게임 플레이 | 실제 판·카드·주사위를 보여주는 3D 장면과 가장자리의 2D 조작 UI | [오목](../../frontend/src/game/omok/omokFocus.css), [원카드](../../frontend/src/game/onecard/onecard.css), [주사위](../../frontend/src/game/farkle/farkle.css) |

핵심은 **공원에서 함께 놀고, 종이에 적힌 안내를 읽고, 실제 놀이 도구를 조작하는 느낌**입니다. 장식보다 현재 상태와 다음 행동을 먼저 알아볼 수 있어야 합니다.

### 2.2 공통으로 맞출 것과 게임별로 정할 것

| 공통으로 맞출 것 | 게임별로 정할 수 있는 것 |
| --- | --- |
| 게임 선택·준비·시작·결과로 이어지는 흐름 | 판의 형태, 카드·말·주사위의 그림 |
| 글자 위계, 버튼 상태, 키보드 포커스 | 게임에 어울리는 녹색·갈색 계열의 보조 색감 |
| 처리 중·실패·연결 끊김·정산 대기 안내 | 손패, 점수판 등 게임 특성에 따른 세부 위치 |
| 팝업 열기·닫기·입력 차단·포커스 복원 | 게임의 재미를 위한 짧은 동작·효과음 |
| 참가자와 관전자에게 보여줄 정보의 경계 | 게임 고유의 단축키와 조작 도구 |
| 엽전 표기, 결과와 정산의 구분 | 판을 잘 볼 수 있는 게임별 카메라 |
| 관전자 상호작용의 공통 기본 요소: 채팅·핑 | 두 요소 외의 관전 기능·연출·배치 |

### 2.3 관전자 공통 요소는 채팅과 핑 두 가지

**팀에서 정한 신규 게임의 관전자 공통 요소는 ① 채팅, ② 게임 화면에서의 핑입니다.** 관전 화면을 만들 때 두 요소를 기본으로 포함합니다. 그 외 관전 요소는 게임 담당자가 자유롭게 정합니다.

| 공통 요소 | 목적 | 기본 동작 |
| --- | --- | --- |
| 채팅 | 관전 중 의견과 반응을 글로 전달 | 메시지를 입력·전송하고, 해당 경기의 채팅을 확인할 수 있음 |
| 핑 | 오목처럼 게임 화면의 특정 위치·대상을 짚어 전달 | 판이나 공개된 게임 요소에 짧게 표시되는 위치·대상 표시 |

이 결정은 **앞으로 적용할 팀 규칙**입니다. 현재 모든 게임에 두 기능이 이미 구현되어 있다는 뜻은 아닙니다. 기존 오목의 [OmokFeedback.tsx](../../frontend/src/game/omok/OmokFeedback.tsx)와 [spectatorEvents.ts](../../frontend/src/game/omok/spectatorEvents.ts)를 참고하되, 오목 전용 좌표·이벤트를 다른 게임에 그대로 복사하지 않습니다.

두 요소를 설계할 때 확인할 사항:

- **채팅:** 입력 중에는 이동·게임 단축키가 실행되지 않게 하고, 전송 중·실패 상태를 안내합니다. 현재 경기의 대화와 다른 경기·공원 주변 채팅을 혼동하지 않게 표시합니다.
- **핑:** 게임의 공개된 위치나 대상을 가리킵니다. 예를 들어 오목은 교차점, 다른 게임은 공개된 판의 칸이나 오브젝트를 대상으로 삼을 수 있습니다. 핑을 보내는 조작이 착수·카드 내기 같은 실제 게임 행동으로 처리되면 안 됩니다.
- **표시:** 채팅과 핑이 판·카드·주 버튼을 지속적으로 가리지 않게 합니다. 핑은 실제 게임 말이나 선택 표시와 구별하고, 시간이 지나면 사라지게 합니다.
- **경기 구분:** 다른 경기의 이벤트나 이미 지난 판 상태의 핑이 현재 화면에 남지 않게 합니다. 전송 권한·공유 대상·빈도 제한은 실제 서버 계약과 맞춥니다.

채팅의 구체적인 위치·표시 방식, 핑의 모양·색·지속시간·입력 방법은 게임 특성에 맞춰 정합니다. 채팅을 누가 읽을 수 있는지와 핑을 누구에게 보여주는지도 게임 UI 명세에 기록합니다. 이 문서에서 오목의 세부 값을 모든 게임의 고정값으로 정하지 않습니다.

**그 외는 담당자 자율 영역입니다.** 예를 들어 응원 이모트, 리액션, 관전 카메라 전환, 게임 고유의 관전 연출은 필요에 따라 추가하거나 생략할 수 있습니다. 이를 새 게임의 공통 필수 기능으로 늘리지 않습니다. 자율 요소에도 기존의 가독성·입력 충돌 방지·비공개 정보 보호 원칙은 적용합니다.

### 2.4 신규 화면에서 피할 것

- 의미 없이 형광색·강한 원색·빛나는 테두리를 추가하는 것.
- 한 화면에 강조 버튼을 여러 개 두거나 모든 카드에 진한 그림자를 넣는 것.
- 설명·에러·버튼까지 모두 배경 이미지에 그려 넣는 것. 읽고 눌러야 할 정보는 HTML로 만듭니다.
- 공원 HUD, 결과 팝업, 설명서를 게임마다 복제하는 것.
- 기존 게임의 버튼·HUD를 같은 모습으로 바꾸기 위해 담당 범위 밖의 CSS를 일괄 수정하는 것.

## 3. 색상·글꼴·크기·간격

### 3.1 기존 코드에서 확인한 색상

아래 값은 실제 소스에 있는 **대표값**입니다. 하나의 전역 팔레트가 구현되어 있는 것은 아닙니다. 같은 기능을 수정할 때는 해당 파일의 기존 변수를 우선 사용합니다.

| 용도 | 대표값 | 출처 / 사용 방법 |
| --- | --- | --- |
| 기본 잉크색 | `#27372b` | `styles.css`의 기본 글자 |
| 한지 바탕 | `#f5ebd3` | `tablet.css`, `paperPopup.css`; 텍스처 로딩 실패 시에도 바탕 유지 |
| 태블릿 잉크색 | `#123b2a` | `--tablet-ink` |
| 태블릿 금색 / 테두리 | `#bf903d` / `#baa171` | `--tablet-gold`, `--tablet-border` |
| 결과 잉크색 | `#163d29` | `--paper-ink` |
| 결과 주 버튼 | `#2b5035` → `#123321` | `paper-primary`의 세로 그라데이션 |
| 공원 HUD 바탕 | `rgba(41, 38, 32, 0.5)` | `--hud-glass`; 드롭다운은 `0.72` |
| 공원 HUD 글자 / 강조 | `#f7f1e5` / `#e8b451` | 밝은 글자와 엽전·선택 강조 |
| 원카드 바탕 / 강조 | `#fbf5e7` / `#edce76` | `--oc-paper`, `--oc-gold` |
| 주사위 글자 / 패널 | `#f5ead5` / `#271e16ed` | `--dice-ink`, `--dice-panel` |
| 밝은 종이 위 오류 | `#943b2e` | `paper-error` |
| 어두운 판 위 긴급 안내 | `#ffb889` | 오목 타이머의 긴급 상태 |

사용 규칙:

- **색은 역할로 고릅니다.** 바탕, 본문, 보조 글자, 선택, 위험 중 어떤 역할인지 먼저 정합니다.
- 한 패널 안에서 비슷한 녹색을 여러 개 만들지 않습니다. 해당 게임의 잉크색 하나를 기준으로 씁니다.
- 선택은 색만 바꾸지 말고 테두리·체크·`선택됨` 같은 표시를 함께 사용합니다.
- 오류는 빨간색만 표시하지 말고 원인과 다음 행동을 적습니다.
- 반투명 패널은 낮·밤, 밝은 바닥·어두운 나무 앞에서 모두 확인합니다. 글자가 묻히면 불투명도를 높입니다.
- 새 글자와 바탕 조합은 명암비를 확인합니다. 신규 UI의 권장 검수 기준은 일반 글자 `4.5:1`, 큰 글자 `3:1` 이상입니다. 이 표의 모든 색 조합이 그 기준을 충족한다고 보장하는 것은 아닙니다.

### 3.2 글꼴

현재 [styles.css](../../frontend/src/styles.css)는 `BusanDandiMyeongjo`의 **300·500·700** 굵기를 로드하고 `font-synthesis: none`을 사용합니다. 태블릿과 게임 조작 UI에는 `Malgun Gothic` 계열도 사용합니다.

| 쓰임 | 새 화면의 기본 선택 |
| --- | --- |
| 브랜드, 안내 제목, 결과 제목 | `'BusanDandiMyeongjo', serif` |
| 규칙 설명, 입력, 게임 조작 패널 | `'Malgun Gothic', system-ui, sans-serif` |
| 점수·남은 시간 | 주변 글꼴을 유지하고 `font-variant-numeric: tabular-nums` 적용 |
| 버튼 | `font: inherit`로 패널의 글꼴을 따름 |

기존 파일에는 600·650·900 등의 굵기도 있습니다. 새 명조 텍스트는 로드된 300·500·700 안에서 선택합니다. 글자만 진하게 만들기 위해 별도 폰트를 추가하지 않습니다. 시스템 글꼴은 OS별 차이가 있으므로 제목 너비를 글자 수로 계산하지 않습니다.

### 3.3 신규 DOM UI의 권장 크기

다음은 **새 화면을 위한 기본값**이며 기존 모든 화면의 실측값은 아닙니다. 태블릿의 1280×800 설계 좌표와 아래 CSS 화면 픽셀을 혼동하지 않습니다.

| 정보 | 기본 크기 | 굵기 / 행간 |
| --- | --- | --- |
| 일반 팝업 제목 | 24–32px | 700 / 1.3 |
| 결과의 핵심 제목 | 40–60px | 명조 700 / 1.2; 작은 화면에서 축소 |
| 패널 소제목 | 18–20px | 700 / 1.4 |
| 본문·주 버튼 | 16px | 500 / 1.5 |
| 보조 설명·상태 | 14px | 500 / 1.5 |
| 짧은 배지·단축키 | 12px 이상 | 부가 정보에만 사용 |
| 핵심 점수·타이머 | 28–42px | 숫자 폭 고정 / 1.2 |

기존 HUD에는 10–13px 보조 글자가 있습니다. 새 핵심 안내를 그 크기에 맞춰 작게 만들지 않습니다. 화면을 줄였을 때도 읽어야 할 본문은 가급적 14px 이상을 유지하고, 버튼과 본문부터 보존합니다.

### 3.4 간격·둥글기·그림자

신규 UI는 다음 권장 단위를 조합합니다. 전역 CSS 토큰은 아직 없습니다.

| 항목 | 기본값 | 예 |
| --- | --- | --- |
| 간격 | 4 / 8 / 12 / 16 / 24 / 32px | 아이콘과 글자 8, 버튼 사이 8–12, 구역 사이 24 |
| 패널 안쪽 여백 | 24–32px | 좁은 화면에서는 16–20px |
| 화면 가장자리 | 20–24px | 좁은 화면에서는 12–16px |
| 입력·작은 버튼 둥글기 | 8–12px | 버튼은 같은 구역에서 통일 |
| 카드·패널 둥글기 | 12–16px | 종이 결과 팝업은 기존 15px 참고 |
| 공원 확인창 둥글기 | 기존 24px | `park-menu-dialog`를 재사용 |
| 테두리 | 기본 1px, 선택 2–3px | 선택 전후 크기가 흔들리지 않게 내부 여백 보정 |
| 그림자 | 패널 전체에 한 번 | 내부 모든 요소에 반복하지 않음 |

`margin`은 요소 바깥 간격, `padding`은 안쪽 여백입니다. 나란한 항목은 각각 `margin`을 주기보다 부모의 `gap`으로 간격을 정하면 수정하기 쉽습니다.

## 4. 화면 배치와 작은 화면 대응

### 4.1 게임 HUD의 기본 읽기 순서

아래는 새 게임의 권장 배치입니다. 판 모양 때문에 달라질 수 있지만 정보의 중요도는 유지합니다.

```text
┌──────────────────────────────────────────┐
│ 참가자·점수       차례·시간       부가 메뉴 │
│                                          │
│           실제 게임 판 / 3D 장면           │
│        클릭할 곳과 상대 행동을 비워 둠      │
│                                          │
│ 채팅/기록       내 상태·손패               │
│                지금 할 행동       설명/기권│
└──────────────────────────────────────────┘
```

- 중앙의 판을 가장 크게 남깁니다. 점수판이나 설명서가 조작 대상을 계속 가리지 않게 합니다.
- 타이머와 차례는 가까이 둡니다. 현재 참가자를 테두리와 `내 차례` 문구로 함께 표시합니다.
- 내 손패·선택 정보·확정 버튼은 가까이 둡니다. 선택 후 화면 반대편까지 시선을 옮기게 하지 않습니다.
- 설명·관전 종료·기권은 주 행동과 구분합니다. 실수로 눌러 손실이 생기는 버튼은 붙여 놓지 않습니다.
- 채팅·설명서·결과창을 각각 띄워 보고 주요 버튼과 겹치는지 확인합니다.

### 4.2 공원 HUD와 태블릿의 기존 배율

- [ParkPage.tsx](../../frontend/src/park/ParkPage.tsx)의 `getHudScale()`은 너비가 900px을 넘으면 `min(1, 너비/1920, 높이/1080)`을 사용합니다. 900px 이하는 배율 1입니다.
- `--park-ui-scale`과 `--park-edge`는 이 공원 화면에서 내려줍니다. 공원 HUD에 붙는 UI는 기존 배치 방식을 따릅니다.
- [태블릿](../../frontend/src/features/tableLobby/TabletLobby.tsx)은 1280×800 기준 화면을 [tabletProjection.ts](../../frontend/src/features/tableLobby/tabletProjection.ts)로 투영합니다. `tablet.css`의 작은 화면 분기도 함께 봅니다.
- **새 일반 팝업이나 새 게임 전체에 이 배율을 다시 곱하지 않습니다.** 이미 축소된 부모 안에서 또 축소하면 글자와 클릭 영역이 지나치게 작아집니다.
- `transform`된 부모 안의 `position: fixed`는 기대와 다르게 배치될 수 있습니다. 화면 전체 팝업이 필요하면 기존 `MenuDialog`의 portal 방식을 참고합니다.

### 4.3 반응형 규칙

기존 코드에는 600·700·799·800·900px 등 서로 다른 분기점이 있습니다. 문서로 하나의 전역 분기점이 이미 적용되었다고 가정하지 않습니다. 기존 화면을 수정하면 그 화면의 분기를 유지하고, 신규 화면은 아래 원칙으로 조정합니다.

1. 너비를 줄이기 전에 줄바꿈·세로 배치를 허용합니다.
2. 낮은 화면에서는 큰 제목과 장식부터 줄입니다. 주 버튼을 숨기지 않습니다.
3. 패널은 `max-height`와 내부 스크롤을 둡니다. 마지막 버튼까지 접근할 수 있어야 합니다.
4. 카드·플렉스 자식에는 필요 시 `min-width: 0`, 한국어 설명에는 `word-break: keep-all`, 긴 닉네임에는 `overflow-wrap: anywhere`를 사용합니다.
5. 카드나 판의 비율은 `aspect-ratio`로 유지합니다. 손패를 맞추기 위해 이미지 자체를 찌그러뜨리지 않습니다.

기본 패널 예시:

```css
.newgame-panel {
  width: min(480px, calc(100% - 32px));
  max-height: calc(100dvh - 32px);
  overflow-y: auto;
  min-width: 0;
}
```

권장 검수 크기는 `1920×1080`, `1366×768`, `1280×720`, 작은 가로 화면 `800×600`, 좁은 세로 화면 `390×844`입니다. 이는 **검수 제안**이며 모바일 전체 플레이 지원을 보장하는 목록은 아닙니다. 지원하지 않는 화면에서는 조작 가능한 척 잘린 UI를 보여주기보다 지원 범위와 필요한 화면 조건을 안내합니다. 지원 범위는 팀에서 게임별로 명시합니다.

### 4.4 레이어와 클릭 통과

기존에 확인한 `z-index` 예시는 다음과 같습니다. 부모의 stacking context가 다르면 숫자만으로 앞뒤를 비교할 수 없습니다.

| 구현 | 현재 값 |
| --- | --- |
| 공통 `.prototype-game` | 4 |
| 원카드 게임 HUD | 5 |
| 공원 빠른 메뉴 틀 / 버튼 | 11 / 12 |
| 태블릿 | 38 |
| 공원 메뉴 배경막 | 40 |
| 종이 결과 팝업 배경막 | 65 |

이 표는 새 전역 레이어 체계를 선언한 것이 아닙니다. 설명서와 원카드 기권창의 native `dialog.showModal()`은 브라우저 **top layer**에 있으므로 일반 `z-index`와도 다릅니다.

- 앞에 안 나온다고 `z-index: 99999`를 추가하지 않습니다. 부모의 `transform`, `opacity`, `isolation`, portal 여부부터 확인합니다.
- 전체 화면 HUD의 빈 부분은 `pointer-events: none`, 실제 버튼·카드·조작 패널은 `pointer-events: auto`를 사용합니다.
- 중앙 빈 공간에 투명한 클릭 방지 박스가 남지 않게 합니다.
- 반대로 모달이 열린 동안 뒤의 판을 클릭하거나 이동할 수 있으면 안 됩니다.

## 5. 버튼·입력·카드·팝업

### 5.1 버튼

| 종류 | 사용 예 | 표현 |
| --- | --- | --- |
| 주 행동 | 준비하기, 선택한 카드 내기, 점수 확정 | 한 구역에 가장 강한 강조 하나 |
| 보조 행동 | 설명서, 취소, 닫기 | 종이색 또는 테두리 버튼 |
| 선택 토글 | 인원, 관전 시점, 카드 선택 | `aria-pressed` + 테두리/선택 표시 |
| 위험 행동 | 기권 확정, 회원 탈퇴 | 경고 문구와 확인 단계 |
| 아이콘 버튼 | 닫기, 메뉴 | `aria-label`과 충분한 클릭 영역 |

새 주요 버튼은 높이 48px을 기본으로 하고 클릭 영역은 가급적 44×44px 이상 확보합니다. 그림이 20px이어도 버튼 영역은 더 크게 잡습니다. 작은 게임판 칸처럼 밀도가 필요한 조작은 확대·키보드 대체 등 해당 게임에 맞는 방법을 마련합니다.

모든 버튼은 아래 상태를 확인합니다.

| 상태 | 표현과 동작 |
| --- | --- |
| 기본 | 역할이 명확한 이름과 배경 |
| hover | 배경·테두리를 조금 변경; disabled에는 적용하지 않음 |
| active | 눌림을 약하게 표현; 배치가 밀릴 만큼 움직이지 않음 |
| focus-visible | 키보드 포커스 테두리 표시; 배경과 구별되는 색 사용 |
| disabled | 실제 `disabled` 사용 + 근처에 사유 표시 |
| 요청 중 | `처리 중…` 등 동사 포함 안내 + 중복 클릭 차단 |

클릭 가능한 것은 `<button type="button">`, 이동 링크는 `<a>`를 씁니다. `<div onClick>`만으로 버튼을 만들지 않습니다. 제출 버튼만 `type="submit"`을 사용합니다.

### 5.2 입력

- 입력 이름은 `<label>`로 연결합니다. placeholder는 예시이며 이름을 대신하지 않습니다.
- 단위와 조건은 입력 전에 보여줍니다. 예: `참가비 (엽전)` / `1인당 참가비를 입력해 주세요.`
- 숫자를 표시할 때는 `1,000 엽전`, 점수는 `1,000점`, 시간은 `30초`처럼 읽히게 합니다. API에 보내는 값은 별도로 검증합니다.
- 빈값·잘못된 값·최솟값/최댓값·서버 거절을 확인합니다. 실제 범위는 계약을 사용하고 문서 예시 숫자를 정책으로 복사하지 않습니다.
- 오류는 입력 가까이에 두고 `aria-invalid`, `aria-describedby`로 연결합니다.
- 실패 후 내용을 무조건 지우지 않습니다. 선택과 입력이 유효하면 유지합니다.
- 비활성 이유가 `잔액 부족`, `방장만 변경 가능`, `연결 확인 중` 중 무엇인지 써 줍니다.

### 5.3 게임 선택 카드와 참가자 카드

- 게임 카드는 같은 비율의 이미지, 게임명, 인원, 한 줄 설명 순서로 구성합니다.
- 선택 카드는 초록 테두리와 선택 상태를 함께 보여줍니다. 이미지는 클릭 가능해 보이는데 실제로 제목만 눌리는 구조를 피합니다.
- 제작 중인 게임은 `준비 중`을 표시하고 실제 진입은 막습니다.
- 참가자 카드의 `나`, `방장`, `준비 완료`, `현재 차례`는 각각 의미가 다릅니다. 한 가지 색으로 뭉뚱그리지 않습니다.
- 빈 좌석은 `참가자를 기다리고 있어요`처럼 표시합니다. 없는 사람의 이름이나 점수를 채워 넣지 않습니다.
- 긴 이름으로 점수나 버튼이 밀리지 않게 합니다. 목록에서 말줄임을 썼다면 프로필 등 전체 이름을 확인할 경로를 제공합니다.

### 5.4 팝업과 설명서

새 팝업을 만들기 전에 기존 컴포넌트를 확인합니다.

| 목적 | 우선 참고할 구현 | 주의 |
| --- | --- | --- |
| 공원 계정·일반 확인 | [MenuDialog.tsx](../../frontend/src/features/parkMenus/MenuDialog.tsx) | `label`, `className`, `onClose`, `children`; 메뉴 CSS 필요 |
| 종이 결과·랭킹 | [PaperPopup.tsx](../../frontend/src/features/tableLobby/PaperPopup.tsx) | `title`, `label`, `onClose`, `children`; 결과와 정산 로직은 별도 |
| 게임 설명서 | [manualState.ts](../../frontend/src/features/manual/manualState.ts), [ManualHost.tsx](../../frontend/src/features/manual/ManualHost.tsx) | 기존 `openManual(...)` 경로 사용, 게임마다 Host를 추가하지 않음 |
| 경기 기권 | [OneCardForfeitDialog.tsx](../../frontend/src/game/onecard/OneCardForfeitDialog.tsx), [OmokSurrender.tsx](../../frontend/src/game/OmokSurrender.tsx) | 공통 기권 상태·복구 흐름까지 확인 |

두 팝업 컴포넌트는 범용 디자인 시스템의 완성된 모달 API가 아닙니다. 지원하는 포커스 대상과 키 처리 방식이 다르므로, 링크·select 등 새 조작을 넣으면 실제 Tab 이동도 확인합니다.

모달 검수 기준:

1. 열릴 때 내용이나 첫 조작으로 포커스를 옮깁니다. 위험 확인창은 안전한 `계속 플레이` / `취소` 쪽을 먼저 선택합니다.
2. Tab과 Shift+Tab이 뒤의 공원으로 빠지지 않게 합니다.
3. Esc는 최상단 창의 닫기 동작을 합니다. 게임의 기권·컵 내려놓기와 동시에 실행되지 않아야 합니다.
4. 닫으면 원래 버튼으로 포커스를 돌립니다. 버튼이 없어졌다면 현재 화면의 적절한 조작으로 이동합니다.
5. 배경 클릭으로 위험 행동을 확정하지 않습니다. 배경 클릭으로 닫을지는 창의 성격에 맞게 정합니다.
6. 닫기는 **창 닫기**입니다. 기권·관전 종료·테이블 퇴장을 뜻하도록 몰래 연결하지 않습니다.

`aria-modal="true"`만으로 뒤의 이동과 클릭이 차단되지는 않습니다. [inputOwnership.ts](../../frontend/src/world/inputOwnership.ts)의 입력 소유권과 기존 modal 동작을 함께 사용합니다. 새 창을 열 때 `clearRoamingInput()`으로 눌린 이동 입력을 정리하고, 필요하면 pointer lock을 해제합니다. 닫을 때 다른 패널의 플래그까지 일괄 초기화하지 않습니다.

## 6. 게임 상태와 사용자 안내

다음 표는 **화면 설계에 필요한 상태 목록**입니다. 서버 enum을 새로 정의하는 표가 아니며, 실제 상태 이름과 전환 조건은 게임 계약을 따릅니다.

| 상황 | 사용자에게 보여줄 것 | 조작 원칙 |
| --- | --- | --- |
| 불러오는 중 | 무엇을 기다리는지: `참가자 정보를 불러오고 있어요.` | 사용할 수 없는 행동만 잠금 |
| 게임 미선택 | 게임 선택 안내 | 권한에 맞는 선택 UI |
| 참가자 부족 | 현재 인원 / 필요한 인원 | 시작 불가 이유 표시 |
| 준비 전 | 참가비, 인원, 내 준비 여부 | 준비하기 / 허용된 설정 변경 |
| 준비 완료 | `준비 완료`, 다른 참가자의 상태 | 허용된 준비 취소 제공 |
| 시작 요청 중 | `경기 시작을 확인하고 있어요.` | 중복 시작·설정 변경 차단 |
| 내 차례 | 가능한 행동, 남은 시간 | 합법적인 조작만 활성화 |
| 상대 차례 | 현재 참가자와 기다리는 이유 | 내 게임 행동 잠금, 허용된 설명·관전 조작 유지 |
| 행동 반영 중 | `카드를 내고 있어요.` 등 | 같은 행동 연속 전송 차단 |
| 잘못된 선택 | 해당 게임의 거절 이유 | 서버 상태를 유지하고 다시 선택 |
| 연결 끊김 / 결과 불명 | 연결 상태와 확인 방법 | 처리 완료로 가정하지 않고 상태 확인 |
| 경기 종료 | 승리·패배·무승부·기권·무효 등 실제 결과 | 종료된 판에 추가 입력 금지 |
| 정산 대기 | `경기는 끝났어요. 정산 결과를 확인하고 있어요.` | 확정되지 않은 엽전 증가 연출 금지 |
| 정산 완료 | 서버가 확정한 내 증감과 결과 | 허용된 다음 판 / 테이블 조작 제공 |
| 관전 중 | 관전 표시, 공개 점수·공개 행동, 공통 채팅·핑 | 개인 손패·비밀 눈·개인 정산 숨김; 채팅·핑과 실제 게임 행동 구분 |

### 6.1 FE가 화면을 위해 만들어도 되는 상태

선택한 카드, 열린 탭, 도움말 표시, 애니메이션 진행률 등은 로컬 UI 상태입니다. 승패, 합법 행동 판정, 확정 점수, 엽전 정산, 서버의 참가 권한은 서버 상태를 기준으로 합니다.

- 타이머는 서버의 마감 시각과 기존 시간 보정 방식을 사용합니다. 매초 감소하는 로컬 숫자를 경기 판정으로 쓰지 않습니다.
- 0초가 됐다는 이유로 FE가 승패를 확정하지 않습니다. 필요한 경우 `서버 판정 확인 중`을 표시합니다.
- 연출이 끝났다는 이유로 다음 차례를 열지 않습니다.
- 요청 타임아웃은 거절과 다릅니다. 이미 처리됐을 수 있으므로 무조건 새 요청을 보내지 않습니다. 기존 복구·동일 요청 확인 경로를 따릅니다.
- 테스트용 상태 대역은 실제 연동과 구분합니다. PR에 어떤 검증이 실제 서버였는지 적습니다.

### 6.2 결과·엽전 표시

결과에는 `게임 이름 → 결과 제목 → 참가자별 결과/점수 → 내 엽전 증감과 정산 상태 → 다음 행동` 순서를 기본으로 합니다.

- `승리`와 `정산 완료`는 다른 정보입니다. 승리 결과가 먼저 와도 정산은 기다릴 수 있습니다.
- 참가비, 총 판돈, 내 순증감, 현재 잔액은 각각 이름을 붙입니다. `+100`만 크게 쓰지 않습니다.
- 관전자에게 참가자의 개인 지갑 정보나 숨겨진 정보를 보여주지 않습니다.
- 결과창을 닫았다 다시 열어도 보상 수령을 중복 처리하거나 보상 연출을 반복하지 않습니다.
- 기존 [RewardCoinFlight.tsx](../../frontend/src/features/wallet/RewardCoinFlight.tsx)는 서버가 확정한 양수 보상과 수령 식별자를 기준으로 연출합니다. 새 게임도 지갑 값을 UI에서 임의로 더하지 않습니다.
- 화면 표시 단위는 신규 사용자 문구에서 **엽전**을 기본으로 합니다. API의 `coin`·`betAmount` 필드 이름은 바꾸지 않습니다. 기존의 `코인` 표기는 해당 기능을 정리할 때 범위를 명시해 조정합니다.

## 7. 문구·아이콘·이미지·움직임

### 7.1 문구

설명은 `~해요`를 기본으로 쓰고, 버튼은 짧은 행동 이름을 씁니다. 위험 확인의 제목은 `기권하시겠습니까?`처럼 명확하게 적을 수 있습니다.

| 피할 표현 | 권장 예 |
| --- | --- |
| 확인 / OK만 있는 버튼 | 준비하기 / 카드 내기 / 관전 종료 |
| 처리 실패 | 카드를 내지 못했어요. 경기 상태를 확인한 뒤 다시 시도해 주세요. |
| 버튼이 회색이기만 함 | 다른 참가자가 준비 중이에요. |
| 에러 코드만 노출 | 연결이 끊겼어요. 다시 연결한 뒤 경기 상태를 확인해 주세요. |
| 아직 확정되지 않은 `보상 지급 완료` | 정산 결과를 확인하고 있어요. |
| `시간 종료`만 표시 | 시간이 끝났어요. 서버 판정을 기다리고 있어요. |

위 문구는 상황에 맞춰 조정합니다. 실제로 다시 시도할 수 없는 행동에 `다시 시도`를 안내하지 않습니다. 내부 필드명·스택 추적·개발 모드 이름은 일반 사용자 문구에 넣지 않습니다.

오류는 해당 행동 가까이에 표시하고, 계속 남아야 할 오류를 짧은 토스트만으로 끝내지 않습니다. 처리 중 안내는 `role="status"`, 즉시 알아야 하는 오류는 필요 시 `role="alert"`를 사용합니다. 매초 바뀌는 타이머를 alert로 읽게 하지 않습니다.

### 7.2 아이콘·이미지

- 먼저 같은 기능의 기존 SVG·이미지를 찾습니다. 엽전·닫기·설명서 아이콘을 게임마다 새로 만들지 않습니다.
- 신규 조작 아이콘은 20–24px 정도를 기본으로 하고 선 굵기와 색을 주변 아이콘에 맞춥니다.
- 장식 이미지는 `alt=""` 또는 `aria-hidden="true"`, 의미가 있는 이미지는 그 역할을 설명하는 대체 텍스트를 둡니다.
- 카드의 숫자·무늬, 주사위 눈처럼 정보가 있는 그림은 배경 이미지에만 의존하지 않습니다. 접근 가능한 이름이나 HTML 정보도 제공합니다.
- 기존 게임 선택 그림은 `public/art/tablet/`, 카드 원본은 `public/art/onecard/` 등에 있습니다. 다음은 기존 게임 선택 아트의 예입니다.

![공원의 나무 테이블 위 원카드: 기존 게임 선택 화면의 아트 예시](../../frontend/public/art/tablet/onecard-v2.webp)

- 새 정적 자산은 게임별 폴더에 넣고 의미 있는 영문 소문자 이름을 씁니다. 예: `public/art/newgame/cover.webp`.
- 코드가 import하는 자산과 `public/` 경로 자산을 구분합니다. `public/art/...` 파일의 브라우저 URL은 `/art/...`입니다.
- 원본 출처·라이선스·생성/편집 기록을 남깁니다. 기존 [ASSET_CREDITS.md](../../frontend/docs/ASSET_CREDITS.md)와 자산 폴더의 `SOURCE.md`·manifest 방식을 참고합니다.
- 썸네일에 과도하게 큰 원본을 그대로 로드하지 않습니다. 현재 표시 크기와 확대 용도를 기준으로 크기·용량을 확인합니다.
- 3D 재질·모델·카메라를 UI 문제 해결을 위해 임의로 바꾸지 않습니다. 씬 변경은 해당 게임·공원 담당 범위와 성능 영향을 함께 검토합니다.

### 7.3 움직임·효과음

- 버튼 hover/눌림은 약 150ms, 패널 진입은 약 200–250ms를 신규 UI의 기본으로 합니다. 실제 카드·주사위 연출은 게임별 동작을 따릅니다.
- 매번 등장하는 설명이나 점수에 긴 애니메이션을 넣지 않습니다.
- `prefers-reduced-motion: reduce`에서는 장식 이동·흔들림·회전을 줄이거나 끕니다. 선택·승패·오류 자체는 텍스트로 계속 전달합니다.
- 효과음만으로 내 차례나 실패를 알리지 않습니다. 음소거에서도 플레이할 수 있어야 합니다.
- 매 프레임 React 전체 상태를 갱신하는 연출을 만들지 않습니다. 기존 게임의 렌더링·오디오 패턴을 먼저 확인합니다.
- 이벤트 재수신·창 재열기로 효과가 중복 재생되지 않는지 확인합니다.

## 8. 코드와 CSS 작성 규칙

### 8.1 실제 기술과 파일 경계

현재 FE는 React + TypeScript + Vite, React Three Fiber/Three.js, Zustand, 일반 CSS를 사용합니다. Tailwind나 shadcn의 전역 디자인 시스템을 전제로 작성하지 않습니다.

신규 게임의 권장 구조는 다음과 같습니다. **아래 `newgame`은 예시이며 실제 등록된 게임이 아닙니다.**

```text
src/game/newgame/
  NewGamePanel.tsx       # 참가자·관전자 화면 연결
  NewGameActions.tsx     # 조작 UI
  NewGameBoard.tsx       # 해당 게임의 3D 판이 필요할 때
  presentation.ts       # 서버 상태 → 표시 문구/표시값
  newgame.css            # 이 게임에만 적용되는 스타일
tests/unit/newgame*.test.ts
tests/e2e/newgame*.spec.ts
docs/NEWGAME_UI.md
```

폴더를 꼭 모두 만들 필요는 없습니다. 작은 UI를 억지로 분리하지 않습니다. 1인 시설 미니게임은 기존 `src/features/bungeoppang/`처럼 `features/<기능>/`가 더 적합할 수 있습니다. 공통 테이블 게임의 등록 흐름과 시설 게임의 진입 흐름을 구분합니다.

### 8.2 CSS 범위

현재 일반 CSS는 파일을 import해도 전역에 적용됩니다. **파일을 나누는 것만으로 스타일이 격리되지 않습니다.**

```css
/* 피할 예: 다른 게임과 공원 메뉴까지 바뀝니다. */
button { background: green; }
.card { width: 200px; }
.mini-status { bottom: 100px; }

/* 권장 예: 내 게임의 루트와 이름을 사용합니다. */
.newgame-hud .newgame-actions button { min-height: 48px; }
.newgame-hud .newgame-card { width: 124px; }
.newgame-hud .newgame-status { bottom: 100px; }
```

- 새 클래스는 `<게임명>-<역할>` 형태로 씁니다. 상태는 `data-*`, `aria-pressed`, `disabled` 등 실제 의미와 연결합니다.
- 게임의 커스텀 속성도 루트에 한정합니다. 예: `--newgame-ink`, `--newgame-accent`.
- `styles.css`, `park.css`, `prototypeTable.css`에 내 게임 규칙을 계속 덧붙이지 않습니다. 기존 공통 선택자와 충돌하면 필요한 부분만 게임 루트 안에서 명시적으로 조정합니다.
- CSS import 순서와 파일 아래쪽의 재정의도 확인합니다. 앞부분의 값만 보고 최종 화면 값을 단정하지 않습니다.
- `!important`로 덮기 전에 선택자 범위와 기존 규칙을 확인합니다.
- portal로 `document.body`에 붙인 팝업은 `.newgame-hud`의 자식이 아닙니다. 클래스와 필요한 변수를 팝업 루트에 직접 제공하거나 기존 팝업 스타일을 사용합니다.

### 8.3 상태·조작·표시의 경계

- 화면에서 선택한 카드와 서버가 실제로 낸 카드를 별도 상태로 다룹니다.
- 서버 요청은 기존 runtime/게임 action 경로를 사용합니다. 버튼 컴포넌트 안에서 별도 소켓 연결을 만들지 않습니다.
- 점수·차례·준비 상태를 다른 화면에서 사용할 수 있도록 UI용 임시 값으로 공통 store를 덮어쓰지 않습니다.
- 새 단축키는 기존 키와 겹치는지 확인하고 [inputOwnership.ts](../../frontend/src/world/inputOwnership.ts)의 `panelOwnsKeys()`, `textInputOwnsKeys(...)` 등 기존 gate를 따릅니다.
- 한국어 조합 중(`isComposing`, 기존 코드의 229 처리), 키 반복, 입력창 포커스, 열린 모달에서는 게임 단축키를 실행하지 않게 합니다.
- 내 화면을 닫는다고 다른 게임·패널의 입력 잠금을 해제하지 않습니다. 이벤트 리스너·타이머는 unmount 시 정리합니다.

## 9. 따라 만들 수 있는 최소 예시

아래는 **새 게임의 어두운 조작 패널을 만드는 예시**입니다. 공통 컴포넌트로 이미 설치된 코드가 아니며, 파일을 생성하고 해당 게임 화면에 연결해야 보입니다. `onSubmit`은 상위에서 실제 runtime 호출을 연결하고, `busy`와 오류도 상위 상태로 내려줍니다. 이 예시만으로 게임 등록·중복 요청 방지·서버 복구가 완성되지는 않습니다.

```tsx
// 예: src/game/newgame/NewGameActions.tsx
import './newgame.css'

type Props = {
  isMyTurn: boolean
  busy: boolean
  connected: boolean
  error: string
  onSubmit: () => void
}

export function NewGameActions({
  isMyTurn, busy, connected, error, onSubmit,
}: Props) {
  const disabled = !connected || !isMyTurn || busy
  const status = !connected
    ? '연결을 확인하고 있어요.'
    : busy
      ? '행동을 처리하고 있어요.'
      : isMyTurn
        ? '내 차례예요. 행동을 선택해 주세요.'
        : '다른 참가자의 차례예요.'

  return (
    <section className="newgame-hud" aria-label="새 게임 조작">
      <div className="newgame-actions" aria-busy={busy}>
        <h2 className="newgame-title">내 행동</h2>
        <p id="newgame-action-status" role="status">{status}</p>
        <button
          type="button"
          className="newgame-primary"
          disabled={disabled}
          aria-describedby="newgame-action-status"
          onClick={onSubmit}
        >
          {busy ? '처리 중…' : '행동 확정'}
        </button>
      </div>
      {error && <p className="newgame-error" role="alert">{error}</p>}
    </section>
  )
}
```

위 ID는 한 화면에 이 패널 하나만 있다는 전제입니다. 여러 개 렌더링하는 컴포넌트라면 React `useId()` 등으로 이름을 고유하게 만듭니다. 실제 버튼 이름은 `카드 내기`, `점수 확정`처럼 게임 행동으로 바꿉니다.

### 10.3 충돌을 줄이는 작업 방식

1. **게임별 브랜치와 worktree를 분리합니다.** 한 폴더에서 여섯 명의 작업 변경을 섞지 않습니다.
2. **작업 시작 시 담당 경로와 개발 서버 포트를 공유합니다.** 포트는 현재 사용 중인 값과 겹치지 않게 정하고 `--strictPort`로 다른 포트로 조용히 이동하지 않게 할 수 있습니다.
3. **게임 내부 파일은 담당자가 수정합니다.** `src/game/<game>/`, 게임별 테스트·UI 명세를 중심으로 작업합니다.
4. **공통 파일은 통합 담당자를 정하거나 변경을 시간차로 반영합니다.** 담당자는 고정 직무가 아니라 해당 변경의 조율 담당자입니다.
5. **공통 변경은 작은 PR로 분리합니다.** 디자인 토큰 도입, 공통 팝업 API 변경, 모든 게임의 버튼 일괄 변경을 게임 기능 PR에 끼워 넣지 않습니다.
6. **병합 후 기존 게임을 확인합니다.** 내 게임 화면만 맞아도 공통 CSS나 카메라 분기로 다른 게임이 깨질 수 있습니다.

| 특히 충돌이 잦은 공통 영역 | 변경할 때 남길 내용 |
| --- | --- |
| `styles.css`, `park.css`, `prototypeTable.css` | 영향을 받는 화면, 필요한 이유, 기존 게임 검수 |
| `GamePanel.tsx`, 태블릿 model·목록 | 기존 게임 분기를 보존했는지, 새 코드의 진입 조건 |
| 공통 protocol·store·runtime | BE 계약, 복구·관전·종료 영향 |
| `CameraRig`, `Avatars`, `AvatarOverlays` | 게임별 분기 조건, 일반 공원으로 복귀하는 조건 |
| 설명서·결과·지갑 | 새 게임만의 데이터와 공통 동작을 어떻게 연결했는지 |
| `package.json`, lockfile | 의존성 추가 이유, 다른 작업에 미치는 영향 |

### 10.4 컨벤션 자체를 바꿀 때

기존 컴포넌트로 해결되지 않는 반복 패턴이 생기면 `적용 화면 → 현재 불편 → 제안 값/동작 → 전후 화면 → 영향을 받는 게임`을 적고 공통 변경으로 제안합니다. 채택되면 실제 코드와 이 문서를 같이 갱신합니다. 문서만 먼저 바꿔 이미 적용된 것으로 보이게 하지 않습니다.

## 11. 검수 체크리스트와 PR 양식

### 11.1 화면·디자인

- [ ] 기존 공원·종이 패널과 색감이 연결된다.
- [ ] 제목, 현재 상태, 주 행동의 순서가 한눈에 보인다.
- [ ] 내 차례·상대 차례·선택·준비 상태를 색 이외의 표시로도 구분한다.
- [ ] 밝은 장면과 어두운 장면에서 글자를 읽을 수 있다.
- [ ] 기본·hover·focus·disabled·요청 중 버튼을 확인했다.
- [ ] 긴 닉네임, 빈 좌석, 지원 최대 인원, 0점·큰 점수·여러 자리 엽전을 확인했다.
- [ ] 이미지가 없거나 늦게 떠도 제목·조작이 남는다.
- [ ] 좁은 화면과 낮은 화면에서 마지막 버튼까지 접근한다.
- [ ] 채팅·설명서·결과창이 판과 주 행동을 가리는지 확인했다.

### 11.2 조작·상태

- [ ] 키보드만으로 주요 버튼에 접근하고 포커스를 볼 수 있다.
- [ ] 팝업 열기·Tab/Shift+Tab·Esc·닫은 후 포커스 복원을 확인했다.
- [ ] 채팅/입력/한글 조합 중 게임 단축키가 실행되지 않는다.
- [ ] 팝업 뒤에서 이동·판 클릭이 실행되지 않는다.
- [ ] 빠른 연속 클릭으로 같은 요청이 중복 전송되지 않는다.
- [ ] 요청 실패와 반영 여부 불명을 구분하고 올바른 복구 행동을 제공한다.
- [ ] 재접속 후 이전 화면의 선택·영수증·오류가 다른 경기로 섞이지 않는다.
- [ ] 참가자와 관전자에서 비공개 정보가 분리된다.
- [ ] 관전자 공통 요소인 채팅과 게임 화면의 핑을 제공한다.
- [ ] 채팅 입력·핑 전송이 실제 게임 행동이나 뒤의 공원 조작으로 실행되지 않는다.
- [ ] 채팅·핑의 공유 범위를 확인하고, 다른 경기나 지난 판의 이벤트가 섞이지 않는다.
- [ ] 그 외 관전 요소는 담당자가 자율적으로 정했으며 공통 필수로 간주하지 않는다.
- [ ] 경기 종료와 정산 완료를 구분한다.
- [ ] 결과창 재열기·중복 이벤트로 보상이 다시 지급되거나 연출되지 않는다.
- [ ] 게임/테이블 퇴장 후 공원 입력·카메라·HUD가 정상 복원된다.
- [ ] 모션 감소와 음소거에서도 핵심 상태를 이해할 수 있다.

### 11.3 코드·검증

- [ ] CSS가 게임 루트 안에 한정되고 다른 게임의 선택자를 수정하지 않았다.
- [ ] 공통 파일 변경 범위와 영향을 PR에 적었다.
- [ ] 새 이미지·폰트·음원의 출처와 용량을 확인했다.
- [ ] 작업 브랜치의 `package.json`에서 실제 명령을 확인했다.

기준 브랜치에서의 기본 명령은 다음과 같습니다. 각자의 worktree에서 `frontend/`를 작업 디렉터리로 실행합니다.

```sh
pnpm typecheck
pnpm build
```

문서·주석만 변경하면 링크·경로·내용 확인으로 충분합니다. UI 구현을 변경했다면 렌더링과 실제 조작을 확인합니다. 게임 상태·액션을 바꿨다면 해당 unit/e2e를, 공통 입력·로비·결과를 바꿨다면 관련 기존 게임 회귀를 추가로 확인합니다. 전체 테스트를 통과했다는 말은 실제 실행했을 때만 적습니다.

태블릿 흐름의 기존 전용 명령은 `pnpm test:e2e:tablet:default`입니다. 일반 `pnpm test:e2e`와는 서버 설정이 다를 수 있으므로 [TABLET_SERVER_CHECKLIST.md](../../frontend/docs/TABLET_SERVER_CHECKLIST.md), 테스트 config와 fixture를 먼저 확인합니다. 개발 목업 화면을 확인한 것과 실제 BE로 다인 플레이한 것을 구분해 기록합니다.

### 12.2 처음 보는 용어

| 용어 | 뜻 |
| --- | --- |
| HUD | 게임 장면 위에 표시되는 점수·시간·버튼 등의 UI |

| public/private state | 모든 참가자·관전자가 볼 정보 / 특정 참가자만 볼 정보 |
| pending | 요청을 보냈지만 아직 처리 결과를 기다리는 상태 |
| uncertain | 요청이 실제 반영되었는지 확신할 수 없어 상태 확인이 필요한 상황 |
| fixture | 특정 상태나 응답을 재현하기 위한 테스트 데이터 |
| 회귀 검수 | 내 변경으로 원래 되던 화면·동작이 깨지지 않았는지 확인하는 것 |
