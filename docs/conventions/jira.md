# Jira_Convention

## 2026-10-22 사용자 요청에 따른 작업 등록 기준

- 새 Story는 독립적으로 완료·인수할 기능 흐름이 생기고 기존 이슈로 관리할 수 없을 때만 만든다. API가 여러 개여도 같은 사용자 흐름이면 하나로 묶는다.
- 리팩터링·버그 수정·테스트 보강·명세/예제 갱신·실행 설정·커밋은 관련 기존 Story의 체크리스트/검증 결과로 갱신한다. 작업 단계마다 새 티켓을 만들지 않는다.
- 같은 목적의 후속 보완은 완료된 이슈에도 연결해 기록하고, 실제 완료 조건이 다시 남으면 상태를 조정한다. 기존 이력은 삭제·병합하지 않는다.
- 독립 목표가 새로 생긴 경우에만 Epic을 검토하며, API 수·커밋 수·작업 날짜를 이슈 분리 기준으로 삼지 않는다.

아래 팀 수신 원문은 보존하며 위 기준은 사용자 담당 작업의 등록 단위에 적용한다.

> **목적:** 프로젝트 내 Jira 이슈의 이름과 구조를 통일해 누구나 같은 기준으로 작업을 등록하고 진행 상황을 파악할 수 있도록 합니다.
> 
> 
> **적용 범위:** Epic과 Story
> 
> **핵심 규칙:** Epic은 완성할 기능 또는 목표, Story는 그 목표를 달성하기 위한 구체적인 작업을 나타냅니다.
> 

---

## 1. Issue Hierarchy

프로젝트에서는 `Epic`과 `Story` 이슈 유형을 사용합니다. 기획·디자인·프론트엔드·백엔드·QA·인프라·문서화 작업도 Story로 관리합니다.

```
EPIC [AUTH] 사용자 인증
├── STORY [PLAN] 인증 정책 정의
├── STORY [DESIGN] 로그인 화면 설계
├── STORY [FE] 로그인 화면 개발
├── STORY [BE] 인증 API 개발
└── STORY [QA] 인증 기능 테스트
```

| Issue Type | 역할 | 판단 기준 |
| --- | --- | --- |
| **Epic** | 하나의 기능 또는 독립적으로 추적할 목표를 관리 | 무엇을 완성할 것인가? |
| **Story** | Epic의 목표를 달성하기 위한 구체적인 작업을 관리 | 어떤 작업을 완료할 것인가? |
- Story는 관련 Epic에 연결하는 것을 원칙으로 합니다.
- 이 프로젝트에서는 기획·디자인·개발·QA 등의 작업도 Story 유형으로 등록합니다. 따라서 모든 Story가 사용자 스토리 형식(예: “사용자로서 …하고 싶다”)일 필요는 없습니다.
- 상태, 우선순위, 담당자, 시작일·마감일은 이슈 제목이 아니라 Jira 필드로 관리합니다.

## 2. Epic Convention

### 2.1 Naming Rule

**형식:** `[목표 코드] 목표명`

Epic 코드는 기능 또는 목표의 종류를 나타냅니다. 짧고 구별하기 쉬운 코드를 사용하고, 같은 의미의 코드를 여러 개 만들지 않습니다.

### 2.2 Epic Code & Examples

| Epic Name | 용도 | 포함 범위 예시 |
| --- | --- | --- |
| `[PROJECT] 서비스 기획` | 서비스 전반에 공통으로 적용되는 초기 기획 | 서비스 목표·범위, 사용자 유형, 상위 요구사항 및 우선순위 |
| `[AUTH] 사용자 인증` | 인증 기능 | 회원가입, 로그인, 로그아웃, 인증 상태 |
| `[USER] 사용자 관리` | 사용자 계정 및 프로필 기능 | 프로필 조회·수정, 계정 정보 |
| `[PRODUCT] 상품 관리` | 상품 관련 기능 | 상품 목록·상세 조회, 상품 정보 관리 |
| `[SEARCH] 검색 및 탐색` | 검색 기능 | 검색, 필터, 정렬 |
| `[ADMIN] 관리자 기능` | 관리자 기능 | 관리자 화면 및 관리 기능 |
| `[FOUNDATION] 프로젝트 공통 기반 구축` | 여러 기능에 공통으로 쓰이는 개발 기반 | 공통 UI, API 공통 규격, 공통 권한 체계 |
| `[OPS] 서비스 운영 환경 구축` | 독립적으로 추적할 운영 목표 | 배포, 모니터링, 운영 환경 |

표는 예시입니다. 실제 서비스에 없는 Epic은 만들지 않습니다. Epic 코드와 이름은 프로젝트 시작 시 팀에서 합의한 뒤 일관되게 사용합니다.

### 2.3 Epic 분리 규칙

- 하나의 Epic은 하나의 기능 또는 독립적으로 추적할 가치가 있는 목표를 나타냅니다.
- 여러 Story를 묶어 별도 진행 상황과 완료 여부를 확인할 필요가 있을 때 Epic으로 만듭니다.
- 서로 다른 기능을 하나의 Epic에 과도하게 묶지 않습니다.
- 모든 Epic에 기획·디자인·개발·QA Story를 억지로 만들지 않습니다. 실제로 필요한 작업만 등록합니다.
- 여러 기능에 공통으로 쓰이는 작업은 독립적인 관리가 필요한 경우에만 `[FOUNDATION]` 등 별도 Epic으로 분리합니다.
- `기획`, `프론트엔드`, `백엔드`, `QA`처럼 업무 단계나 담당 조직만을 기준으로 Epic을 나누지 않습니다. 업무 영역은 Story 접두어로 표현합니다.
- 서비스 전체 기획은 범위와 산출물이 여러 기능에 걸치므로 `[PROJECT] 서비스 기획` Epic으로 관리합니다. 개별 기능의 상세 기획은 해당 기능 Epic 안의 `[PLAN]` Story로 관리합니다.
- 제목에 상태나 날짜를 넣지 않습니다.

### 2.4 Epic Description Template

```
## Purpose
이 Epic으로 달성하려는 목표를 작성합니다.

## Scope
- 포함할 기능 또는 작업:
- 관련 사용자 또는 시스템:

## Out of Scope
- 이번 범위에서 다루지 않는 항목:

## Definition of Done
- 완료로 판단할 조건:

## References
- 기획서 / 디자인 / 기술 문서 링크:
```

필요하지 않은 항목은 생략할 수 있습니다. 다만 `Purpose`, `Scope`, `Definition of Done`은 가능한 한 작성합니다.

## 3. 서비스 전체 기획과 기능별 기획 구분

기획 문서는 **서비스 전체를 위한 기획인지, 특정 기능을 위한 기획인지**에 따라 배치합니다.

### 3.1 서비스 전체 기획

서비스의 방향·범위·상위 요구사항처럼 여러 기능에 공통으로 적용되는 기획은 별도 Epic으로 관리합니다.

**Epic:** `[PROJECT] 서비스 기획`

```
EPIC [PROJECT] 서비스 기획
├── STORY [PLAN] 서비스 목표 및 범위 정의
├── STORY [PLAN] 사용자 유형 및 주요 시나리오 정의
├── STORY [PLAN] 상위 요구사항 및 우선순위 정리
├── STORY [PLAN] 서비스 공통 정책 정의
└── STORY [DOCS] 서비스 기획서 정리 및 공유
```

이 Epic은 개별 화면이나 API 구현이 아니라 서비스 전반의 기획 산출물과 합의 사항을 관리합니다.

### 3.2 기능별 기획

로그인·사용자 관리·상품 검색처럼 특정 기능의 상세 요구사항과 정책은 해당 기능 Epic 아래에 Story로 등록합니다.

**Epic:** `[AUTH] 사용자 인증`

```
EPIC [AUTH] 사용자 인증
├── STORY [PLAN] 인증 요구사항 정의
├── STORY [PLAN] 로그인 및 로그아웃 정책 정의
├── STORY [DESIGN] 로그인·회원가입 화면 설계
├── STORY [FE] 로그인·회원가입 화면 개발
├── STORY [BE] 인증 API 개발
└── STORY [QA] 인증 기능 테스트
```

### 3.3 공통 정책 및 기반 작업

권한·공통 UI·API 공통 규격처럼 여러 기능에 영향을 주는 작업은 독립적으로 계획하고 추적할 필요가 있을 때 별도 Epic으로 분리합니다.

```
EPIC [FOUNDATION] 프로젝트 공통 기반 구축
├── STORY [PLAN] 공통 권한 정책 정의
├── STORY [DESIGN] 디자인 시스템 설계
├── STORY [FE] 공통 UI 컴포넌트 개발
├── STORY [BE] 공통 API 응답 규격 정의
└── STORY [INFRA] 개발 환경 및 CI/CD 구축
```

**중복 방지 규칙:** 서비스 전체의 상위 정책은 `[PROJECT] 서비스 기획`에, 특정 기능의 상세 정책은 해당 기능 Epic에 둡니다. 같은 작업을 두 Epic에 중복 등록하지 않습니다. 문서 파일은 실제 작업 Story에 링크로 첨부하거나 `References`에 연결합니다.

## 4. Story Convention

### 4.1 Naming Rule

**형식:** `[업무 영역] 구체적인 작업 내용`

스토리 접두어는 작업의 성격을 나타냅니다. 담당자의 직책을 반드시 뜻하는 것은 아닙니다.

### 4.2 Story Prefix

| Prefix | 업무 영역 | 예시 |
| --- | --- | --- |
| `[PLAN]` | 기획 | 요구사항 정의, 정책 수립, 사용자 시나리오 |
| `[DESIGN]` | 디자인 | UI/UX 설계, 와이어프레임, 디자인 시스템 |
| `[FE]` | 프론트엔드 | 화면 개발, 상태 처리, API 연동 |
| `[BE]` | 백엔드 | API, 비즈니스 로직, 데이터 처리 |
| `[QA]` | 품질 검증 | 테스트 케이스, 기능 테스트, 회귀 테스트 |
| `[INFRA]` | 인프라·배포 | 개발 환경, CI/CD, 배포 설정 |
| `[DOCS]` | 문서화 | API 명세, 운영 가이드, 개발 문서 |

새로운 접두어가 필요하면 팀에서 먼저 합의합니다. 같은 작업을 사람마다 서로 다른 접두어로 분류하지 않습니다.

### 4.3 Story Naming Examples

| 권장 이름 | 의미 |
| --- | --- |
| `[PLAN] 서비스 요구사항 정의` | 서비스 전체 요구사항 정리 |
| `[PLAN] 회원가입 정책 정의` | 회원가입 기능의 정책 정리 |
| `[PLAN] 상품 검색 요구사항 정의` | 검색 기능의 동작과 조건 정의 |
| `[DESIGN] 로그인 화면 설계` | 로그인 UI/UX 설계 |
| `[FE] 로그인 화면 개발` | 로그인 화면 구현 |
| `[BE] 로그인 API 개발` | 로그인 API 구현 |
| `[QA] 로그인 실패 시나리오 검증` | 로그인 오류 시나리오 테스트 |
| `[INFRA] 테스트 환경 배포 파이프라인 구성` | 테스트 환경의 배포 자동화 |
| `[DOCS] 인증 API 명세서 작성` | 인증 API 문서 작성 |

### 4.4 Story 작성 규칙

- Story 이름은 `[업무 영역] 구체적인 작업 내용` 형식을 따릅니다.
- 하나의 Story는 명확한 목표와 완료 조건을 가져야 합니다.
- `기획`, `개발`, `테스트`, `수정`처럼 대상이 불분명한 제목은 피합니다.
- 여러 개의 독립적인 결과가 들어 있다면 Story를 분리합니다.
- 관련 Epic에 연결하고, 설명에 작업 범위와 완료 조건을 작성합니다.
- 담당자, 우선순위, 상태, 일정은 Jira 필드로 관리합니다.
- 문서 작성이 독립적인 산출물이고 완료 여부를 추적해야 할 때 문서화 Story를 만듭니다. 단순한 참고 링크 추가라면 별도 Story를 만들지 않아도 됩니다.

### 4.5 Story Description Template

```
## Purpose
이 작업이 필요한 이유와 목표를 작성합니다.

## Tasks
- 수행할 작업을 작성합니다.

## Acceptance Criteria
- [ ] 완료 조건 1
- [ ] 완료 조건 2

## References
- 관련 기획서 / 디자인 / API 명세 링크:
```

작업 특성상 적절하지 않은 항목은 생략할 수 있습니다. `Acceptance Criteria`는 완료 여부를 객관적으로 판단할 수 있게 작성합니다.

```
EPIC [AUTH] 사용자 인증
```

```
├── STORY [FE] 사용자 프로필 조회·수정 화면 개발
├── STORY [BE] 사용자 프로필 조회·수정 API 개발
└── STORY [QA] 사용자 프로필 기능 테스트
```

## 6. Naming Restrictions

| 지양 | 권장 | 이유 |
| --- | --- | --- |
| `[FE] 프론트엔드 개발` | `[FE] 로그인 화면 개발` | 작업 대상이 명확해야 함 |
| `[BE] API 개발` | `[BE] 로그인 API 개발` | 범위가 불명확한 제목을 피함 |
| `[PLAN] 기획 작업` | `[PLAN] 회원가입 정책 정의` | 산출물 또는 결과를 명시함 |
| `[QA] 테스트` | `[QA] 로그인 실패 시나리오 검증` | 검증 대상을 명시함 |
| `[진행 중] 사용자 인증` | `[AUTH] 사용자 인증` | 상태는 Jira 필드로 관리 |
| `[10월] 상품 관리` | `[PRODUCT] 상품 관리` | 일정은 Jira 필드로 관리 |

## 7. Team Checklist

### Epic 체크리스트

- [ ]  
    
    하나의 기능 또는 독립적인 목표를 나타내는가?
    
- [ ]  
    
    정해진 `[목표 코드] 목표명` 형식을 따르는가?
    
- [ ]  
    
    목적·범위·완료 기준이 명확한가?
    
- [ ]

## 8. Convention Summary

| 항목 | 규칙 |
| --- | --- |
| Epic 이름 | `[목표 코드] 목표명` |
| Story 이름 | `[업무 영역] 구체적인 작업 내용` |
| Epic 기준 | 기능 또는 독립적으로 추적할 목표 |
| Story 기준 | 완료 조건이 명확한 작업 |
| 서비스 전체 기획 | `[PROJECT] 서비스 기획` Epic |
| 기능별 기획 | 해당 기능 Epic 아래 `[PLAN]` Story |
| 공통 기반 | 독립적인 추적이 필요할 때 `[FOUNDATION]` Epic |
| Story 업무 영역 | `[PLAN]`, `[DESIGN]`, `[FE]`, `[BE]`, `[QA]`, `[INFRA]`, `[DOCS]` |
| 상태·일정 | 제목이 아니라 Jira 필드로 관리 |
| 중복 방지 | 같은 작업을 여러 Story 또는 Epic에 중복 등록하지 않음 |

**핵심 원칙:** Epic은 완성할 기능 또는 목표를 나타내고, Story는 그 목표를 달성하기 위한 구체적인 작업을 나타냅니다. 서비스 전체 기획은 별도 Epic으로, 개별 기능의 기획은 해당 기능 Epic 아래 Story로 관리합니다.
