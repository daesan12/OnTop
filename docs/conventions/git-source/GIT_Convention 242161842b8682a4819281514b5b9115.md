# GIT_Convention

# Git 작업 안내

- 기준일: 2026-
- 저장소: `https://`
- 개발 기준 브랜치: `develop`

이 문서는 브랜치 전략, 커밋 규칙, Merge Request 절차를 하나로 정리한 팀 공통
기준입니다. 규칙 변경이 필요하면 문서를 먼저 수정하고 팀에 공유합니다.

## 1. 브랜치 역할

GitLab Flow를 응용해 `master` / `develop` / 작업 브랜치 3계층으로 운영합니다.

| 브랜치 | 역할 |
| --- | --- |
| `master` | 배포 가능한 릴리스 이력. 검증을 통과한 변경만 반영 |
| `develop` | 다음 릴리스를 위한 개발 통합 기준선이자 일반 MR 대상 |
| `feat/*` | `develop`에서 분기하는 기능·설계 작업 |
| `fix/*` | 버그 수정 |
| `refactor/*` | 기능 변경 없는 코드 리팩터링 |
| `docs/*` | 독립 문서 변경 (README, 가이드 등) |
| `hotfix/*` | 운영 중 긴급 수정을 위해 `master`에서 분기하는 브랜치 |
- 일반 작업은 최신 `develop`에서 분기하고 MR 대상도 `develop`입니다.
- `master`에는 릴리스 승격과 긴급 수정만 반영합니다.
- 작업 브랜치는 MR 승인자가 병합 후 삭제합니다.
- 현재 단계에서는 별도 `release/*` 브랜치를 강제하지 않습니다. 릴리스 검증은
`develop`에서 수행하고, 통과한 상태만 `master`로 승격합니다.

```
feat/*
fix/*        ---> develop ---> master
refactor/*                       |
docs/*                           +---> hotfix/* ---> master (+ develop 재반영)
```

## 2. 작업 시작

```bash
git fetch origin --prune
git switch develop
git pull --ff-only origin develop
git switch -c feat/S15P21B210-123-user-login
```

브랜치 이름은 `<type>/<Jira번호>-<kebab-case-description>`을 권장합니다.

- 예: `feat/S15P21B210-45-spark-batch-pipeline`, `fix/S15P21B210-77-token-expiry`
- Jira 번호가 없는 소규모 작업은 `docs/git-guide-update`처럼 설명만 사용합니다.

## 3. 경로별 기본 소유

> 미정 - 프로젝트 디렉터리 구조와 담당이 확정되면 아래 표를 채웁니다.
> 

| 경로 | 담당 |
| --- | --- |
|  |  |
|  |  |
|  |  |
|  |  |

담당은 다른 사람의 변경을 금지한다는 뜻이 아니라 동시 수정을 막기 위한 기본
책임자입니다. 담당 밖 파일을 수정할 때는 Jira와 MR에 이유를 남깁니다.

## 4. 커밋

한 커밋에는 하나의 의미 있는 변경만 포함하고, 기능 단위로 작게 쪼개서
커밋합니다.

### 4.1 메시지 형식

```
<type>: <subject>
<type>(scope): <subject>
```

- 제목만으로 충분한지, 본문이 필요한지 먼저 구분합니다.
- 본문에는 무엇을, 왜 바꿨는지를 적고 ’어떻게’는 지양합니다.
- `scope`는 선택이며 `spark`, `kafka`, `backend`, `web`처럼 영역을 적습니다.
- 제목은 명령형으로 간결하게 쓰고 마침표를 붙이지 않습니다.

### 4.2 타입 표

| 타입 | 설명 | 예시 |
| --- | --- | --- |
| `init` | 프로젝트 초기화 | `init: 프로젝트 초기 설정` |
| `feat` | 새로운 기능 추가 | `feat(auth): 사용자 인증 기능 추가` |
| `fix` | 버그 수정 | `fix(auth): 토큰 만료 문제 해결` |
| `refactor` | 리팩터링 (기능 변경 없음) | `refactor: 중복 검증 로직 제거` |
| `perf` | 성능 개선 | `perf(query): 집계 쿼리 최적화` |
| `test` | 테스트 코드 | `test: 로그인 단위 테스트 추가` |
| `docs` | 문서 수정 | `docs: README 설치 방법 갱신` |
| `style` | 포맷팅·스타일 (기능 변경 없음) | `style: 들여쓰기 정리` |
| `build` | 빌드 시스템·외부 의존성 | `build: Dockerfile 추가` |
| `ci` | CI/CD 설정 수정 | `ci: GitLab CI 테스트 잡 추가` |
| `chore` | 기타 설정·정리 작업 | `chore: .env.example 업데이트` |
| `revert` | 커밋 되돌리기 | `revert: 인증 로직 변경 되돌림` |
| `release` | 버전 릴리즈 | `release: v1.0.0 릴리즈` |

### 4.3 적용 예시

```bash
git commit -m "init: Spring Boot 초기 설정"
git commit -m "build: .gitignore 설정"
git commit -m "feat(user): 회원가입 API 구현"
git commit -m "fix(auth): 로그인 시 비밀번호 검증 오류 수정"
git commit -m "chore: CORS 설정 추가"
git commit -m "docs: README.md 업데이트"
```

본문이 필요한 경우:

```
feat(pipeline): 실시간 집계 스트림 추가

배치 집계만으로는 대시보드 지연이 커서 실시간 경로를 분리했다.
기존 배치 결과와 동일한 스키마를 사용해 소비 측 변경은 없다.
```

### 4.4 이슈 연동

커밋 메시지나 MR 설명에 아래 키워드를 넣으면 병합 시 이슈가 자동으로 닫힙니다.

```bash
git commit -m "fix(auth): 로그인 버그 수정 (Closes #42)"
git commit -m "feat(reco): 추천 알고리즘 개선 (Resolves #123)"
```

- 사용 가능 키워드: `Fixes #번호`, `Closes #번호`, `Resolves #번호`
- 여러 이슈: `Closes #42, Closes #56`
- 원격 저장소에 푸시되어야 적용됩니다.

## 5. 공통 파일

다음 파일은 충돌 가능성이 높으므로 한 번에 한 사람만 수정합니다.

- 루트 환경·빌드 설정과 lock 파일
- API·이벤트 계약 파일 (예: `openapi.yaml`, `asyncapi.yaml`)
- DB 마이그레이션 디렉터리
- CI/CD·인프라 설정 (GitLab CI, Jenkins, Terraform 등)
- 공용 스키마·설정 원본

API나 스키마 변경은 계약을 먼저 MR로 합의하고, 병합된 `develop`을 각 구현
브랜치에 다시 반영합니다. 이미 적용된 마이그레이션 파일은 수정하지 않고 새
버전을 추가합니다.

## 6. 커밋 전 확인

```bash
git status --short
git diff --check
git diff
```

각 모듈의 테스트·정적 검사 명령은 디렉터리 구조가 확정되면 아래에 추가하고,
해당 디렉터리 README에도 같은 명령을 기록합니다.

```
TODO: 모듈별 빌드·테스트 명령 추가
예) cd backend && ./gradlew test
예) npm run lint && npm run test
```

필요하면 `.husky/pre-commit`으로 자동화합니다. (부록 B 참고)

## 7. Push와 Merge Request

```bash
git push -u origin <branch-name>
```

- 일반 기능·수정·문서 MR의 대상 브랜치는 `develop`입니다.
- 기능 하나가 끝날 때마다 `master`로 MR을 만들지 않습니다.
- MR은 작성자가 아닌 리뷰어가 승인 후 병합하고, 작업 브랜치를 삭제합니다.

MR에는 다음 내용을 포함합니다.

- 관련 Jira / 이슈
- 무엇을 왜 바꿨는지
- 영향받는 화면·API·DB·이벤트
- 실행한 테스트와 결과
- 리뷰어가 확인할 사항

템플릿은 `.gitlab/merge_request_templates/`에서 관리합니다. (부록 A 참고)

## 8. 최신 develop 반영

작업 중 하루에 한 번 이상 최신 기준을 반영합니다.

```bash
git fetch origin
git rebase origin/develop
```

공유된 브랜치에서 이미 다른 사람이 작업을 이어받았다면 rebase 대신 merge를
사용하고, 사전에 팀과 확인합니다.

```bash
git switch develop
git pull origin develop
git switch <branch-name>
git merge develop
```

## 9. develop 통합과 master 승격

팀 통합일에는 다음 순서로 진행합니다.

1. `master`에만 있는 최신 변경이 있으면 먼저 `master` 에서 `develop`으로 MR을
만들어 반영합니다.
2. 각 작업 브랜치는 최신 `origin/develop`을 반영하고, 충돌은 작업 브랜치에서
해결한 뒤 `develop` 대상 MR로 병합합니다.
3. 한 브랜치를 병합할 때마다 정적 검사와 해당 영역 테스트를 실행합니다.
4. 모든 작업을 합친 `develop`에서 전체 CI, 단위·통합 테스트와 주요 사용자 흐름
스모크 테스트를 실행합니다.
5. 충돌이 모두 해소되고 검증이 통과한 경우에만 `develop`에서 `master`로 MR을
만들어 승격합니다.

통합 중 발견한 문제는 `develop`에서 수정·재검증하며, 검증에 실패한 상태를
`master`로 옮기지 않습니다.

운영 중 긴급 수정은 `master`에서 `hotfix/*`를 분기해 검증 후 `master`로 MR을
만들고, 동일 변경을 `develop`에도 병합합니다.

## 10. 금지·주의

- `develop`과 `master`에 직접 푸시하지 않고 MR과 리뷰를 거칩니다.
- 일반 기능 브랜치에서 `master`로 바로 MR을 만들지 않습니다.
- 다른 사람의 변경을 확인 없이 삭제하지 않습니다.
- 공유 브랜치에 `git push --force`를 사용하지 않습니다.
- `.env`, 비밀번호, 토큰, 인증서, Terraform 상태를 커밋하지 않습니다.
- `git reset --hard`, `git clean -fd`는 영향 범위를 모르면 실행하지 않습니다.

비밀정보를 커밋했다면 파일 삭제만 하지 말고 즉시 키를 폐기·재발급하고 팀에
알립니다.

## 부록 A. Merge Request 템플릿

GitLab은 `.gitlab/merge_request_templates/` 아래 파일을 MR 생성 화면에서
선택할 수 있게 제공합니다.

```
.gitlab/
└─ merge_request_templates/
   ├─ Default.md      # feat/fix/refactor -> develop
   ├─ Hotfix.md       # hotfix/*          -> master
   └─ Docs.md         # docs/*            -> develop
```

### Default.md

```markdown
## 변경사항 요약
<!-- 무엇을 왜 바꿨는지 -->
-

## 관련 Jira / 이슈
<!-- 예: S15P21B210-123, Closes #12 -->
-

## MR 타입
-[ ] feat: 새로운 기능 추가
-[ ] fix: 버그 수정
-[ ] refactor: 코드 리팩터링
-[ ] style: 포맷팅·UI 스타일 수정
-[ ] test: 테스트 코드 추가·보완
-[ ] docs: 문서 수정
-[ ] chore: 빌드·설정 수정

## 영향 범위
<!-- 화면 / API / DB / 이벤트 -->
-

## 체크리스트
-[ ] 로컬에서 정상 동작을 확인했습니다.
-[ ] 테스트를 실행했고 결과를 아래에 적었습니다.
-[ ] 기존 기능에 영향이 없음을 확인했습니다.
-[ ] 문서가 필요한 경우 함께 수정했습니다.
-[ ] 비밀정보가 포함되지 않았습니다.

## 실행한 테스트와 결과
-

## 스크린샷 (선택)

## 리뷰어가 확인할 사항
-
```

### Hotfix.md

```markdown
## 문제 상황
<!-- 발생한 문제와 영향 범위, 가능하면 스크린샷 -->
-

## 해결 방법
-

## 관련 Jira / 이슈
-

## 체크리스트
-[ ] 수정 부분을 테스트했습니다.
-[ ] 기존 기능이 정상 동작함을 확인했습니다.
-[ ] `develop`에도 동일 변경을 반영할 계획을 적었습니다.

## 기타
-
```

### Docs.md

```markdown
## 작업 내용
-

## 관련 Jira / 이슈
-

## 체크리스트
-[ ] 오타·문법을 확인했습니다.
-[ ] 문서 구조를 명확히 했습니다.
-[ ] 필요한 예제·링크를 추가했습니다.

## 기타
-
```

## 부록 B. 커밋 전 자동 검사 (선택)

```
.husky/
└─ pre-commit        # Git hook에서 자동 실행
scripts/
└─ pre-commit.sh     # 실제 검사 스크립트 (수동 실행도 가능)
```

`.husky/pre-commit`

```bash
#!/bin/sh
. ./scripts/pre-commit.sh
```

Husky 설치

```bash
npm install husky --save-dev
npx husky install
```

`scripts/pre-commit.sh` 예시 (프로젝트 스택에 맞게 수정)

```bash
#!/bin/bash

# 1. 코드 스타일 검사
# ./gradlew checkstyleMain      # Spring Boot
# flake8 . && black --check .   # Python
# npx eslint . --fix            # JS/TS

# 2. 테스트 실행
# ./gradlew test
# pytest --maxfail=1 --disable-warnings -q
# npx jest --bail --maxWorkers=4

# 3. 변경 파일 확인
echo "Changed files:"
git diff --name-only --cached

exit 0
```
