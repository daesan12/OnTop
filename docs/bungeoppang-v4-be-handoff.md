## 전달 요지

기존 「붕어빵 뒤집기 BE 작업명세 v4」와 함께 전달하는 보충 문서다. 기존 명세의 주문·쟁반·납품·정산 구현 범위를 새 요청으로 중복 추가하지 않는다. FE를 구현하면서 구체화된 **연동 우선순위와 아직 합의가 필요한 응답·실패 처리**를 정리했다. 이 문서도 승인된 API/DTO 명세는 아니다.

손님 등장, 재료 전환, 불 표시, 쟁반 이동, 폐기 연출을 위한 별도 서버 이벤트는 필요하지 않다. 현재 손님은 개인 게임의 주문 카드 내부 2D 연출이다. 공개 월드 NPC 이동이나 다른 플레이어에게 연출을 전송하는 기능은 요청 범위에 없다.

## 현재 상태와 기존 BE 작업 범위

| 구분 | 현재 상태 / 요청 |
| --- | --- |
| FE v4 | 네 가지 소·랜덤 불·쟁반·주문·납품 규칙과 화면 구현. 명시적인 개발 모드에서 로컬 서비스로 검증 |
| 실제 연결 | 기본 개발/프로덕션 FE는 기존 승인 v2 API 유지. v4 실제 서버·DB 지급 검증은 미완료 |
| 확인한 BE 코드 | 이 커밋의 `BungeoppangRules.VERSION`과 저장 규칙 버전은 v2. 배포 서버의 현재 상태를 조회한 결과는 아님 |
| 기존 v2 활용 | 세션·랜덤 불·소유권 검증·멱등 정산·지갑 등 기존 기반을 v4에 맞게 확장 |
| 기존 v4 명세 구현 | 소 종류를 포함한 행동 검증, 현재 주문 발급, 쟁반 재계산, FIFO 전체 납품, 납품 시 점수 반영, 특수 보너스, 서버 확정 지급 |

FE의 `nextOrder` 등 이름은 내부 서비스 인터페이스다. 동일한 이름의 엔드포인트나 DTO를 만들어 달라는 의미가 아니다. 실제 전송 방식과 필드는 BE와 승인한 계약에 맞춰 FE 어댑터를 작성한다.

## 우선 확정이 필요한 사항

### 1. 납품 확인과 다음 주문을 중복 없이 처리하는 계약

사용자가 납품하면 FE는 재고와 예상 점수를 즉시 반영하고 다음 주문을 기다린다. 기다리는 동안에도 타이머와 기존 빵 조리는 계속된다. 이는 현재 미리보기 정책이며 운영 정책 확정이 필요하다.

- 어떤 세션·주문·행동 기록까지 승인했는지 식별할 수 있는 응답이 필요하다. 미래 주문 목록 전체를 FE에 전달하지 않는다.
- 납품 승인과 다음 주문 발급을 일관되게 처리하고, 응답 유실 후 동일 요청을 다시 보내도 같은 처리 결과와 같은 주문을 돌려줘야 한다. 재시도로 이중 납품되거나 주문이 재추첨되면 안 된다.
- 현재 FE는 재시도할 때 **납품 직후 고정한 기록**을 다시 보낸다. 그동안 조리 로그는 계속 늘어날 수 있으므로, 승인한 기록 범위와 이후 기록을 연결하는 방식을 합의해야 한다.
- 통신 실패와 서버의 납품 거부를 구분할 오류가 필요하다. 서버가 거부하면 재고·점수·현재 주문을 어떻게 복구할지 정해야 한다. 서버 확정 상태 반환 또는 승인 기록을 기준으로 재생하는 방식 등을 함께 결정한다.

현재 로컬 서비스 검증에는 실제 서버 거부 후 상태를 복구하는 통합 동작이 포함되지 않는다. 승인 계약에 따라 FE에서도 이를 구현해야 한다.

### 2. 종료 직전 납품과 정산의 순서

예: 59.9초에 납품하고, 60초 종료 뒤에 납품 응답이 도착하는 경우다.

- 유효 시간 내 납품을 최종 정산에 한 번만 포함하는 기준을 정해야 한다.
- 진행 중 납품 요청과 완료 요청이 동시에 도착하거나 순서가 바뀌어도, 주문 승인·최종 로그 재계산·지급 결과가 같아야 한다.
- 종료 뒤 새 주문 표시가 필요한지, 납품 확인만 복구하면 되는지와 결과 재조회 방식을 합의한다.
- 완료·포기·만료가 경쟁할 때 최종 상태와 재시도 응답도 명시한다.

### 3. 시작 응답과 행동 기록의 실제 형식

- 시작 시 판 식별자, 규칙/설정 버전, 시간 기준, 현재 주문, 불 원본을 제공하는 방식을 확정한다. 판 도중 규칙 설정이 바뀌지 않도록 한다.
- FILL의 소 종류, 철판 행동, 쟁반 폐기 대상, 납품 대상 주문을 식별하는 형식을 정한다. 현재 FE의 배열 인덱스나 fixture 필드가 운영 식별자 규격으로 승인된 것은 아니다.
- 행동 순서·중복·시간 단위·최대 기록 수·요청 크기와 오류 응답을 합의한다. v4 로그를 기존 v2 검증기로 처리하면 안 된다.
- 불 목록 길이·추가 공급·소진 정책을 정한다. 미리보기의 불 400개/주문 64개는 개발용 값이며, 기존 v2의 불 64개도 v4 확정 한도로 간주하지 않는다. 소진 시 FE가 독립 추첨하거나 값을 재사용하지 않는다.

### 4. 시간과 확정 결과의 의미

- FE는 현재 3.5초 카운트다운 뒤 실제 플레이 60초를 진행한다. 서버 시작 시각과 플레이 원점, 60,000ms 입력 포함 여부, 전송 지연 유예, 탭 비활성 처리 기준을 맞춰야 한다.
- 40초 전후 익힘 계산과 정수 내림은 기존 v4 명세의 동일 계산식을 사용해야 한다. 다음 주문 대기 중 조리를 계속하는 정책도 서버 검증과 일치해야 한다.
- 결과에는 총점, 조리 성공/황금/실패/폐기, 최고 콤보 외에 납품 빵 수·완료 주문 수·특수 납품 수·추가 보너스 점수를 구분할 정보가 필요하다. 이름과 응답 구조는 BE 계약으로 정한다.
- 조리 성공 개수와 납품 개수는 다르다. 기존 `verifiedCompletedCount = made` 호환 의미를 유지할지 명시한다.
- 계산 보상과 실제 지급액, 일일 획득 누계/상한을 구분한다. 일일 100냥 상한·중복 지급 방지는 기존 요구사항이며, KST 자정 전후 한도 귀속일은 기존 v4 명세대로 합의가 필요하다.

## 이번 연출 때문에 추가하지 않아도 되는 BE 기능

| FE 화면 | 사용하는 정보 / 처리 |
| --- | --- |
| 손님 입장·대기·퇴장 | 현재 주문 수신, 준비 수량, 납품 상태로 FE 연출. 서버 승인 거부 시 표시 복구는 위 계약에 맞춰 처리 |
| 팥·슈크림·피자·초코 색과 도구 전환 | FE 재료 선택 상태. 선택 애니메이션 자체를 별도 행동 로그로 전송하지 않음 |
| 약불·보통불·센불 / 불꽃 / 굽기 배율 | 서버가 발급한 불과 합의한 경과 시간·규칙으로 표시 |
| 쟁반 이동·납품 이동·폐기함 반응 | 게임 규칙상 성공한 행동과 실제 소비 재고를 기준으로 FE 연출 |
| 밤 시인성·모션 감소 | FE 재질·접근성 처리 |

손님 대기시간 제한·이탈 벌점·재고 부패·랭킹은 이번 보충 요청에 추가하지 않는다.

## BE에서 회신받고 싶은 자료와 공동 검증

1. 위 1~4항의 정책과 승인된 통신 명세: 경로/메시지 방식, 요청·응답 예시, 식별자, 시간 단위, 오류, 재시도 기준.
2. 시작 → 정상 납품 → 다음 주문 → 응답 유실 후 재시도 → 종료 직전 납품 → 최종 정산/재조회 예시.
3. 규칙 버전과 미정 설정값, 개발 환경 사용 방법, 지갑이 준비된 테스트 계정, 연동 가능한 시점.
4. 공통 fixture 비교 및 실제 개발 DB에서 세션·지갑을 함께 검증한 결과. FE 목업 테스트와 실제 지급 검증은 구분한다.

현재 공통 fixture는 불 100 두 번, 양면 PERFECT 팥 2개를 한 주문에 납품하는 예다. 기대값은 **20점, 계산 보상 1냥, 납품 2개, 완료 주문 1건, 불 소비 2회, 빈 쟁반**이다. 이 fixture는 전송 DTO가 아닌 규칙 비교 자료이며, 실제 지급액은 지갑/일일 한도에 따라 별도 검증한다.

추가로 특수 보너스 내림·가득 찬 쟁반·실패/폐기·40초 경계·납품 중복/유실·종료 경합·동시 정산·자정 경계를 기존 BE v4 명세의 검증 항목과 함께 확인한다. BE 계약 확정 후 FE 어댑터·거부 시 복구·실제 연동 테스트를 마무리한다.

## 채팅 전달문

붕어빵 v4 FE 구현 내용을 기준으로 BE 연동 협의사항을 정리했습니다. 기존 BE 작업명세 v4와 보충 문서를 같이 확인 부탁드립니다.

손님 이동, 네 가지 소 색상/전환, 불 세기 표시, 쟁반·폐기 연출은 FE에서 처리해서 별도 연출용 API는 필요 없습니다. 기존 v4 명세의 주문·쟁반·납품·정산 구현은 그대로 필요합니다.

우선 맞추고 싶은 부분은 ① 납품 확인/다음 주문 응답과 재시도 시 중복 방지, ② 종료 직전 납품과 최종 정산의 처리 순서, ③ 시작·행동 로그 형식과 서버 거부 시 상태 복구, ④ 플레이 시간 기준과 최종 결과 항목입니다. 현재 FE는 납품을 예상 반영하고 다음 주문 대기 중에도 조리를 계속하므로 이 정책을 서버 검증과 함께 확정하면 좋겠습니다.

지금 v4는 개발용 로컬 서비스로 검증했고 실제 서버 지급은 아직 연결 전입니다. 승인 API/응답 예시와 위 정책, 연동 가능한 시점을 공유해 주시면 FE 어댑터와 실제 연동 검증을 이어서 진행하겠습니다. 보충 문서: `docs/bungeoppang-v4-be-handoff.md`.
