# 붕어빵 이용 상태 말풍선 — FE 완료 및 BE 구현 요청

- 갱신일: 2026-10-28
- FE 작업 브랜치: `feat/bungeoppang-v5-fe-polish`
- 통합 기준: `dev`의 `165c155`

## 어떤 작업인가요?

붕어빵 미니게임을 하는 사용자의 머리 위에 **“붕어빵 뒤집는 중”** 상태 말풍선을 표시하는 작업입니다. 같은 공원 채널에 있는 다른 사용자도 볼 수 있습니다.

일반 채팅은 크림색이고 시간이 지나면 사라집니다. 이번 상태 말풍선은 금빛 테두리의 갈색으로 구분하며, 붕어빵 조리 라운드가 진행되는 동안 계속 표시합니다. 채팅과 동시에 표시할 수 있고, 채팅이 사라져도 상태 말풍선은 유지됩니다.

이번 브랜치는 **FE 전용이며 BE 코드·테스트·DB 변경을 포함하지 않습니다.** 기존 브랜치의 BE 참고 구현은 가져오지 않았습니다. 아래 계약을 기준으로 BE 담당자가 최신 dev에서 별도 구현·검토·배포를 진행해 주세요. 이미 유사 기능을 구현했다면 최종 응답과 배포 결과만 공유해 주세요.

## FE 완료 내용과 BE 요청 범위

### FE

- 서버가 보내는 이용 상태를 받아 아바타별로 보관합니다.
- 상태가 `BUNGEOPPANG`이면 별도의 상태 말풍선을 표시합니다.
- 일반 채팅의 표시 시간과 독립적으로 유지합니다.
- 서버가 상태를 해제하거나 사용자가 채널에서 사라지면 말풍선을 제거합니다.
- 기존 조리 화면에서 본인의 아바타와 머리 위 UI를 숨기는 동작은 유지합니다. 다른 사용자는 공원에서 해당 아바타의 상태를 볼 수 있습니다.

관련 파일: `frontend/src/network/protocol.ts`, `worldClient.ts`, `frontend/src/world/AvatarOverlays.tsx`, `frontend/src/park/scene.css`

### BE 구현 요청 — 이번 FE 변경에는 포함하지 않음

- `MinigameService`에서 서버가 승인한 라운드 시작·종료에 맞춰 내부 이벤트를 발행합니다.
- `MinigameConfiguration`에서 이벤트 발행을 연결합니다.
- `TableHub`는 **트랜잭션 커밋 이후(`AFTER_COMMIT`)** 이벤트를 받아 같은 채널에 `WORLD_STATE`를 전송합니다. 롤백된 시작·종료는 공개 상태를 바꾸지 않습니다.
- `WorldChannelRegistry`가 공개 이용 상태와 만료 시점을 관리합니다.
- 이전 라운드의 늦은 이벤트가 새 라운드 상태를 덮어쓰지 않도록 서버 내부 세션 ID를 확인합니다.
- 완료 요청이 누락돼도 서버가 정한 조리 종료 시각이 지나면 월드 갱신 과정에서 상태를 해제합니다.

관련 파일: `backend/src/main/java/com/ssafy/ontop/minigame/service/MinigameActivityChanged.java`, `MinigameService.java`, `backend/src/main/java/com/ssafy/ontop/minigame/config/MinigameConfiguration.java`, `backend/src/main/java/com/ssafy/ontop/table/service/TableHub.java`, `backend/src/main/java/com/ssafy/ontop/world/service/WorldChannelRegistry.java`

기존 WORLD_STATE에 서버가 결정한 상태를 싣는 안입니다. 별도 클라이언트 상태 설정 요청이나 점수·보상 규칙 변경은 요구하지 않습니다. 저장 구조와 내부 이벤트 이름은 BE에서 확정해 주세요. 180초 플레이와 카운트다운을 포함해 서버의 `playEndsAt`까지 유지해야 합니다.

## FE와 BE가 맞춰야 하는 데이터

FE는 `WORLD_STATE.payload.avatars[]`의 선택 필드 `activity`를 받을 준비가 되어 있습니다. 아래는 BE에 제안하는 응답의 해당 부분입니다.

```json
{
  "userId": "101",
  "activity": "BUNGEOPPANG"
}
```

- `"BUNGEOPPANG"`: 붕어빵 이용 상태 표시
- `null` 또는 필드 생략: 상태 말풍선 제거
- 서버 내부 라운드 ID, 점수, 보상, 조리 입력 기록은 이 필드로 공개하지 않습니다.
- 기존 서버처럼 필드가 없어도 FE는 정상 처리하지만, 상태 말풍선은 표시되지 않습니다. 기능을 사용하려면 BE 변경도 배포되어야 합니다.
- 기존 공개 계약은 [world-websocket-api.md](world-websocket-api.md)를 참고하고, `activity` 추가는 BE 최종 계약 확정 시 함께 갱신해 주세요.

## 표시 시점

| 상황 | 처리 |
| --- | --- |
| 서버가 새 라운드 시작을 승인하고 커밋 | 표시 시작. 서버가 정한 카운트다운 포함 |
| 조리 진행 중 / 같은 채널에 다른 사용자가 나중에 입장 | 현재 상태를 스냅샷으로 전달하여 표시 유지 |
| 완료·이용 종료·무효 처리 커밋 | 해당 라운드의 상태 해제 |
| 완료 요청 없이 서버 조리 종료 시각 도달 | 월드 갱신에서 상태 자동 해제 |
| 시작·종료 트랜잭션 롤백 | 공개 상태 변경 없음 |
| 채널 퇴장·이동 또는 연결 종료 | 기존 채널의 상태 정리 |
| 이전 라운드 이벤트가 늦게 도착 | 새 라운드 상태를 변경하지 않음 |

미니게임 입장 대기 화면과 결과 화면에는 조리 중 상태를 유지하지 않는 안입니다. v4/v5는 서버의 `playEndsAt`, 기존 v2는 서버 시작 시각부터 60초를 기준으로 만료시켜 주세요.

## BE 개발자에게 부탁드릴 작업

1. **이용 상태 기능을 구현하거나 기존 구현을 확인해 주세요.** 이번 FE 브랜치에는 BE 코드가 없습니다. BE 작업 브랜치에 비슷한 기능이 있다면 최종 필드명과 값을 FE와 맞춰 주세요. FE 제안은 `activity: "BUNGEOPPANG" | null`입니다.
2. **라운드 처리와 이벤트 연결을 확인해 주세요.** 시작·종료 이벤트는 실제 커밋 후 방송되어야 하고, 거절·롤백된 요청은 상태를 바꾸면 안 됩니다. 기존 보상·점수·종료 처리에 영향이 없는지도 검토해 주세요.
3. **현재 서버 코드에 통합하고 BE 배포를 확인해 주세요.** 기존 미니게임 활성 환경을 사용합니다. 현재 설정은 `(local | dev) & db & !prod & !production` 프로필과 `ontop.minigames.enabled=true` 조건입니다. 이번 요청은 운영 프로필의 활성 범위를 넓히는 작업을 포함하지 않습니다.
4. **실제 dev 환경에서 두 계정으로 확인해 주세요.** 아래 확인표를 수행하고, 배포한 커밋과 확인 결과를 공유해 주세요. FE와 BE 변경이 모두 반영된 환경에서 확인해야 합니다.

### 실제 환경 확인표

- [ ] A 계정이 시작하면 같은 채널 B 계정에게 상태 말풍선이 보임
- [ ] 조리 도중 B 계정이 나중에 입장해도 보임
- [ ] 일반 채팅과 색상이 다르고, 채팅이 사라진 뒤에도 조리 중 상태는 유지됨
- [ ] 정상 완료·이용 종료 시 사라짐
- [ ] 완료 요청을 보내지 못해도 서버 조리 종료 시각이 지나면 사라짐
- [ ] 시작 거절·종료 거절 또는 롤백 시 잘못 표시되거나 지워지지 않음
- [ ] 채널 이동·연결 종료 후 기존 채널에 표시가 남지 않음
- [ ] 다른 채널에는 전달되지 않음
- [ ] 연속 플레이에서 이전 판의 지연 이벤트가 새 판의 상태를 지우거나 다시 켜지 않음

## 이전 참고 구현의 검증 기록과 현재 범위

- 아래 수치는 이전 `feat/bungeoppang-activity-bubble` 참고 구현 시점의 기록이며, 이번 FE 전용 MR의 BE 구현 완료를 의미하지 않습니다.
- FE 단위 테스트: 75개 파일, 746개 테스트 통과
- FE 테스트 포함 타입 검사, 프로덕션 빌드, migration boundary 검사 통과
- 이전 참고 구현의 BE 테스트: 44개 통과. 해당 BE 소스/테스트는 이번 FE 전용 변경에서 제외했습니다.
- 브라우저 테스트: 일반 채팅과의 색상 구분, 채팅 만료 후 상태 유지, 서버 해제 시 제거를 확인

BE 검증은 로컬 테스트와 송신 대역을 사용했고, 브라우저 검증은 서버 계약 fixture를 사용했습니다. **실제 dev의 두 계정·공유 DB·배포 환경 검증은 아직 수행하지 않았으므로 위 확인을 부탁드립니다.**
