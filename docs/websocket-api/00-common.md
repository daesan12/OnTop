# 📌 공통 규격

연결·메시지 공통 형식과 ERD 경계입니다. 처음 한 번 확인하고 개별 기능 페이지를 참고합니다.

## 1. 적용 범위

| 포함 | 제외 |
| --- | --- |
| Raw WebSocket 연결·종료 | 정식 로그인·계정 복구 |
| 연결별 임시 사용자 식별 | DB 접근·엔티티·ERD 변경 |
| 테이블 착석·퇴장·첫 착석자의 게임 선택 | 실제 게임 시작·게임별 입력 |
| 준비·준비 취소·전원 준비 표시 | 엽전 조회·차감·추가 베팅·정산 |
| 참가자 전체 상태 동기화 | 광장 이동·채팅·관전·AI 대행 |

`allReady=true`는 준비 조건 충족을 뜻합니다. 실제 게임 시작, 판돈 차감, 게임 기록 생성 완료를 뜻하지 않습니다.

## 2. ERD와의 관계

사용자가 제공한 1차 ERD 이미지를 기준으로 역할을 구분합니다. ERD 담당자가 이후 변경하는 스키마를 이 문서에서 확정하거나 수정하지 않습니다.

| ERD 테이블·필드 | 의미 | 이번 API에서의 처리 |
| --- | --- | --- |
| `users.id` | 실제 계정의 사용자 ID | 조회하지 않음. 임시 사용자 ID와 구분 |
| `users.game_restricted_until` | 게임 참가 제한 종료 시각 | 실제 계정 기반 참가 제한 검증은 후속 인증 연동 범위 |
| `game_types` | 게임 종류·필요 인원·최대 인원 | 조회하지 않음. 개발용 테이블 정원만 별도로 사용 |
| `game_sessions.id` | 게임 한 판의 ID | 생성하지 않음 |
| `game_sessions.room_id` | 게임이 진행된 방 식별자 | 향후 테이블·경기 연결을 검토할 항목. 이번 `tableId`를 DB에 저장하지 않음 |
| `game_participants` | 게임 한 판의 참가 기록·결과·이탈 정보 | 착석만으로 행을 생성하지 않음. 준비 상태는 메모리에서 관리 |
| `wallets`, `wallet_transactions` | 잔액과 엽전 거래 이력 | 접근·변경하지 않음 |
| `minigame_sessions` | 미니게임 실행·보상 기록 | 사용하지 않음 |

이번 API의 **테이블은 게임 시작 전 대기 공간**입니다. ERD의 게임 세션과 별개이며, WebSocket 연결도 별개의 객체입니다.

개발용 임시 ID는 실제 계정 인증이나 잔액·참가 제한 검증을 대신하지 않습니다. 대기 중 연결 종료를 정식 경기의 기권·이탈 기록으로 저장하지 않습니다. 실제 경기·재접속·기권 처리는 이번 범위 밖입니다.

## 3. 연결 규격

| 항목 | 규격 |
| --- | --- |
| 로컬 주소 | `ws://localhost:8080/ws/tables` |
| 연결 경로 | `/ws/tables` |
| 방식 | Raw WebSocket, STOMP·SockJS 미사용 |
| 메시지 형식 | UTF-8 JSON 텍스트 객체 |
| 활성 환경 | `local` 프로필의 로컬 개발 환경 |
| Origin | 동일 출처의 개발 페이지만 허용. 모든 Origin 허용 설정 사용 안 함 |
| 사용자 식별 | 서버가 연결 성공 시 발급하는 `dev-` 접두사의 UUID 문자열 |
| 저장 | 서버 메모리. 서버 재시작 시 전체 초기화 |

- 브라우저 개발 페이지는 같은 서버의 HTTP 주소에서 열어 연결합니다. `file://`로 연 HTML은 지원 대상이 아닙니다.
- 연결 성공 후 첫 애플리케이션 메시지는 `CONNECTED`입니다.
- 클라이언트는 `CONNECTED` 수신 이후 요청을 보냅니다.
- `userId`는 연결에 귀속되며 클라이언트가 선택하거나 변경할 수 없습니다.
- 새 연결은 새 임시 사용자입니다. 새 탭도 별도 사용자로 취급합니다. 재연결에 따른 기존 좌석 복구는 제공하지 않습니다.
- `local` 외 프로필에서는 이 개발용 연결 경로와 확인 페이지를 활성화하지 않습니다.

### 개발용 테이블

| tableId | 정원 | 전원 준비 최소 인원 |
| --- | --- | --- |
| `table-1` | 2 | 2 |
| `table-2` | 2 | 2 |

서버 시작 시 두 테이블을 생성합니다. 테이블 생성·삭제·목록 조회 API는 이번 범위에 없습니다. 정원 2명은 연결 검증용 설정이며, 정식 2~4인 게임의 인원 규칙을 변경하는 값이 아닙니다.

## 4. 공통 메시지 형식

### 클라이언트 요청

```json
{
  "requestId": "req-001",
  "type": "TABLE_JOIN",
  "payload": {
    "tableId": "table-1"
  }
}
```

| 필드 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| `requestId` | string | O | 공백이 아닌 1~64자. 클라이언트가 요청마다 새 식별자 생성 |
| `type` | string | O | 대문자 메시지 이름. 대소문자 구분 |
| `payload` | object | O | 메시지별 데이터. 인자가 없으면 `{}` |

- 루트는 JSON 객체여야 합니다. 배열·문자열·null은 요청으로 받지 않습니다.
- 필수 필드 누락, 타입 오류, 명세에 없는 필드는 오류로 처리합니다. `userId`·좌석 번호를 요청에 추가해 사용자를 지정할 수 없습니다.
- `requestId`는 요청·응답 연결용입니다. 결제·정산의 멱등성 키가 아니며, 같은 ID의 재전송을 자동 중복 제거한다고 보장하지 않습니다.
- 자동 재시도는 하지 않습니다. 응답이 오기 전 같은 동작 버튼은 비활성화하고, 연결 종료 시 미완료 요청을 실패로 정리합니다.

### 서버 메시지

모든 서버 메시지는 `requestId`, `type`, `payload` 세 필드를 포함합니다.

| 필드 | 타입 | 설명 |
| --- | --- | --- |
| `requestId` | string 또는 null | 직접 응답은 요청 ID 복사. 자발적인 상태 알림은 null |
| `type` | string | 서버 메시지 이름 |
| `payload` | object | 메시지별 결과 |

요청 성공 시 `TABLE_JOIN`·`GAME_SELECT`·`READY_SET`은 요청자에게 `TABLE_STATE`, `TABLE_LEAVE`는 `TABLE_LEFT`를 반환합니다. 별도 ACK 메시지는 사용하지 않습니다.

같은 상태를 다른 참가자에게 전송할 때는 `requestId=null`로 보냅니다. 다른 사용자가 생성한 요청 ID를 참가자 전체에 노출하지 않습니다.

## 5. 메시지 목록

| 방향 | type | 용도 | 수신 대상 |
| --- | --- | --- | --- |
| 서버 → 클라이언트 | `CONNECTED` | 연결 완료·임시 사용자 식별 | 연결한 본인 |
| 클라이언트 → 서버 | `TABLE_JOIN` | 테이블 착석 | 서버 |
| 클라이언트 → 서버 | `GAME_SELECT` | 첫 착석자의 게임 선택 | 서버 |
| 클라이언트 → 서버 | `TABLE_LEAVE` | 현재 테이블 퇴장 | 서버 |
| 클라이언트 → 서버 | `READY_SET` | 준비·준비 취소 | 서버 |
| 서버 → 클라이언트 | `TABLE_STATE` | 테이블 전체 상태 | 요청자 또는 해당 테이블 참가자 |
| 서버 → 클라이언트 | `TABLE_LEFT` | 본인 퇴장 완료 | 퇴장 요청자 |
| 서버 → 클라이언트 | `ERROR` | 요청 실패 | 요청자 |

## 6. 연결 종료·동시 요청

### 대기 중 연결 종료

1. 정상 종료 또는 서버가 연결·전송 실패를 감지하면 연결 정보를 제거합니다.
2. 착석 중이었다면 좌석을 비우고 남은 참가자의 준비를 false로 바꿉니다.
3. 실제 테이블 상태가 바뀐 경우 버전을 1 증가시키고 남은 참가자에게 상태를 알립니다.
4. 종료한 연결에는 `TABLE_LEFT` 응답을 보내지 않습니다.

네트워크 단절은 서버가 즉시 인지하지 못할 수 있습니다. 이 문서는 단절 후 몇 초 이내 정리를 보장하지 않으며, 자동 재접속·heartbeat 규격은 포함하지 않습니다. 실패 감지 후 중복 정리가 호출돼도 상태·버전을 중복 변경하지 않습니다.

이 규칙은 **대기 상태에만 적용**합니다. 향후 경기 중 연결 종료에는 AI 대행·재접속 정책을 적용해야 하며 여기의 좌석 제거를 그대로 재사용하지 않습니다.

### 동시 요청 처리

- 빈 좌석 확인과 참가자 등록을 하나의 원자적 작업으로 처리해 정원을 초과하지 않습니다.
- 사용자 착석 위치와 테이블 좌석 정보가 서로 다르게 남지 않도록 함께 변경합니다.
- 준비·퇴장·연결 종료도 같은 상태 변경 순서에 따라 처리합니다. 이미 제거된 사용자의 준비 요청은 거절합니다.
- 참가자 구성 변경에 따른 준비 초기화와 버전 증가는 한 번의 상태 변경으로 처리합니다.
- 테이블 잠금을 유지한 채 네트워크 전송하지 않습니다. 연결별 전송은 직렬화하고 상태 처리 순서를 보존합니다.

## 7. 전체 사용 예시

| 순서 | 행동 | 기대 결과 |
| --- | --- | --- |
| 1 | 브라우저 A·B 연결 | 각자 다른 임시 userId의 CONNECTED 수신 |
| 2 | A가 table-1 착석 | A 좌석 배정, ready=false, allReady=false |
| 3 | B가 table-1 착석 | 두 화면에 같은 좌석 목록·준비 상태 표시 |
| 4 | A가 ready=true 전송 | 두 화면에서 A 준비 표시, allReady=false |
| 5 | B가 ready=true 전송 | 두 화면에서 allReady=true. 게임은 시작하지 않음 |
| 6 | A가 ready=false 전송 | 두 화면에서 allReady=false |
| 7 | B가 퇴장 | B는 TABLE_LEFT 수신, A는 빈 좌석·본인 준비 false 상태 수신 |
| 8 | A 연결 종료 | 테이블이 빈 상태로 정리됨 |

## 8. 검증 항목

- 두 연결의 정상 착석·준비·준비 취소 동기화.
- 한 명만 준비했을 때 전원 준비로 판정되지 않음.
- 세 번째 사용자의 만석 테이블 착석 거절.
- 마지막 좌석에 대한 동시 요청 중 한 명만 성공.
- 같은 사용자·같은 테이블의 중복 착석과 같은 준비값 반복 요청에서 상태·버전 유지.
- 다른 테이블로 무단 중복 착석 거절.
- 참가자 추가·퇴장·연결 종료 시 준비 초기화.
- 잘못된 JSON·공통 필드·payload·지원하지 않는 type 오류 응답.
- 오류 요청이 기존 상태를 변경하지 않음.
- table-1 변경이 table-2·미착석 연결에 전달되지 않음.
- 반복 연결 정리에서 인원·버전이 중복 변경되지 않음.
- 새로운 연결에는 새로운 임시 userId 발급.
- 게임 기록·참가 기록·지갑·거래 이력이 생성되거나 변경되지 않음.
- `local` 외 환경에서 개발용 경로 비활성.

## 9. 참고 기준

- 사용자 제공 1차 ERD 이미지: 사용자·지갑·거래 원장·게임 종류·게임 세션·게임 참가자·미니게임 세션.
- 사용자 지정 [OnTop 통합 기획서 v0.4](https://app.notion.com/p/OnTop_-_-154161842b868387b6ad0174db68ee71): 첫 착석자의 게임 선택·전원 준비. 선택자 대기 중 이탈 시 남은 참가자에게 권한을 넘기는 규칙은 2026-10-19 사용자 확인으로 보완했다. 과거 v0.3의 AI 대행 가정은 현재 구현 기준으로 사용하지 않는다.
- [Spring WebSocket 서버 문서](https://docs.spring.io/spring-framework/reference/6.2/web/websocket/server.html): Raw WebSocket 처리, Origin 제한, 연결별 동시 전송 제어.
