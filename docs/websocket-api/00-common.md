# 📌 공통 규격

연결·메시지 공통 형식과 ERD 경계입니다. 처음 한 번 확인하고 개별 기능 페이지를 참고합니다.

이 페이지의 테이블 기본 범위와 별도로 [경기 통신](09-game-communication.md)은 오목·주사위·원카드·거짓말 다리의 입력·상태·관전·복구를 구현·검증했습니다. [광장 계약](../world-websocket-api.md)은 서버 이동·충돌·20m 채팅을 다룹니다. 공통 규격의 완료는 실제 로그인·참가 차감·DB 정산·운영 적용의 완료를 뜻하지 않습니다.

## 1. 적용 범위

| 포함 | 제외 |
| --- | --- |
| Raw WebSocket 연결·종료 | 정식 로그인·계정 복구 |
| 연결별 임시 사용자 식별 | DB 접근·엔티티·ERD 변경 |
| 선택적 서버 검증 사용자 연결부 | 실제 네이버·SSAFY 로그인·JWT/세션 구현 |
| 테이블 착석·퇴장·첫 착석자의 게임 선택 | 실제 게임 시작·게임별 입력 |
| 준비·준비 취소·전원 준비 표시 | 엽전 조회·차감·추가 베팅·정산 |
| 참가자 전체 상태 동기화 | 근거리 채팅·이력·관전·AI 대행(채널 채팅·위치 공유는 별도 광장 계약) |

`allReady=true`는 준비 조건 충족을 뜻합니다. 실제 게임 시작, 판돈 차감, 게임 기록 생성 완료를 뜻하지 않습니다.

## 2. ERD와의 관계

사용자가 제공한 1차 ERD 이미지를 기준으로 역할을 구분합니다. ERD 담당자가 이후 변경하는 스키마를 이 문서에서 확정하거나 수정하지 않습니다.

| ERD 테이블·필드 | 의미 | 이번 API에서의 처리 |
| --- | --- | --- |
| `users.id` | 실제 계정의 사용자 ID | 직접 조회하지 않음. 기본 dev ID와 구분. 인증 연결 모드는 서버 검증기가 반환한 내부 ID를 사용 |
| `users.game_restricted_until` | 게임 참가 제한 종료 시각 | 실제 계정 기반 참가 제한 검증은 후속 인증 연동 범위 |
| `game_types` | 게임 종류·필요 인원·최대 인원 | 조회하지 않음. 개발용 테이블 정원만 별도로 사용 |
| `game_sessions.id` | 게임 한 판의 ID | 생성하지 않음 |
| `game_sessions.room_id` | 게임이 진행된 방 식별자 | 향후 테이블·경기 연결을 검토할 항목. 이번 `tableId`를 DB에 저장하지 않음 |
| `game_participants` | 게임 한 판의 참가 기록·결과·이탈 정보 | 착석만으로 행을 생성하지 않음. 준비 상태는 메모리에서 관리 |
| `wallets`, `wallet_transactions` | 잔액과 엽전 거래 이력 | 접근·변경하지 않음 |
| `minigame_sessions` | 미니게임 실행·보상 기록 | 사용하지 않음 |

이번 API의 **테이블은 게임 시작 전 대기 공간**입니다. ERD의 게임 세션과 별개이며, WebSocket 연결도 별개의 객체입니다.

개발용 임시 ID는 실제 계정 인증이나 잔액·참가 제한 검증을 대신하지 않습니다. 대기 중 연결 종료를 정식 경기의 기권·이탈 기록으로 저장하지 않습니다. 인증 사용자 재접속의 조회·30초 유예 연결부는 [재접속 계약](../game-reconnect.md)에 있으며 실제 경기·기권 처리는 경기 담당 미연결입니다.

## 3. 연결 규격

| 항목 | 규격 |
| --- | --- |
| 로컬 주소 | `ws://localhost:8080/ws/tables` |
| 연결 경로 | `/ws/tables` |
| 방식 | Raw WebSocket, STOMP·SockJS 미사용 |
| 메시지 형식 | UTF-8 JSON 텍스트 객체 |
| 활성 환경 | `local` 프로필의 로컬 개발 환경 |
| Origin | 동일 출처의 개발 페이지만 허용. 모든 Origin 허용 설정 사용 안 함 |
| 사용자 식별 | 기본 모드 `dev-UUID` / 인증 모드 서버 검증 내부 계정 ID 문자열 |
| 저장 | 서버 메모리. 서버 재시작 시 전체 초기화 |

- 브라우저 개발 페이지는 같은 서버의 HTTP 주소에서 열어 연결합니다. `file://`로 연 HTML은 지원 대상이 아닙니다.
- 연결 성공 후 첫 애플리케이션 메시지는 `CONNECTED`입니다.
- 기본 모드는 `CONNECTED` 수신 이후 요청을 보냅니다. 경기 담당이 등록된 인증 모드에서는 자동 `GAME_CONNECTION_STATE`로 대기 기능 허용 상태도 확인합니다. 담당 미등록 시 자동 알림 없이 대기 기능을 유지합니다.
- `userId`는 연결에 귀속되며 클라이언트가 선택하거나 변경할 수 없습니다.
- 기본 모드의 새 연결·새 탭은 새 임시 사용자이며 대기 좌석 복구는 제공하지 않습니다. 인증 모드의 중복 연결은 새 연결만 close 1008로 거절하고, 단절 후 경기 복귀는 [재접속 계약](../game-reconnect.md)을 따릅니다.
- `local` 외 프로필에서는 이 개발용 연결 경로와 확인 페이지를 활성화하지 않습니다.

### 개발용 테이블

| tableId | 정원 | 전원 준비 최소 인원 |
| --- | --- | --- |
| `table-1` | 미선택·원카드·거짓말 4, 오목·주사위 2 | 2 |
| `table-2` | 미선택·원카드·거짓말 4, 오목·주사위 2 | 2 |

채널 미설정 개발 모드만 위 table-1·table-2를 사용합니다. 채널을 설정하면 채널마다 테이블을 분리하며 먼저 CHANNEL_JOIN에 성공한 뒤 [GET /api/v1/tables?channelId=…](../table-query-api.md)의 서버 발급 tableId를 사용합니다. 게임별 정원은 OnTop v0.4 기준이며 2명 이상 현재 착석자 전원 준비로 판정합니다. 테이블 생성·삭제 API와 실제 경기·DB는 미구현입니다.

### 광장과 테이블 보기

연결 → 채널 입장 → 위치·채팅·감정표현 → 현재 채널 테이블 목록 → 보기 또는 착석 → 선택·준비 순으로 연동합니다. [광장 계약](../world-websocket-api.md)과 [공개 대기 상태 보기](08-table-watch.md)를 함께 따릅니다. WORLD_STATE의 위치 버전과 CHANNEL_STATE의 입퇴장 버전·테이블 버전을 서로 비교하지 않습니다. 채널 입장 시 서버 스폰 위치가 생성됩니다. WORLD_MOVE는 seq/dx/dz/run/jump 입력만 보내고, 새 채널·새 연결에서는 캐시와 입력 순번을 초기화합니다.

감정표현의 종류·단축키·아바타 모션은 팀과 프론트가 정하고, 서버는 등록한 코드의 같은 채널 전달을 담당합니다. WAVE/CLAP은 테스트 예시이며 최종 제품 목록이 아닙니다. 현재 소유권·구매 권한 조건은 없고 같은 채널의 대기 착석자·보기 사용자도 사용할 수 있습니다. 실제 로그인·경기 복구 게이트는 별도로 유지합니다.

TABLE_WATCH_STATE는 착석 TABLE_STATE와 별도 캐시에 저장합니다. 구독은 좌석·선택권·준비·시작 인원을 점유하지 않습니다. 명시 해지는 TABLE_WATCH_LEFT(요청 ID), 착석·채널 퇴장 성공의 자동 해지는 TABLE_WATCH_LEFT(null) 다음 해당 성공 응답입니다. 실패는 기존 구독을 유지하고 연결 종료·heartbeat는 구독을 정리합니다. 실제 경기 관전·비공개 정보는 미연결입니다.

## 4. 공통 메시지 형식

### 클라이언트 요청

```json
{
  "requestId": "req-001",
  "type": "TABLE_JOIN",
  "payload": {
    "tableId": "table-1"
  }
}
```

| 필드 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| `requestId` | string | O | 공백이 아닌 1~64자. 클라이언트가 요청마다 새 식별자 생성 |
| `type` | string | O | 대문자 메시지 이름. 대소문자 구분 |
| `payload` | object | O | 메시지별 데이터. 인자가 없으면 `{}` |

- 루트는 JSON 객체여야 합니다. 배열·문자열·null은 요청으로 받지 않습니다.
- 중복 JSON 키와 뒤따르는 추가 JSON도 거절합니다. 텍스트 메시지 수신 제한은 16KiB입니다.
- 필수 필드 누락, 타입 오류, 명세에 없는 필드는 오류로 처리합니다. `userId`·좌석 번호를 요청에 추가해 사용자를 지정할 수 없습니다.
- `requestId`는 요청·응답 연결용입니다. 결제·정산의 멱등성 키가 아니며, 같은 ID의 재전송을 자동 중복 제거한다고 보장하지 않습니다.
- 자동 재시도는 하지 않습니다. 응답이 오기 전 같은 동작 버튼은 비활성화하고, 연결 종료 시 미완료 요청을 실패로 정리합니다.

### 서버 메시지

모든 서버 메시지는 `requestId`, `type`, `payload` 세 필드를 포함합니다.

| 필드 | 타입 | 설명 |
| --- | --- | --- |
| `requestId` | string 또는 null | 직접 응답은 요청 ID 복사. 자발적인 상태 알림은 null |
| `type` | string | 서버 메시지 이름 |
| `payload` | object | 메시지별 결과 |

요청 성공 시 `TABLE_JOIN`·`GAME_SELECT`·`READY_SET`은 요청자에게 `TABLE_STATE`, `TABLE_LEAVE`는 `TABLE_LEFT`를 반환합니다. 별도 ACK 메시지는 사용하지 않습니다.

같은 상태를 다른 참가자에게 전송할 때는 `requestId=null`로 보냅니다. 다른 사용자가 생성한 요청 ID를 참가자 전체에 노출하지 않습니다.

## 5. 메시지 목록

| 방향 | type | 용도 | 수신 대상 |
| --- | --- | --- | --- |
| 서버 → 클라이언트 | `CONNECTED` | 연결 완료·임시 사용자 식별 | 연결한 본인 |
| 클라이언트 → 서버 | `TABLE_JOIN` | 테이블 착석 | 서버 |
| 클라이언트 → 서버 | `GAME_SELECT` | 첫 착석자의 게임 선택 | 서버 |
| 클라이언트 → 서버 | `TABLE_LEAVE` | 현재 테이블 퇴장 | 서버 |
| 클라이언트 → 서버 | `READY_SET` | 준비·준비 취소 | 서버 |
| 서버 → 클라이언트 | `TABLE_STATE` | 테이블 전체 상태 | 요청자 또는 해당 테이블 참가자 |
| 서버 → 클라이언트 | `TABLE_LEFT` | 본인 퇴장 완료 | 퇴장 요청자 |
| 서버 → 클라이언트 | `ERROR` | 요청 실패 | 요청자 |

## 6. 연결 종료·동시 요청

### 대기 중 연결 종료

1. 정상 종료 또는 서버가 연결·전송 실패를 감지하면 연결 정보를 제거합니다.
2. 착석 중이었다면 좌석을 비우고 남은 참가자의 준비를 false로 바꿉니다.
3. 실제 테이블 상태가 바뀐 경우 버전을 1 증가시키고 남은 참가자에게 상태를 알립니다.
4. 종료한 연결에는 `TABLE_LEFT` 응답을 보내지 않습니다.

네트워크 단절은 서버가 즉시 인지하지 못할 수 있습니다. [heartbeat](../websocket-heartbeat.md)는 서버 Ping/Pong으로 응답 없는 연결을 감지합니다. 기본 10초 주기·10초 응답 제한이며 단절 후 정확한 감지 시간을 보장하지 않습니다. 자동 클라이언트 재접속은 별도입니다. 실패 감지 후 중복 정리가 호출돼도 상태·버전을 중복 변경하지 않습니다.

이 규칙은 **대기 상태에만 적용**합니다. 인증 사용자의 경기 복귀는 [30초 재접속 연결부](../game-reconnect.md)를 따릅니다. 실제 경기 상태는 경기 담당이 제공하며 AI 대행은 없습니다.

### 동시 요청 처리

- 빈 좌석 확인과 참가자 등록을 하나의 원자적 작업으로 처리해 정원을 초과하지 않습니다.
- 사용자 착석 위치와 테이블 좌석 정보가 서로 다르게 남지 않도록 함께 변경합니다.
- 준비·퇴장·연결 종료도 같은 상태 변경 순서에 따라 처리합니다. 이미 제거된 사용자의 준비 요청은 거절합니다.
- 참가자 구성 변경에 따른 준비 초기화와 버전 증가는 한 번의 상태 변경으로 처리합니다.
- 테이블 잠금을 유지한 채 네트워크 전송하지 않습니다. 연결별 전송은 직렬화하고 상태 처리 순서를 보존합니다.

## 7. 전체 사용 예시

| 순서 | 행동 | 기대 결과 |
| --- | --- | --- |
| 1 | 브라우저 A·B 연결 | 각자 다른 임시 userId의 CONNECTED 수신 |
| 2 | A가 table-1 착석 | A 좌석 배정, ready=false, allReady=false |
| 3 | B가 table-1 착석 | 두 화면에 같은 좌석 목록·준비 상태 표시 |
| 4 | 첫 착석자 A가 GAME_SELECT로 DICE 선택 | 두 화면에 gameCode=DICE, capacity=2, 전원 ready=false |
| 5 | A가 ready=true 전송 | 두 화면에서 A 준비 표시, allReady=false |
| 6 | B가 ready=true 전송 | 두 화면에서 allReady=true. 기본 모드는 게임을 시작하지 않음 |
| 7 | A가 ready=false 전송 | 두 화면에서 allReady=false |
| 8 | B가 퇴장 | B는 TABLE_LEFT 수신, A는 빈 좌석·본인 준비 false 상태 수신 |
| 9 | A 연결 종료 | 빈 테이블 정리·게임 선택 해제·정원 4 복원 |

## 8. 검증 항목

- 두 연결의 정상 착석·준비·준비 취소 동기화.
- 한 명만 준비했을 때 전원 준비로 판정되지 않음.
- DICE 등 2인 게임을 선택한 만석 테이블에서 세 번째 사용자 착석 거절.
- 마지막 좌석에 대한 동시 요청 중 한 명만 성공.
- 같은 사용자·같은 테이블의 중복 착석과 같은 준비값 반복 요청에서 상태·버전 유지.
- 다른 테이블로 무단 중복 착석 거절.
- 참가자 추가·퇴장·연결 종료 시 준비 초기화.
- 잘못된 JSON·공통 필드·payload·지원하지 않는 type 오류 응답.
- 오류 요청이 기존 상태를 변경하지 않음.
- table-1 변경이 table-2·미착석 연결에 전달되지 않음.
- 반복 연결 정리에서 인원·버전이 중복 변경되지 않음.
- 새로운 연결에는 새로운 임시 userId 발급.
- 게임 기록·참가 기록·지갑·거래 이력이 생성되거나 변경되지 않음.
- `local` 외 환경에서 개발용 경로 비활성.

## 10. 경기 통신 연결부

2026-10-20 [경기 통신 상세 7종](09-game-communication.md)을 기존 Notion 목록과 공통 안내에 반영했다. 위 기본 대기 흐름에 실제 경기 엔진·차감·정산이 추가된 것은 아니다.

- `GAME_STATE_CHECK`와 `GAME_STATE`: 인증 계정의 상태 조회·참가자 자동 갱신. 공개 상태와 본인 개인 상태만 개별 전송한다.
- `GAME_ACTION_SEND`와 `GAME_ACTION_RESULT`: 경기 입력 전달·처리 확인. 실제 턴·규칙·중복 반영 방지는 경기 담당이 연결한다.
- `GAME_WATCH`·`GAME_UNWATCH`·`GAME_WATCH_LEFT`: 대기 테이블 보기와 별개인 경기 관전 연결부. 관전자 개인 상태는 `{}`이며 Gateway에서 현재 권한을 확인한다.
- 실제 로그인·엔진은 미연결이다. 새 항목은 진행 중이며 기본 dev의 인증 필요 오류가 정상이다. 최초 응답은 원래 요청 ID, 자동 갱신은 null이다.

## 11. 경기 종료·정산 결과

2026-10-20 [결과 계약](../game-result-api.md)의 GAME_RESULT_CHECK/GAME_RESULT를 Notion 상세2종과 공통·오류 안내에 반영하고 다시 열어 확인했다. 본인 참가 결과만 전달하며 PENDING/null 순증감과 SETTLED/확정 순증감을 구분한다. 결과 알림으로 지급이나 좌석·조작권 전환을 실행하지 않는다. Postman06의 저장 메시지8개도 원본과 대조했다. 실제 DB·정산·지급은 미연결이다.
