# 이벤트 당첨 결과 저장 계약

Jira S15P31B105-352. 이 문서는 V153 스키마의 경계와 후속 추첨·연락처 API에서 지켜야 할 데이터 규칙을 설명한다.

## 회차와 시간

`event_rounds`는 `RAFFLE`, `BUNGEOPPANG`, `JUMPMAP`, `ASSET_VALUE` 부문마다 KST 월요일의
`week_start_date`를 가진다. 같은 부문·주차는 한 행뿐이다. `starts_at`은 포함하고 `ends_at`은
제외하는 UTC 시각으로 저장한다. 예를 들어 일요일 23:59:59.999 KST 기록은 후보이고 다음 월요일
00:00 KST 기록은 아니다. `announces_at` 이전에는 회원에게 결과를 공개하지 않는다.

응모권 회차는 기존 `raffle_rounds`와 한 번만 연결된다. 추첨 서비스는 두 회차의 주차와 판매 종료 시각이
일치하는지 확인하고, 판매된 `raffle_tickets`만 후보로 사용해야 한다. 마이그레이션은 이벤트 회차나 상품을
미리 만들지 않는다. 생성·마감·자동 추첨은 후속 작업에서 구현한다.

## 상품과 당첨자

`event_prize_slots`의 한 행은 상품 한 개에 해당한다. 주간 응모권의 1등 1개·2등 2개·3등 5개는
각각 1·2·5개의 슬롯으로 표현한다. `event_winners`는 슬롯당 한 명, 부문·주차당 회원 한 번만
기록한다. 따라서 같은 주차의 응모권에 여러 장을 보유한 회원이 두 등수를 받을 수 없다. 다른
부문에서의 중복 당첨은 가능하다. 슬롯과 당첨 결과의 회차가 다른 경우 복합 외래 키가 거절한다.

`raffle_ticket_id`는 응모권 당첨 근거다. 게임상은 서버의 원본 기록 ID와 점수·완주 시간 및 기록
달성 시각을, 보유 가치상은 마감 시각 합계와 처음 그 합계에 도달한 시각을 보존한다. 기록 유효성,
응모권의 실제 소유자·회차, GM 제외, 부문별 슬롯 수, 동점 순서는 후속 서비스가 확정 트랜잭션에서
검증한다. 관리자 조회 권한 ID가 GM의 기준이다.

보유 가치 동점 선착순은 현재 `wallets.updated_at`만으로 판정하지 않는다. 예약 금액 변경 등으로
그 시각이 갱신될 수 있으므로 엽전 원장·의상 소유 변화 또는 이벤트용 시점 기록에서 합계 도달 시각을
확정해야 한다. 산정식과 동점 기준을 구현·검증하기 전에는 보유 가치상을 확정하지 않는다.

`event_rounds.finalized_at`은 결과 확정 시각이며, 자동 또는 관리자 실행 출처를 함께 저장한다.
`event_finalization_attempts`는 성공·이미 확정·실패를 포함한 실행 이력을 남기기 위한 테이블이다.
같은 회차의 재시도는 이미 확정된 `event_winners`를 변경하지 않아야 한다.

## 연락처

`event_winner_contacts`는 회원·KST 주차당 암호화된 전화번호 한 건을 저장한다. 같은 주의 여러
당첨 항목에 하나의 제출을 적용하고, 다음 주 당첨은 별도 제출로 관리한다. 암호문과 암호화 키 식별자,
끝 네 자리, 제출·삭제 예정 시각만 DB에 둔다. 평문은 저장하지 않는다. 후속 API는 발표된 당첨자
본인인지 확인한 뒤 저장하고, 관리자 조회 권한과 보관 기간을 별도로 적용해야 한다.

## 마이그레이션 확인

V153은 기존 테이블을 변경하거나 데이터를 채우지 않는다. `db/migration` 공통 경로에 두어 기존
DEV·운영 배포의 Flyway 목록에 포함한다. 프로젝트 전체 버전은 하나의 순서이므로 다른 팀의
마이그레이션과 번호를 조율한 뒤 MR을 병합한다. `EventAwardMigrationMySqlTests`는 별도의 빈
MySQL 8.4 DB에서 V153 직전까지 적용한 후 기존 응모권 회차를 보존하면서 V153을 적용하고,
중복 당첨·회차가 다른 슬롯·연락처 중복을 검증한다.

2026-11-06 DEV 읽기 전용 확인에서는 V151까지 성공했고 `db/shop`의 V100·V152 및 상점 테이블은
적용되지 않았다. 이 상태에서 V153이 먼저 적용되면 낮은 버전의 선택적 상점 마이그레이션을
나중에 위치만 추가하는 방식으로는 Flyway가 적용하지 못한다. 의상 가치상을 활성화하기 전에
상점 마이그레이션 편입·이력·적용 순서를 별도 계획으로 검증해야 한다. 이 작업은 기존 이력을
`repair`하거나 공유 DB에 `outOfOrder`를 켜지 않는다.
